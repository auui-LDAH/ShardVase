## 0. 决策摘要

| # | 问题 | **决定** | 一句话理由 |
|---|------|----------|-----------|
| **Q6** | 元数据在发布构建中是否保留？ | **剥离描述符表**（开发构建保留） | 实测：发布构建 0 暴露 |
| **Q7** | 接口用符号约定还是函数指针表？ | **符号约定** | 实测：模块函数名 0/32 进二进制，暴露为 0 |

**共同原则**：**把"协议"与"运行期发现"分离** —— 接口用符号约定（零暴露），
元数据只进开发构建，入口仍走既有 `indirect`。这样"可替换"与"不可静态定位"
在**不同层**各自成立，不再矛盾（详见平衡方案文档）。

## 1. Q6：元数据在发布构建中是否保留？

### 决定
**剥离**。描述符表只在开发构建（`PROT_BUILD_WITH_MODULE_TABLE` 定义时）存在；
发布构建不含。

### 依据（实测）
最小实验（同一程序 + 13 个模拟模块）：

| 策略 | 大小 | `.rdata` | 模块名可见 | vs 基线 |
|------|------|----------|-----------|---------|
| S0 基线（无描述符） | 140800 | 43098 | 0 | — |
| S1 全量（名 + 指针） | 142336 | 44378 | **12/13** | +1536 |
| S2 元数据（名，无指针） | 141824 | 43738 | **12/13** | +1024 |

**关键**：描述符把**模块名与清单**带进产物（S2 亦如此，12/13 可见）。
剥离后发布构建的暴露与基线一致（0 个模块名）。

### 影响面
- 开发构建：多 ~1024 字节（可接受，用于工具与自省）
- 发布构建：**0 额外暴露**，但**无运行期自省能力**
- `modcheck` / `compose.py` 走 `modules.json`（源码侧），**不依赖产物中的表** —— 故剥离不影响构建期校验

### 诚实说明
剥离的代价是**运行期无法枚举模块**。若将来需要运行期自省（如统一的
"保护状态"报告接口），需重新评估 —— 那会是一个新的权衡点。

## 2. Q7：接口用符号约定还是函数指针表？

### 决定
**符号约定**。

```c
/* 约定（写进 MODULE_GUIDE，由 modcheck 静态检查）：
 *   每个模块必须导出：
 *     prot_status prot_<name>_scan(prot_<name>_report* out);
 *     uint32_t    prot_<name>_<judge>(const prot_<name>_report*);
 *   可选：
 *     prot_status prot_<name>_init(void);
 *     prot_status prot_<name>_fini(void);
 */
```

### 依据（实测）
| 测量 | 结果 |
|------|------|
| 模块导出函数名总数 | 32 |
| **出现在 `build/demo.exe` 中的个数** | **0 / 32** ✓ |
| `indirect` 表内函数名可见数 | **0 / 8** ✓ |

**原因**：C 语言没有元数据 —— 函数名只在编译期用于链接，**不进二进制**
（`/DEBUG:NONE` 已剥离调试目录）。

→ **符号约定的开销与暴露 = 0**。这是整个方案的基石。

### 为什么不选函数指针表（评审发现的硬错误）
草案原设计把 `init/scan/decide/enforce/fini` 函数指针放进 `const` 表。
但 `src/indirect.c` 的目标是"静态反汇编无直接 call 目标"，而明文函数指针表
**正好抵消**该成果（攻击者读一张表即得全部模块入口）。

**这是协议层面的内部矛盾**：
| 目标 | 要求 |
|------|------|
| 协议要"可替换" | 需要**统一的函数指针表** |
| 保护要"不可静态定位" | **排斥**明文函数指针表 |

符号约定让两者在不同层各自成立。

### 弱化点与补偿
- **弱化**：符号约定无编译期类型检查（函数指针有）
- **补偿**：`modcheck` 已有 `FN_DECL` 正则雏形，可扩展为"命名约定 + 签名检查"
- **已实证**：本项目的 `/alternatename` 弱符号机制（阶段 1 用于序列号
  provider）证明 **MSVC 下"可选符号 + 默认实现"可行且零影响既有工程**

## 3. Q8：第三方须提供 `known_limits`？

### 决定
**要求提供**，但**发布构建剥离其文本**。

### 依据（实测）
| 项 | 现状 |
|----|------|
| 模块数 | 13 |
| **有 `known_limits` 的模块** | **13 / 13**（已全覆盖）|
| `known_limits` 条目总数 | 32 |

**现状已是"全模块声明"** —— 故"要求"不增加负担，只是**把现状固化为规则**。

### 为什么发布构建要剥离文本
`known_limits` 的文字等于**"哪里最弱"的清单**（例如"计时检测固定消耗 250ms"
"回跳呈近平方级开销"）。公开源码（开源）本就可见，但**产物里不必再带一份**
给攻击者省事。

### 影响面
- 开发构建 / 源码：完整保留（P4 诚实边界是资产）
- 发布构建：剥离文本，**保留能力位**（数字无语义，需逆向才懂）
- `modcheck`：新增规则"`known_limits` 不得为空"（现为部分实现）

## 4. Q9：命名是否强制统一？

### 决定
**新模块强制统一；现有模块不改名（加别名过渡）**。

### 依据（实测的命名现状）
| 模块 | 判定函数 | 命名 |
|------|----------|------|
| `antidebug` | `prot_antidebug_detected` | `detected` |
| `dbiguard` | `prot_dbiguard_suspicious` | `suspicious` |
| `vmdetect` | `prot_vmdetect_suspicious` | `suspicious` |
| `integrity` | `prot_integrity_check_self` / `check_iat` | `check_*` |

**现状是三种命名混用**（`detected` / `suspicious` / `check_*`）。

### 为什么不强制改名
**改名 = 破坏 ABI**。这些函数：
- 被宿主（`demo/main.c` 36 处调用、骨架 34 处）直接引用
- 被 `indirect` 表引用（`s_fn[]`）
- 被文档与测试引用

改名会让**所有下游**（含已有第三方接入者）编译失败，收益仅是"整齐"。

### 具体做法
```
新模块（以及未来新增的判定函数）:
    统一用 prot_<name>_suspicious()   <- 选定此名（语义中性: "可疑程度"）
    理由: "detected" 隐含二值, 而实际返回的是可疑项位掩码/计数;
          "suspicious" 更贴合语义, 且现有 2/3 检测器已用该名

现有模块:
    **保留原名**（不改 = 不破坏 ABI）
    在 modules.json 的 exports 里显式登记"判定函数名"
    -> modcheck 依登记校验, 而不依赖命名推断
    -> 可选: 后续版本加 prot_<name>_suspicious() 作为**别名包装**（纯增量,
       不删旧名), 待主版本升级时再考虑弃用
```

### 影响面
- 现有 13 模块：**零改动**
- `modcheck`：新增"导出名一致性"检查（依 `modules.json` 登记）
- 文档（`MODULE_GUIDE.md`）：写明新模块命名规则

## 8. 一句话总结

> **接口用符号约定（零暴露），元数据只进开发构建（发布剥离），
> 入口走既有 indirect，现有模块零改名。**
> 四项决策的共同点是：**在不削弱保护的前提下获得可替换性** ——
> 因为暴露面被精确量化过（符号名 0/32、描述符 +1024 字节 / 12 个模块名可见）。
