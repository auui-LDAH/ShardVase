## 1. 经实测**确认成立**的部分

### 1.1 `report_flags` 投影方案是必要的 ✅

**草案主张**：不同模块的 report 结构体无法统一，故需投影为语义位掩码。

**实测**：

| 模块 | 报告结构体 | 字段数 |
|------|-----------|--------|
| `antidebug` | `prot_antidebug_report` | **12** |
| `dbiguard` | `prot_dbiguard_report` | **4** |
| `vmdetect` | `prot_vmdetect_report` | **3** |

字段名完全不同（`peb_being_debugged` vs `inline_hooks` vs `cpu_hypervisor`），
**无法用同一 struct 表达** → §10.5 的方案是唯一可行解，不是过度设计。

### 1.2 "已有 5/9 规则"准确 ✅

逐条复核 `tools/modcheck.py`：

| 规则 | 复核结果 |
|------|----------|
| R3 依赖闭包 | ✅ **确已实现** —— 实测 `antidebug` 缺 `syscall` 时报 `[X] antidebug 依赖 syscall, 但组合中未包含 syscall` |
| R4 `touches_text`/`verifies_text` 冲突 | ✅ 确已实现（`full` 组合报出 `.text` 冲突） |
| R5 `page_align` 页冲突 | ✅ 确已实现（在 `selfcrypt_proto.py` 构建期，实测 `vm_var` 因与 `main` 同页被跳过） |
| R7 drill 覆盖 | ✅ 确已实现（覆盖率 13/13） |
| R2 `known_limits` 非空 | 🟡 部分（schema 有要求，但无独立检查） |

**结论**：草案说"5/9 已有、渐进式"是**准确的**，没有夸大。

### 1.3 L1–L4 分级是合理的 ✅

L3（全替换）是最有价值的验收目标 —— 它逼出所有隐藏假设。保留。

## 2. **硬错误**（照做会失败）

### 2.1 ❌ §10.9 阶段 6a 的验收标准"产物字节不变"**不可达**

**草案原文**：

> **为什么 6a 要求"产物字节不变"**：这是 P1 的具象化 —— 接入描述符若改变了
> 产物，说明改动触及了布局，必须重新验证。**字节不变是最强的等价性证明。**

**实测推翻**（最小实验：同一程序，加/不加描述符表）：

| 指标 | 无描述符 | 有描述符 | 差异 |
|------|----------|----------|------|
| 文件大小 | 140800 | 141312 | **+512** |
| `.text` 节 | 85328 | 85536 | **+208** |
| `.rdata` 节 | 43098 | 43354 | **+256** |
| SHA-256 | `9606683c...` | `5d911e3d...` | **不同** |

**原因**：描述符结构体 + 注册表数组是**被引用的数据**，
`/OPT:REF` 只能删除未被引用的符号 → 必然保留 → `.rdata` 增大；
配套的遍历循环进 `.text`。这是**语义必然**，不是实现问题。

**更危险的推论**：由于本项目对 `.text` 布局极度敏感（P2：`revoke` 因与
`main` 同页被永久排除），**`.text` 改变意味着 selfcrypt 的加密段与
`main` 的页关系可能变化** → 可能触发页冲突跳过（如 `vm_var`）。

**修正建议**：

```
6a 验收标准改为：
  · 行为等价：e2e T1-T28 + attacks A1-A12 全绿
  · 加密函数数一致（selfcrypt 处理的函数个数不变）
  · 门禁 14/14
  并**明确预期** .text/.rdata 增大（记录增量，确认在可接受范围）
```

> **这同时修正了 P1 的表述**："字节不变"描述的是**同配置重构建**
> （可复现性），而**不同实现**之间的等价性只能用**行为**证明。
> 原草案把两个不同命题混为一谈了。

### 2.2 ❌ §10.3 的函数指针与既有保护机制**直接冲突**

**草案设计**：

```c
typedef struct prot_module_desc {
    ...
    prot_status (*init)(void);
    prot_status (*scan)(void* report_out);
    uint32_t    (*decide)(const void* report);
    ...
} prot_module_desc;
extern const prot_module_desc* const g_prot_modules[];
```

**冲突**（读取 `src/indirect.c` 头部注释确认其设计意图）：

> `indirect.c` 的目标是：
> "静态反汇编：调用点只有 `call prot_indirect_resolve` + `call rax`，
> **无直接 call 目标**（调用方无法静态读到最终函数地址）"

而 `prot_module_desc` 表若以 `const` 存放在 `.rdata`，攻击者**读一张表
就能拿到全部模块的入口地址** —— 这**正好抵消** `indirect` 的成果。

**这是协议层面的内部矛盾**：

| 目标 | 要求 |
|------|------|
| 协议要"可替换" | 需要**统一的函数指针表**（运行期发现） |
| 保护要"不可静态定位" | **排斥**明文函数指针表 |

草案没有意识到这一点，因为它只在"架构"层面思考，没检查"保护"层面。

**调和方向（供评审选择）**：

| 方案 | 做法 | 代价 |
|------|------|------|
| **A** | 描述符表经 `indirect` 通道装载（不落静态明文） | 复杂；启动期多一次解密 |
| **B** | 入口指针有效但**目标函数被 selfcrypt 加密** | 较自然；已有机制复用 |
| **C** | 描述符表分片 + 运行期重组 | 最复杂，收益不明 |
| **D** | 只**开发构建**启用描述符表，发布构建走间接化 | 两套路径 → 维护成本 + 可能漂移 |
| **E** ⭐ | 描述符**只存元数据**（名字/caps/依赖/边界），**不存函数指针**；<br>函数入口仍走既有 `indirect` 表（协议用**符号约定**而非指针绑定） | 需验证可表达性 |

**我的倾向：E**。理由：

- 描述符是**元数据**（用于组合校验、可行 checker 读取），
  **不需要**在运行期被"调用"
- 函数入口已由 `indirect` 表管理，两条通道各司其职
- 元数据可安全公开（名字、能力位、边界），**不含地址**
- 与 P4 一致：`known_limits` 等元数据本就是给人和工具看的

**但 E 需要一份"符号约定"**（如"模块必须提供 `prot_<name>_scan`"），
而**符号约定比函数指针弱**（无编译期类型检查）。需在实施时加**静态检查**
（`modcheck` 已有 `FN_DECL` 正则的雏形）。

## 3. **遗漏的议题**（草案没提，但实施时会撞上）

### 3.1 判定函数命名不统一（现状事实）

**实测**：

```
antidebug -> prot_antidebug_detected
dbiguard  -> prot_dbiguard_suspicious
vmdetect  -> prot_vmdetect_suspicious
```

**现状是 `detected` vs `suspicious` 混用**。协议若要"统一接口"，必须
定义命名规范 —— 但草案 §10.3 只给了描述符，**没给命名规则**，
而 §10.6 的 R9（符号冲突检查）也没覆盖"命名一致性"。

**建议**：在 §10 增加"命名规范"小节，并给出**迁移策略**
（改名会破坏 ABI；或接受不统一并在描述符里显式声明判定函数名）。

### 3.2 静态可发现性（上节 2.2 的延伸）

协议让模块"自我注册"，但**如何避免注册表成为攻击者的地图**？这不仅是
函数指针问题，还包括：模块名是否暴露能力（`antidebug` 一眼看出用途）、
`known_limits` 是否告诉攻击者"哪里最弱"。

**建议**：明确"元数据是否随发布构建保留"。若保留，需评估信息泄露；
若不保留，则运行期无法自省（协议价值降低）。**这是必须显式决策的点**。

### 3.3 迁移路径与破坏性

草案 §10.8 给了版本策略（ABI 不匹配则构建期报错），但**没给迁移路径**：

- 现有 13 个模块如何过渡？（§10.9 说"零重写接入"，但需验证）
- 第三方模块开发者如何知道当前 ABI？
- 若 ABI 升级，既有第三方模块如何升级？

**建议**：补一节"迁移指南"，含一个**最小示例**
（把 `src/_template.c` 从"现有形态"改造成"协议形态"的 diff）。

## 5. 修正后的实施建议

**原 §10.9 的 6a–6e 需调整**：

| 阶段 | 原内容 | 修正后 |
|------|--------|--------|
| 6a | 接入描述符，**产物字节不变** | 接入描述符；验收改为**行为等价**（e2e+attacks 全绿 + 加密函数数一致），并**记录** `.text`/`.rdata` 增量 |
| 6b | 宿主遍历注册表 | 不变（但需先解决 2.2 的入口绑定方式） |
| 6c | `report_flags` 聚合 | 不变（✅ 已确认必要） |
| 6d | T-L1/L2/L3 替换性测试 | 不变（✅ 但 T-L3 的边界应作为**待测结论**而非预设豁免） |
| 6e | ABI 校验入门禁 | 不变 |
| **6f（新增）** | **命名规范统一 + 迁移指南** | 解决 §3.1 |
| **6g（新增）** | **元数据保留策略决策 + 实施** | 解决 §3.2 / Q6 |

**建议的实施顺序**：先做 **6a 的正确版本**（行为等价验收），
因为它是所有后续步骤的前提，且能立即暴露 `.text` 布局影响。

## 6. 评审方法与局限（诚实说明）

**方法**：对每条"实测/已实现"声明重新测量；对每个设计假设构造最小实验。

**局限**：

| 局限 | 说明 |
|------|------|
| 未做**真实改造**验证 | 2.2 的冲突是**静态分析 + 设计意图对照**得出的，未实际构造"描述符表被读取"的攻击演示 |
| T-L3 边界是**预判** | "selfcrypt/integrity 桩替换可能失败"未实测（需真实实施 6d） |
| 未评估**性能** | 遍历注册表 vs 直接调用的开销未测量（预计可忽略，但未验证） |

> **原则**：上述未验证项**不写入结论**，只标注为"待实施时验证"。
> 与本项目既有纪律一致：**不确定的写"待验证"，不写"应该没问题"**。
