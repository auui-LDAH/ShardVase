# 完全开源后的反制措施补偿 —— 能否用"模块自定义组合"规避？

> **用户的直觉（2026-09-21）**：
> "开源会失去很多反制措施，没办法通过模块自定义设置规避吗？"
>
> **这个直觉指向一个真实存在的类别**：**每部署/每构建秘密**。
> 本文档用实测判断：它**能否补偿**开源失去的设计秘密。

---

## 0. 结论

| 判定 | 内容 |
|------|------|
| ✅ **直觉方向正确** | "每部署秘密"确实是开源后**唯一**的补偿来源 |
| ⚠️ **但当前实现下补偿近乎为零** | 因为**组合可被静态区分**（实测，见 §2）|
| 🔧 **可修** | 修法明确（见 §4），且**与"抬高破解成本"方针同向** |

> **一句话**：**能补偿，但现在没有** —— 需要先把"组合"变成**真正的秘密**。

---

## 1. 必须区分两类"反制措施"

开源失去的**不是全部**，只有一类：

| 类别 | 例子 | 完全开源后 |
|------|------|-----------|
| **A. 设计秘密** | VM 语义、掩码算法、检测项清单、`indirect` 置换逻辑 | ❌ **必然失去** |
| **B. 每部署/每构建秘密** | 这一次选了哪些模块、期望值、密钥流、`s_perm`、掩码字节 | ✅ **理论上可保留** |

**你的直觉指向 B** —— 问的是"这一次的配置"能否成为攻击者不知道的东西。

**关键技术前提**：
> **组合要成为秘密，它必须不可被静态识别。**
> 若攻击者看一眼产物就知道"这是 `hardened` 组合"，那组合就不是秘密。

---

## 2. ⚠️ 实测：不同组合**可被静态区分**（补偿失效）

### 2.1 实验（固定种子，只变组合）

| 组合 | 字节数 | 节数 | 节名 |
|------|--------|------|------|
| `minimal` | 215040 | **10** | 无 `.protcrc` |
| `standard` | 226304 | 11 | 有 `.protcrc` |
| `hardened` | 229376 | 11 | 有 `.protcrc` |
| `full` | 229376 | 11 | 有 `.protcrc` |

### 2.2 三个可区分特征（实测）

| # | 特征 | 区分力 |
|---|------|--------|
| **①** | **节名集合** | `minimal` 无 `.protcrc` → **一眼看出"没开完整性校验"** |
| **②** | **产物大小** | 3 种不同大小（215040 / 226304 / 229376）|
| **③** | **模块特征串** | `vmdetect` 只在 `hardened`/`full` 出现 → 可精确推断组合 |

### 2.3 这意味着什么

```
攻击者只需读 PE 头（几十字节）+ 搜几个字符串:
   -> 立即知道这是哪个组合
   -> 立即知道"哪些防护没开"
   -> 针对缺失的防护下手

例: 若判定为 standard（无 vmdetect），就不必对抗虚拟机检测
```

**结论**：**当前实现下，"模块自定义组合"不构成秘密**，无法补偿开源的损失。

---

## 3. 另外两处实测发现（开源后同样成为攻击者的"地图"）

### 3.1 完整性覆盖范围**固定且被标注**

实测 `.protcrc` 内容（VSize 现为 64 = 4 条 × 16 字节）：

```
magic "PROTCRCP" + crc   <- .text      (索引 0)
magic "PROTCRCD" + crc   <- .rdata     (索引 1)
magic "PROTCRDP" + crc   <- .pdata     (索引 2)
magic "PROTCRCX" + crc   <- .protxec   (索引 3, 2026-10-04 新增)
```

- 覆盖：**`.text` / `.rdata` / `.pdata` / `.protxec`** 共 4 段
- **未覆盖**：`.data` `.protcrc` `.protcry` `.protpad` `.fptable` `.rsrc` `.reloc`

> `.protxec` 于 2026-10-04 纳入覆盖（`docs/ATTACK_DRILL9.md` §5 的"守卫检查器自身
> 不在 CRC 覆盖内"缺口收口）。烧录表自身（`.protcrc`）**刻意**不覆盖以避免自引用；
> Linux/ELF 侧**刻意**保持 3 段（`PROT_CODE_SEG()` 在 ELF 下为空 ⇒ 检查器本就落在
> `.text`，已被索引 0 覆盖）。

> **完全开源后**，攻击者读源码即知"改哪个区域不会被校验发现"。
> 尤其 `.data` 与 `.protcry`（可写区）**未被覆盖** —— 这是可利用面。

### 3.2 antidebug 检测项**固定 12 项**

```
peb_being_debugged / peb_nt_global_flag / debug_port / debug_flags
debug_object / hardware_breakpoints / timing_suspicious / kernel_debugger
debug_heap_flags / int3_honey / ppid_blacklist / clock_drift_sec
```

> 完全开源后，攻击者**精确知道**这 12 项，可**只针对它们**做规避 ——
> 而不是盲目对抗。这**大幅降低**绕过成本。

## 4. 修法：让"组合"成为真正的秘密（与抬高成本方针同向）

> **核心思路**：把"配置差异"从**可观测**变为**不可观测**。

### 4.1 消除组合的可区分特征（最高优先）

| 特征 | 现状 | 修法 |
|------|------|------|
| **节名集合** | `minimal` 缺 `.protcrc` | **始终创建全部节**；未启用的填空节（内容随机）|
| **产物大小** | 3 种不同大小 | **统一填充到固定大小**（或按固定桶对齐）|
| **模块特征串** | `vmdetect` 字样只在该组合出现 | 字符串**加密/统一**（已有 strcrypt，需覆盖 CLI 参数名）|
| **代码量差异** | 不同组合 `.text` 大小不同 | 无法完全消除，但可**填充**到桶边界 |

**可验收指标**：
```
目标: 4 个组合的 {节名集合, 产物大小, 可测字符串} **完全一致**
      攻击者无法从产物判断"开了哪些模块"
```

### 4.2 让"哪些模块生效"运行期才定

更彻底的做法（与"简化 VM"同向）：

| 手段 | 说明 |
|------|------|
| **运行期选择** | 把组合编译成"统一框架 + 运行期查表"，而非编译期裁剪 |
| **多态桩** | 未启用的模块保留**空实现**（与原实现同尺寸），使二进制形态一致 |
| **调用点统一** | 所有模块经同一间接通道调用（已有 `indirect`，需扩展）|

> **代价**：产物变大（含空实现）；与"简化"有张力 —— 但**安全优先**。

### 4.3 让检测项**不可枚举**（应对 §3.2）

| 手段 | 说明 |
|------|------|
| **检测项随机子集** | 每构建**随机选** N 项（而非固定 12 项）→ 攻击者不知这次查什么 |
| **等价变体** | 同一检测的多种实现（读 PEB / 系统调用 / 时序），每构建随机选 |
| **伪装** | 未启用的检测项也**保留代码**（返回固定值）→ 形态一致 |

### 4.4 扩大完整性覆盖（应对 §3.1）

| 手段 | 说明 |
|------|------|
| **覆盖全部节** | 含 `.data` `.protcry` `.fptable` 等当前未覆盖区 |
| **覆盖范围随机** | 每构建随机决定覆盖哪些区域（攻击者不知边界）|
| **CRC 链式** | 段间 CRC 互相依赖（改一处须重算整链）|
| **去除 magic 标注** | `PROTCRC`+`P/D` 这种**自解释标记**应改为随机值 |

> 实测发现：`.protcrc` 里的 `PROTCRC` magic 是**自解释的**
> —— 等于给攻击者标注了"这里是完整性校验"。应改为每构建随机的 magic。

## 5. 补偿后的成本模型

```
攻击者成本 = 理解 + 定位 + 提取 + 改造成本 + 验证
               ↑      ↑      ↑       ↑         ↑
完全开源:      ≈0    ??     ??      ??        ??

当前实测:  定位 ≈ 0（组合可辨、节名自解释、覆盖范围已知）
           -> 补偿失效

修完 §4 后:
  攻击者必须**动态分析**才能知道:
    · 这次开了哪些模块（§4.1/4.2）
    · 这次查哪些检测项（§4.3）
    · 这次覆盖哪些区域（§4.4）
  => 每构建都要**重新动态摸底** -> 定位成本大幅上升
```

### 关键洞察：**"配置不可观测"是开源方针的第二根支柱**

| 支柱 | 内容 | 依赖 |
|------|------|------|
| **第一根** | 每构建**数据**变化（期望值/密钥/掩码）| 随机化 |
| **第二根** | 每构建**配置**不可观测（组合/检测项/覆盖范围）| **填充 + 随机化 + 去标注** |

> 用户问的"模块自定义能否补偿"—— **正是第二根支柱**。
> 它有**理论依据**（每部署秘密），但**当前实现没做到**。

## 6. 与你既有方针的一致性

| 你的方针 | 本文档的建议 | 是否一致 |
|----------|-------------|----------|
| 完全开源 | 接受设计秘密丢失 | ✅ |
| 简化 VM | §4.2 把编译期裁剪改为运行期选择 —— **某种意义上是"统一化"而非简化**，需权衡 | ⚠️ 有张力 |
| 抬高破解成本 | §4 全部措施都提高定位成本 | ✅ |

**需要你权衡的一点**：
> §4.2（运行期选择 + 空实现）会让产物**变大**、代码**不再"精简"**，
> 与你"简化 VM"的诉求有张力。
> **但 §4.1/4.3/4.4（填充、随机子集、去标注）不影响简化** ——
> 建议先做这三项，§4.2 视情况再定。

## 7. 诚实边界

1. **§4 效果未实测** —— 全部是设计方向，"指标"是目标不是结果
2. **"配置不可观测"有理论上限** —— 代码量差异无法完全填充消除
   （攻击者仍可从 `.text` 熵/指令分布推测"有没有某模块"）
3. **填充会增大产物** —— 具体增幅未测
4. **不主张"不可破解"** —— 仍是成本博弈
5. **对抗性会升级** —— 这是"抬高成本"而非"一劳永逸"
