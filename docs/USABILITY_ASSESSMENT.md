## 0. 一句话结论

> **可用性：高**（接入 <17 秒机器时间，契约与工具齐备）
> **适用性：中偏窄**（Windows x64 商业软件；不适合需要内核级防护或跨平台的场景）
> **上限：由两个硬约束决定** —— ①授权侧 RSA-3072 是信息论断点
> ②代码保护侧在**用户态**存在不可逾越的天花板（B5）。
> **本项目不承诺"不可破解"，只承诺"成本可测量、边界公开"。**

### 1.2 运行开销 —— ✅ **R2 已实测**（2026-09-29）

**实测数据**（`tools/perf_baseline.py`，每项 7 次取中位数；本机）：

| 组合 | 模块数 | 产物大小 | 冷启动 | **自检** | 峰值工作集 |
|------|-------|---------|--------|---------|-----------|
| `minimal`（license/hostid/strcrypt）| 3 | 329,080 B | 10.53 ms | **13.63 ms** | 2.60 MB |
| `standard` | 9 | 329,080 B | 11.27 ms | **648.56 ms** | 2.60 MB |
| `full` | 13 | 329,080 B | 20.75 ms | **686.95 ms** | 2.60 MB |

**增量（相对 minimal 基线）**：
```
standard: 自检 **+634.93 ms (+4658%)** · 内存 +0.00 MB
full:     自检 **+673.32 ms (+4940%)** · 内存 +0.00 MB
```

> ### ⚠️ 读数解读（**必须与组合构成一起看**）
> `minimal` **不含 VM / selfcrypt / integrity**（只 3 个模块）——
> 所以 **+673 ms 的增量来自 VM 解密装载 + 自加密 + 完整性校验**（10 个模块的代价），
> **不能**解读为"保护开销低"。
>
> **产物大小三者相同（329,080 B）是预期** —— 我方 Pillar-2 的
> **尺寸归一化**（`gen_padding`）刻意使大小不泄漏模块构成
> （哈希不同: `4D9E0EE9…` / `3E930A9B…` / `30AE4EEE…`）。
>
> **内存几乎不随模块增长**（2.60 -> 2.61 MB）是**真实结论**:
> 工作集由 CRT/系统 DLL 映射主导，我方模块为同一 EXE 内代码。

**测量方法**（可复核）: `PeakWorkingSet64`，5 ms 轮询 + `--wait-ms 800`；
时间取中位数（本机曾实测 **±40% 抖动**，故不用均值）。

| 项 | 实测值 | 来源 |
|----|--------|------|
| `antidebug` 计时检测 | **固定 250ms**（5×20ms + 150ms）| `modules.json` known_limits |
| `vm` 回跳开销 | O(ip) 重绕密钥流；大量回跳呈**近平方级** | 同上 |
| 启动总开销 | **已测**（minimal 10.53 / standard 11.27 / full 20.75 ms）| 上表，`tools/perf_baseline.py` |
| 常驻内存增量 | **已测**（峰值工作集 2.60 MB，**几乎不随模块数变化**）| 上表，同上 |

> **诚实说明**：`antidebug` 的 250ms 是**可量化代价**，对启动敏感的程序
> 应选 `minimal` 拼装图（不含 antidebug）。

### 1.6 ✅ R2.3 从零接入核查（2026-09-29）—— **抓到 4 个缺陷**

**方法**: 用 wizard 的**无头 API**（`generate_project`/`build_project`）
复现 `TUTORIAL.md` 的流程（GUI 无法在非交互环境跑 —— 见发现 ①）。

**实测数据**（与文档宣称对照）:
| 步骤 | 文档宣称 | **实测** | 偏差 |
|------|---------|---------|------|
| 生成工程 | 0.03 秒 | **0.009 秒** | ✅ 更快 |
| 构建（standard）| 16 秒 | **15.9 秒** | ✅ 吻合 |
| smoke | PASS | ✅ **PASS (license gate passed)**（修复 4 处缺陷后）| ✅ 吻合 |

#### 发现的 4 个缺陷

| # | 缺陷 | 证据 | 状态 |
|---|------|------|------|
| **①** | `prot_wizard.py` **是 tkinter GUI**，`--help` **挂住 120 秒** | 实测超时；源码 `tk.Tk()` + `mainloop()`，**无 argparse** | **诚实边界**（文档已说"GUI 向导"；但 TUTORIAL 给的命令无 CLI 替代 —— 建议补 `--headless`）|
| **②** | **`$busSrcs` 路径未加引号** -> 空格拆词 | `cl: warning D9024: 无法识别的源文件类型"D:\specifically"` | ✅ **已修** |
| **③** | **`$signStep` 路径未加引号** | `vmenc.py: error: unrecognized arguments: for development and work\…` | ✅ **已修** |
| **④** | **smoke 只重定向 stdout、未重定向 stderr** | `smoke_out.log` = **0 字节**；分离两流实测: 诊断信息全在 **stderr**（146 B）| ✅ **已修**（提交 `1397001`，2026-09-30）|

#### ②③ 的根因是**同一个**（已在本仓库记名过）
```
build.ps1 的注释早已写明:
  "本仓库路径含空格（…\Reverse Engineering\…）——
   `-join ' '` 生成的裸串在 cmd /c 里会被拆词"
=> **脚手架（prot_sdk/skeleton）未同步该修复**，两处漏加引号。
```
> **教训**: 主构建链修过的坑，**脚手架/示例/工具链要一并检查**
> （"修一处要问：还有谁复制了这段逻辑"）。

#### ④ 是本轮**最危险的发现**
```
smoke 的判据是 `$sText -match 'license: 1'`，而 $sText 来自
`-RedirectStandardOutput` —— **只重定向 stdout**。
实测: 程序把 usage/错误全部写入 **stderr** ->
  smoke_out.log = 0 字节 -> 判据必然失配 -> **FAIL 且原因不可见**。
=> 与 P3 教训同型（"门禁绕过会掩盖真实缺陷"）：
   **诊断信息丢失**会把"可修的错误"变成"无从下手的失败"。
```
**修复**（已完成，见上表 ④）: `build_skeleton.ps1` 增加 `$sErr = smoke_err.log`
并在失败时打印 `$sOutLines` / `$sErrLines` 两流（提交 `1397001`）。

#### ⑤ 附带发现: usage 提示显示**字面宏名** —— ✅ **已修**（Q2，2026-10-02）
```
（原记录症状）usage: APP_EXE_NAME [--selftest] ...
                        ^^^^^^^^^^^^ 应为真实程序名
```
**根因（非"显示名注入未覆盖 usage"）**: `app_main.c` 的字符串化只有**一级**
间接 —— `#define APP_EXE_NAME_STR PROT_APP_STR_(APP_EXE_NAME)`。C 标准规定
`#` 的操作数**不做宏展开**，故 `#x` 把参数**符号本身**字符串化，得到字面量
`"APP_EXE_NAME"`。修法是经典**两级间接**（`PROT_APP_STR(x) -> PROT_APP_STR_(x)`）。

**端到端定证**: `cl` 实测（`-D` 带引号/带空格均正确展开）→
`tools/skeleton_check.py --keep` 重建后扫 `build/SkelCheck.exe`，
8 条 usage 串全为 `usage: SkelCheck ...`，`literal macro name present? False`。

> 另注: `demo/main.c` 不受影响 —— 它的 usage 全是**硬编码字面量** `demo.exe`，不走宏。

## 2. 适用性评估（适合什么、不适合什么）

### 2.1 能力分布（决定"能做什么"）

来源：`modules.json`（13 模块）

| 能力位 | 模块数 | 含义 |
|--------|--------|------|
| `verify` | **6** | 校验类（授权/完整性）最多 |
| `conceal` | 5 | 隐藏类（VM/加密） |
| `detect` | 3 | 检测类（反调试/DBI/VM） |
| `prevent` | 1 | 阻止类 |
| `respond` | 1 | 响应类 |

**解读**：**强在"验证"与"隐藏"，弱在"主动阻止"**。
这是设计选择（误杀成本高），不是缺陷。

### 2.2 明确的适用场景

| 场景 | 适配度 | 理由 |
|------|--------|------|
| Windows x64 商业软件防拷贝 | ★★★ | 核心设计目标 |
| 离线授权 + 机器绑定 | ★★★ | RSA-3072 + 全字段签名 |
| 需分级授权（试用/正式/增值）| ★★★ | `tier` 参与签名 |
| 需审计授权台账 | ★★☆ | 哈希链台账（工具层） |
| 行业内小工具防"顺手破解" | ★★★ | 成本非对称性最优场景 |
| 需要组合取舍（按威胁模型）| ★★★ | 编译期可组合（实测见 BLUEPRINT §3.4）|

### 2.3 **明确不适用**的场景（诚实清单）

| 场景 | 为何不适合 |
|------|-----------|
| **需要防内核级攻击** | 本项目是**用户态**保护（边界 **B5**）。驱动级 dump/hook 不在覆盖范围 |
| **需要跨平台**（Linux/macOS/Android）| 当前仅 Windows x64。`EXTENSION_PLAN.md` 记录 Android 为未来方向 |
| **需要防"到期回拨"** | 依赖本地时钟（边界 **B2**）。商业场景需**在线时间锚点** |
| **安装目录可写且无法加固** | 可换公钥自授权（边界 **B1**）。**必须**用 ACL 只读 |
| **要求实时吊销** | 离线黑名单有延迟（边界 **B6**）|
| **要求零误报** | 反调试/DBI 类检测**存在误报可能**（咨询项已与关键项分离以降低影响）|
| **要求"永不破解"承诺** | 本项目**明确不承诺**（任何此类承诺都不可信）|
| **Web/云原生应用** | 设计面向原生二进制 |

### 2.4 部署前置条件（**必须满足，否则防护失效**）

| # | 条件 | 不满足的后果 |
|---|------|-------------|
| 1 | **安装目录 ACL 只读** | 攻击者可换公钥重签（B1 实证破防）|
| 2 | **分发 `vm.blob`** 且由签发方签名 | 程序无法启动（0xB10B）|
| 3 | 私钥**离线保管** | 签发体系失效 |
| 4 | 商业场景配**在线时间锚点** | 过期可回拨（B2）|
| 5 | 客户机为 **Windows x64** | 不支持的平台 |

## 3. 上限评估（能做到什么程度）

### 3.1 两个硬约束（上限的来源）

```
┌─────────────────────────────────────────────────────────────┐
│ 约束一: 授权侧 —— RSA-3072 是**信息论断点**                    │
│   攻击者还原全部 VM 也造不出合法签名（无私钥）                   │
│   -> 这一层**没有上限问题**，是密码学保证                       │
├─────────────────────────────────────────────────────────────┤
│ 约束二: 代码保护侧 —— **用户态天花板**（边界 B5）               │
│   内核级攻击者可以 dump/hook 一切                              │
│   -> 这一层**有不可逾越的上限**，任何用户态方案都如此            │
└─────────────────────────────────────────────────────────────┘
```

**关键区分**：
- **授权不可伪造** —— 信息论保证，与攻击者能力无关
- **代码不可读懂** —— 只是**成本问题**，攻击者资源足够则可还原

### 3.2 攻击成本矩阵（引自 `THREATMODEL.md` §3，实测归档）

| 攻击者 | 手法 | 净成本 | 结果 |
|--------|------|--------|------|
| 脚本级 | 字符串搜索→定位补丁 | 中 | **被完整性杀掉** |
| 脚本级 | 直接改内存 `result` | 中 | **被看门狗 CRC 杀** |
| 脚本级 | 改 `machine_id` 冒充 | 中 | **跨机仍被 L4b 拦** |
| 中级 | IDA 还原 3 个 VM → keygen | **天级** | 成功但**不通用** |
| 中级 | DBI 符号化全还原 | **天级** | 还原后**每个构建重玩** |
| 高级 | 通用 VM 还原器 | **周+** | 需按构建适配，**跨构建通用性大降** |
| 泄漏型 | 一次还原批量使用 | 即时 | **各构建指纹互异，不能批量 patch** |

**上限的含义**：
> 攻击者**能**还原（成本天级~周级），但**还原产物不能跨构建复用**。
> 即：**上限不是"不可还原"，而是"还原成本 × 每次构建"**。

### 3.3 已公开的 5 项显式破防（不隐瞒）

| # | 手法 | 前置条件 | 缓解 |
|---|------|----------|------|
| D5 | 同目录伪造 `winhttp.dll` | 安装目录**可写** | ✅ **R2.1 实测阻断**（`deploy_harden.ps1`）|
| L3 | 替换嵌入公钥自签 | 安装文件**可写** | ✅ **R2.1 实测阻断**（同上）|
| L4 | 回拨时钟复活过期授权 | 可改本机时间 | 在线时间锚点（B2）|
| S5 | 台账可改写/删除 | 可访问台账 | 哈希链（已落地）|
| V3 | 台账 CSV 注入 | 同上 | 字段卫生（已落地）|

> **5 项破防没有"未知项"** —— 全部落在已公开边界或已缓解的工具层问题内。

### 3.4 上限的**量化表述**

| 维度 | 上限 |
|------|------|
| 授权伪造 | **不可行**（RSA-3072，信息论）|
| 跨机构建复用还原结果 | **不可行**（引擎语义 + 随机期望值随构建变）|
| 单构建逻辑还原 | **可行，天级~周级**（取决于攻击者资源）|
| 内核级绕过 | **可行**（用户态天花板，B5）|
| 到期绕过（离线）| **可行**（时钟回拨，B2）|
| 安装目录可写场景 | **可自授权**（B1）|

## 4. 综合判断

### 4.1 能力定位

> **本项目是"把攻击成本从分钟级推到天/周级，并让授权伪造在密码学上不可行"
> 的用户态保护方案。它不是、也不可能是"防住有充足资源的内核级攻击者"的方案。**

### 4.2 投入产出比最优的场景

| 场景 | 为何最优 |
|------|----------|
| 独立开发者/小团队的 Windows 商业工具 | 攻击者通常是"顺手破解"而非定向攻坚 |
| 需要离线授权且能控制部署环境 | 可用 ACL 消除 B1，用时间锚点消除 B2 |
| 愿意接受"成本非对称"而非"绝对安全" | 这正是本方案的设计哲学 |

### 4.3 明确的欠佳场景

| 场景 | 问题 |
|------|------|
| 高价值目标 + 有组织的攻击者 | 天/周级成本对其不构成阻碍 |
| 无法控制部署环境（如共享主机）| B1 无法消除 |
| 需要跨平台 | 不支持 |
| 要求零误报 | 反调试类检测无法保证 |
