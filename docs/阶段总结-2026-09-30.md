## 3. 技术沉淀（**本阶段新增**）

### 3.1 R2.3 的四连缺陷 —— **"已记名的坑未同步"**

```
缺陷 ② `$busSrcs` 路径未加引号 -> cl D9024 在空格处拆词
缺陷 ③ `$signStep` 路径未加引号 -> vmenc.py "unrecognized arguments: for development and work\…"
缺陷 ④ smoke **只重定向 stdout** -> smoke_out.log = **0 字节**，诊断全在 stderr
缺陷 ⑤ `-ArgumentList` 路径未加引号 -> 参数错乱 -> usage
```
**根因是同一个**：仓库根路径含空格，而 `build.ps1` 的注释**早已记名**该坑 ——
**脚手架（`prot_sdk/skeleton`）未同步修复**。

> **原则**：**修一处要问「还有谁复制了这段逻辑」**（主链 -> 脚手架 -> 示例 -> 工具链）。

### 3.2 ⭐ **"诊断信息丢失" 是最危险的失败形态**（R2.3 的决定性教训）

```
修好缺陷 ④（同时读 stderr）之后，smoke **立刻**打印:
   smoke stderr: usage: APP_EXE_NAME …
   -> 暴露"参数解析失败" -> 直接定位到缺陷 ⑤
```
```
=> **诊断信息不可丢失** —— 它把"无从下手的失败"变成"一眼可见的根因"。
   与项目既有 P3 教训（"门禁绕过会掩盖真实缺陷"）**同型**。
```

### 3.3 ⭐⭐ **判据必须打在「被测对象的检测域内」**（R3.2 的教训，**我犯了两次**）

```
第一次（R1 之前已记名）: 变异必须打在检查器检测域内 —— 否则变异"通过"是假象

第二次（本阶段，**我违反了自己记名的纪律**）:
  R3.2-b 用 "退出码 == PROT_EXIT_TAMPERED(2989)" 判"守卫抓到 patch"
  实际: demo 的段 CRC（check_self）**先于**守卫执行（L175 < L211）
    · patch **非掩码区**目标 -> CRC 先终止进程（2989）
      => 2989 是 **CRC 的功劳**，守卫**根本没机会跑**
    · patch **掩码区**目标 -> 走反调试（219），而那个 219 由
      **测试工具自身**的 OpenProcess 触发
  => 退出码**没有判别力**。
  改用守卫自己的计数 `g_guard_hits` -> **5/5 全部为 0** => 上轮结论被推翻。
```

### 3.4 **"测量 ≠ 缺陷" 的第 4、5 次实例**

| 实例 | 表象 | 真相 |
|------|------|------|
| R3.3 `L2` 尾随垃圾 | 加尾随后全 rc=1 -> "尾随被拒" | **对照组（无尾随）也 rc=1**（序列号与构建不匹配）-> 判定无效 |
| R2.3 `--help` 挂住 120s | "CLI 有缺陷，不处理 --help" | 它是 **tkinter GUI**（无 argparse）-> **我的假设错了** |

> **对策（已固化）**：任何「拒绝/阻断/失败」类判定，**必须先有通过的对照组**。

### 3.5 PowerShell / 工具链陷阱（**本阶段新增 2 条**）

## 4. R3.2 的**反向结论**（本阶段最重要的一项）

### 4.1 发现（R3.2-a，**静态分析，成立**）

`src/integrity.c` 的段 CRC **先清零 selfcrypt 掩码区**（`build_selfcrypt_mask`）
-> **掩码区内的判定点改它不影响 CRC**。实测归属：

| 判定点 | .text 偏移 | 在掩码区 | patch 被 CRC 抓到 |
|--------|-----------|---------|------------------|
| **`prot_integrity_check_self`** | +7488 | ✅ | ❌ **不** |
| **`prot_license_verify`** | +11776 | ✅ | ❌ **不** |
| `prot_antidebug_detected` | +22192 | ❌ | ✅ 会 |
| `prot_dbiguard_suspicious` | +8880 | ❌ | ✅ 会 |
| `prot_vmdetect_suspicious` | +624 | ❌ | ✅ 会 |

**两个高危缺口**：
```
① patch `prot_integrity_check_self` -> 完整性防护被**静默关闭**
   根因: 校验器**自己**落在掩码区 = **不在自己 CRC 的覆盖范围内**（自我指涉缺口）
② patch `prot_license_verify` -> 授权恒通过且不被 CRC 抓到
```

### 4.2 实施（第 1/2/4 组）与**否定性验证**

```
第1组: `prot_integrity_check_guards`（序言快照比对）+ 看门狗集成
第2组: 注册式扩展（覆盖 license/dbiguard/vmdetect）
第4组: `guard_selftest` 入库门禁（29 项）
```
**决定性验证**（判据 = `g_guard_hits`）：
```
对照（不 patch）: hits = 0   ✅ 无恒报
5 个判定点逐一 patch: hits **全部 = 0**   ❌ **守卫未命中任何目标**
```

### 4.3 结论与处置

```
· **R3.2-b 未产生可用加固** —— 代码在，但**有效性未证明且证据指向"无效"**
· `guard_selftest` 判据已改为 `g_guard_hits > 0`
  -> 门禁第 29 项**现在会 FAIL** —— 这是**诚实的失败**，保留以防假阳性再混过
· 已提交内容的影响**如实标注**（`DECISION_REDUNDANCY_PLAN.md` §10.5）:
    c7df177「实测抓住函数头 patch」-> **不成立**（是 .text CRC 的功劳）
    b7f9f96「正向+负向可自证」-> **负向是假阳性**
· **其中一项仍有效**: R3.2-a 的掩码区归属（静态分析，可复现）
```
