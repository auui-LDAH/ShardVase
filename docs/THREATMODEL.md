# 反逆向保护套件 — 威胁模型与效果评估 (THREAT)

> 分阶段评估本套件在四条攻击路径（离线静态破解 / 动态调试 / 篡改补丁 / 批量复制）
> 下的真实防御强度。核心结论一句话：**本套件的强度来自"复合门槛 + 每次构建随机化"，
> 目标是把单镜像破解成本抬高到小时～天级，而非理论上的不可破解。**
> 本文档与 CONTRACT.md 配套：CONTRACT 说"怎么做"，本文说"软肋在哪、能扛多大成本"。

## 1. 威胁模型

| 攻击者 | 目标 | 环境 | 资源 |
|--------|------|------|------|
| A1 脚本小子 | 改退出码 / 改机器标识 / 拿通用 key | 本机，Cheat Engine + x64dbg | 小时级 |
| A2 中级逆向者 | 还原校验算法，批量 keygen / 补丁 | 本机/虚拟机，x64dbg + IDA/Ghidra + DBI | 天级 |
| A3 专业破解/保护工作室 | 出通用脱壳 + VM 还原器 | 多机 + 自动化 dump 工程 + 自研引擎 | 周～月级，成本高 |
| A4 发行版泄漏 | 一次还原打遍所有构建版本 | 对应某一次分发 | 取决于随机化强度 |

**成功判据（攻击者"得手"的最低标准）**：
- 静态：能唯一定出合法序列号（keygen），或改几字节让任意序列号通过（patch）。
- 动态：运行时拿到明文指令 / 让校验必然通过而不被察觉。
- 完整性与环境检测只是"拖延"，不是终点；真正断它的是"能否生成合法密钥"。

## 2. 防护分层与理论强度评级

评级用破解"最小有效工时"（分钟/小时/天/周），非马屁。五档：低=分钟、中=小时、高=天、极高=周+、断源=理论不可绕过。

| 防护层 | 对应实现 | 防的目标 | 理论强度 | 弱点 / 可绕过 |
|--------|----------|-----------|---------|---------------|
| L1a 构建期 opcode 随机化 | `vmenc.py` make_opcode_keymaps + `vm.c` vm_build_keymaps 置换 `key[1]` | 指纹/两次构建同构 | **高**（对批量、重放） | 不提高单镜像还原难度；每个构建需单独逆向 |
| L1b 调度间接化（dispatch 表 + ctx 散列） | `g_routes[]` 函数指针路由 + 运行期槽位 | 反汇编器 / 搜索 switch 结构 | 中 | 引擎透明；还原"规范 opcode 序"是标准任务 |
| L1c 等价多路径（volatile 防折叠） | `vm_kr_*` 多等价实现 | 反汇编成"标准操作序列" | 中 | DBI/解释执行可自动对齐，各路径语义相同 |
| L1d 指令集扩充（0x00..0x2E，A4 扩 4 条） | 47 op 函数路由表 + brk 断言陷阱 | 扩大接口面 + 校验内门控 | 低～中 | 只面增长，实际难度来自引擎规模而非指令数 |
| **L1e 引擎语义随构建变异（A2）** | `sem` 开关：操作数字节序 LE/BE-SWAP + 折叠公式 4 选 1，生成/执行两侧同流派生 | **通用还原器一次通吃所有构建** | **极高**（对 A3 通用还原器） | 单镜像还原难度不变；还原器需按构建调整取数语义 |
| L2a 拆 3 个独立小 VM | `license_{hash,mix,verify}.vasm` | **单镜像 dump 只有 1/3 逻辑** | 中高 | 需反向拆出完整流程；但不需 VM 引擎级还原 |
| L2b 窗口加密 + 用后即焚 | `vm.c` win[64] + vm_wprune + CRC 流式 | memdump 抓全明文 | **极高** | 对"实时解析 + 内存改写"无效；可动态定向还原 |
| L2c 运行时语义随机化（ctx 播种） | `vm_ctx_seed()`（TSC/QPC/栈地址） | 重放同一镜像 | 中高 | 结果是可验的；是"行为随机"非"逻辑随机" |
| **L2d 镜像外部装载（DBI launcher，债 #3 结清）** | `src/blob.c` + `vmenc.py pack`：VM 密文打包为独立 `vm.blob`，启动时装载进内存；exe 内无 VM 逻辑 | **静态只拿 exe 无从分析**（断源） | **极高**（对 A4 发行泄漏） | 拿到 exe+blob 组合后仍回落到原有难度 |
| L3a PEB/NtQuery/硬件断点 分组检测 | `antidebug.c` | 静态调试器 | 中 | ScyllaHide 一键绕过；看门狗只每 5s |
| L3b 多轮 QPC + int3 蜜罐 + 调试堆 | `PROT_AD_TIMING_*`、VEH、heap ForceFlags | 反分析 | 中 | int3 蜜罐在真调试内"冻结"不触发策略——列为咨询项 |
| L3c ThreadHideFromDebugger | `NtSetInformationThread(17)` | 本线程断点 | 低 | 只隐身本线程；内核/驱动调试不防 |
| L4a .text/.rdata/.pdata CRC + 看门狗（A3） | `integrity.c` 3 段 CRC（`.protcrc` 烧录，IAT/重定位掩码两侧一致）+ 周期复查 | 字节级补丁 | **高**（A3 起覆盖 .rdata/.pdata） | 对"仅内存改写"无效；无拉黑逻辑 |
| L4b machine_id 多因子 FNV 绑定 | `hostid.c` / `vmenc.hostid` | 换机 / 拷贝 | 高（对换机使用） | FNV 是哈希非签名，改内存值即可"冒充"单机 |

> 单层被绕过不代表保护失效：A1 想做"全覆盖"至少要撞 L2a/dump + L4b + L1a + L3 数道。
> 但严肃说，**密码学短板**：`key[0]/key[1]` 明埋在 `demo\gen\*_blob.c`，机器标识是
> 可写值，"期望值"是**可计算函数**而非带私钥的签名——所以理论上"伪造合法 key"仍可推导。
> 这正是 Phase 4 的 RSA 离线签发的落点（见 §4）。

## 3. 攻击路径成本矩阵（中位有效工时，单位：小时）

| 攻击者 | 目标方式 | 起始门槛 | 该方案的主要障碍 | 净成本 | 拦截判定 |
|--------|----------|----------|------------------|--------|----------|
| A1 脚本 | 字符串搜索→定位补丁（exit1→0） | 极低 | L1：字符串全部加密，无明文 | 中 | L4a 完整性杀掉 |
| A1 脚本 | 直接改内存 `result` 值 | 低 | L2b 让 result 在 VM 里反复重写；改后即被看门狗 CRC 杀 | 中 | L4a |
| A1 脚本 | 改 `machine_id` 内存值冒充授权机 | 低 | 只能改本机值；跨机仍受 L4b 换机限制 | 中 | L4b（防换机） |
| A2 中级 | IDA 还原 3 个 VM → keygen | 高 | 引擎语义可见，但结构跨构建随机 | 天级 | 成功但不通用 |
| A2 中级 | DBI 动态符号化全还原 | 高 | 需绕过 antidebug（可绕过），再逐 VM dump | 天级 | 还原后"每个构建重玩" |
| A3 高级 | 通用 VM 还原器 | 极高 | 引擎语义随构建变异（操作数序/折叠，A2） | 周+ | 还原器需按构建适配取数语义，跨构建通用性大降 |
| A4 泄漏 | 一次还原批量使用 | -- | 各构建指纹互异，不能批量 patch | 即时 | 独立版本各自逆向 |

## 4. 上限分析：为什么要 RSA

**短板根源**：校验期望值由 `FNV-1a serial -> mix(machine_id) -> expect` 是**可推导函数**，
公参（序列号、机器标识）都在本地。攻击者在完整还原所有 VM 后，**仍能自己制造合法的
(serial, expect) 对**——不需要任何密钥。

因此理论层是：
- 静态 / 动态逆向 → 可以拿全（成本高，但**通**）。
- **生成合法授权 Key → 没有私钥就办不到** ← 这是唯一"信息论上断掉"的层。

Phase 4 的 RSA 离线签发 = 把"期望值"换成"公钥验签"：VM 校验的是序列号/机器标识对应的
RSA 签名，公钥在程序里，私钥离线。攻击者还原全部 VM 也**造不出合法签名**——这才是
"离线不可破"的锚点，现阶段的 FNV/xorshift 是过渡态实现。

> **2026-08-10 已落地（A1, 见 docs/PRODUCTION.md）**：`vmenc.py keygen/sign` 离线签发
> RSA-2048，`src/license.c` BCrypt 验签，公钥 blob 嵌入二进制，私钥 gitignore；
> 宿主只算 `license_ok`，VM#4（`demo/license_gate.vasm`）逐位 AND 门控。
> 防伪造链路（A5 license-forge / A6 license-other-machine）已在 tests/attacks.py 全绿。
> **2026-08-14 追加落地（A2/A3/A4/A5）**：引擎语义随构建变异（L1e，§6 债 #2
> 结清）、完整性覆盖 .text/.rdata/.pdata（L4a 升级）、指令集扩到 0x2E（A4）、
> 看门狗周期反调试复查（A5）。
> 剩余真实短板见 §5-3（内存改 machine_id）+ §6。

## 5. 实战判断（诚实面）

1. **跨构建问题**：~~L1a 只让构建互异，不阻断"构建间通用还原"——A3 的还原器覆盖
   vm.c 取指/窗口/路由语义即可通吃。引擎语义不随构建变异是上限短板之一。~~
   **已结清（A2，2026-08-14）**：操作数字节序（LE/BE-SWAP）+ 折叠公式随构建
   变异，通用还原器需先识别并适配每个构建的取数语义。
2. **驻留/运行期改写**：~~完整性只在 `.text`，磁盘补丁会被 CRC 杀，但"内存改写 + 不动文件"
   不会被杀~~。**A3 起 `.text/.rdata/.pdata` 三节都查**（2026-08-14），磁盘补丁
   覆盖到数据区；"仅内存改写"仍不防（主流 AC/保护场景的通用攻击手法，看门狗
   复查可缓解驻留期篡改）。
3. **机器标识可换**：L4b 值在内存可改，真正 bind-to-machine 需 RSA/签名或在线激活；
   本地只能做到"换机即失败"。
4. **反调试置信度**：干净环境 T7/selftest 已验证 0 误报；A5 看门狗周期复查
   提升驻留期检测密度；真机 T3 仍待做（累计成本分钟级），这是"置信度"问题
   而非架构问题。

## 8. 结论

理论缺口大小：**中～较高**。"破解一次成本 > 正版价格/收益"的效益侧已经做到
（静态逆向小时—天级，动态立即被完整性杀）。但仍在"防分析"梯队；
**把"防分析"升级为"防伪造"（RSA 签名）+ "引擎变异"** 后，才会进入"拿到全镜像也
无法生成合法 Key"的不可绕层级——那才配得上"商业保护"四个字。
