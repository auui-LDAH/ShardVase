# UWP / MSIX 可行性评估

> **性质**：可行性评估（**只评估，不实施**）。
> **结论摘要**：**部分能力可用，核心保护能力与 UWP 沙箱模型冲突** ——
> 不是投入能解决的问题，除非重新设计保护方案。
> **日期**：2026-09-21

---

## 0. 结论先行

| 能力 | UWP 下可行性 | 说明 |
|------|-------------|------|
| **授权验签**（RSA-3072）| ✅ **可用** | 纯计算 + 文件读取，沙箱内可行 |
| **机器绑定**（hostid）| ✅ **可用** | 读取硬件标识通常允许 |
| **字符串加密**（strcrypt）| ✅ **可用** | 进程内解密，无特殊权限需求 |
| **VM 执行**（vm 解释器）| 🟡 **可能可用** | 纯计算；但依赖内存页属性，需实测 |
| **自加密**（selfcrypt）| ❌ **冲突** | 需改写 `.text` + `VirtualAlloc` RWX（见 §2）|
| **完整性校验**（integrity）| ❌ **冲突** | 需读取自身镜像布局，且与 selfcrypt 耦合 |
| **反调试**（antidebug）| 🟡 **大部分失效** | 需跨进程/令牌查询，沙箱限制（见 §2）|
| **DBI 检测**（dbiguard）| 🟡 **部分失效** | 依赖内存区域遍历 |
| **间接化**（indirect）| ✅ **可用** | 纯调用约定，无权限需求 |
| **外部装载**（blob）| 🟡 **需调整** | 沙箱文件系统受限，路径需改 |

**一句话**：**"授权与加密"类可用，"反调试与自保护"类大部失效。**

## 1. 实测部分（本机可验证的）

### 1.1 基线（Medium 完整性级别）

用探针程序实测（链接真实保护库）：

```
integrity_level=8192 (0x2000=Medium)
virtualalloc_rwx=OK          <- RWX 页可分配
virtualprotect=OK            <- 页属性可改
openprocess_self=OK
openprocess_pid4=DENIED      <- 注意: 对系统进程已默认拒绝
prot_antidebug_scan=OK  detected=0
```

**这些是当前（普通桌面应用）下的实测值**，作为对照基线。

## 2. 逐项判定（依据公开约束 + §1 基线）

### 2.1 ❌ selfcrypt：与沙箱模型**直接冲突**

**机制回顾**：selfcrypt 在启动时**就地解密 `.text` 中的函数体**。
这要求：
1. 代码段页可写（`VirtualProtect` 改为 `PAGE_EXECUTE_READWRITE`）
2. 解密后恢复为可执行

**UWP 的阻碍**：
| 约束 | 影响 |
|------|------|
| W^X（Write XOR Execute）策略 | UWP/AppContainer heavily 限制同时可写可执行的页 |
| 代码完整性（Code Integrity）| 受保护进程不允许修改已签名代码段 |
| 动态代码生成限制 | 部分沙箱禁止 `VirtualAlloc` 产生可执行内存 |

> **这是本项目"自加密"能力的**根本性**冲突** —— 不是工作量问题。

**可能的缓解方向**（需重新设计，非本评估范围）：
- 把 selfcrypt 目标从 `.text` 移到**可写数据段**（牺牲"代码加密"语义）
- 用"独立进程 + 进程间通信"（UWP 对多进程支持有限）

### 2.2 🟡 antidebug：大部分检测项失效

现有 12 维检测中：

| 检测项 | UWP 下 |
|--------|--------|
| `peb_being_debugged` / `peb_nt_global_flag` | 🟡 读自身 PEB 通常可行 |
| `debug_port` / `debug_flags` / `debug_object` | 🟡 需 `NtQueryInformationProcess`，可能受限 |
| `hardware_breakpoints` | ✅ 读自身线程上下文，可行 |
| `timing_suspicious`（QPC+Sleep）| ✅ 可行 |
| `kernel_debugger` | 🟡 需系统信息查询，可能受限 |
| `debug_heap_flags` | 🟡 需读 PEB，可行性待测 |
| `int3_honey` | ✅ 自身代码，可行 |
| `ppid_blacklist` | 🟡 需查询父进程，沙箱可能限制 |
| `clock_drift_sec` | ✅ 可行 |

**判定**：**部分可用**，但"跨进程/系统信息"类检测在沙箱下受限。
具体哪几项失效**需在真实 MSIX 环境实测**。

### 2.3 ✅ 可用类（授权与加密）

| 模块 | 为何可用 |
|------|----------|
| `license` | RSA 验签是纯计算；授权文件读取可用 `ApplicationData` 或 `StorageFile` |
| `hostid` | 读取硬件标识通常允许（部分项可能在沙箱下受限）|
| `strcrypt` | 进程内解密字符串表，无特殊权限 |
| `indirect` | 纯调用约定（`s_fn[]` + `s_perm`），无权限需求 |
| `vm` | 解释器是纯计算；但**若 VM 镜像需从外部装订**，涉及文件访问 |

### 2.4 🟡 blob（外部装载）：需调整

现有实现从 exe / URL 装载 `vm.blob`。UWP 下：
- 文件系统被沙箱化（仅 `ApplicationData`、已知位置）
- 网络需声明能力（`internetClient`）

**可行但需改路径策略**。

## 4. 建议

### 4.1 我的建议：**不做完整 UWP 支持**

理由：

| 理由 | 说明 |
|------|------|
| **技术冲突是根本性的** | selfcrypt/完整性校验与 W^X 沙箱模型冲突（§2.1）|
| **目标用户很少** | UWP 应用在商业桌面软件中占比**低**；企业内部分发多用 MSIX 打包的**桌面应用**（非 AppContainer）|
| **机会成本高** | 同样投入放在 .NET 门（**已完成**）、在线授权、跨平台等回报更高 |
| **分支维护成本持续** | UWP 版需与桌面版并行维护，违反"单一事实源"原则 |

### 4.2 但有一个**高价值替代**：MSIX 打包的**桌面应用**

> **区分两个概念**：
> - **UWP / AppContainer**：强沙箱，与自保护冲突（§2.1）
> - **MSIX 打包的 Win32 桌面应用**：可声明 `runFullTrust` 能力，**几乎无沙箱限制**

**MSIX + `runFullTrust` 的桌面应用**是本项目**完全可以支持**的形态：
- 保护能力不受影响（等同普通桌面应用）
- 获得 MSIX 的部署优势（干净安装、自动更新、卸载无残留）

**这可能是用户真正想要的** —— 若目标是"现代化打包"，走这条路即可，
**不需要**改保护方案。

### 4.3 建议的后续动作（若你认可）

| 优先 | 项 | 成本 |
|------|----|------|
| 1 | 写一份 **MSIX + runFullTrust 打包指南**（不改保护代码）| 低 |
| 2 | 若确有 UWP 需求，先做 **U2（真实环境逐模块实测）** | 中 |
| 3 | 仅在 U2 证明可行后，才评估 U3（重设计自加密）| 高 |

## 6. 一句话总结

> **UWP（AppContainer）与本项目的"自加密 + 反调试"能力有根本性冲突 ——

> 形态完全可用且无需改保护方案。建议走后者。**
