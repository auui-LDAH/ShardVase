# 调试控制台计划（DEBUG_CONSOLE_PLAN）

> **性质**：用户 2026-09-30 提出的**新待办** —— 把本项目反复手工做的调试动作
> 收敛为一个**可用工具**。本文件是设计与分步计划（**待确认后实施**）。
> **版本**：2026-09-30 v1 · 状态：**📋 待确认**

---

## 0. 一句话

**本项目 100+ 次调试里，同一批动作被反复手写**（找符号 → 算运行时地址 →
读写目标进程内存 → 解释退出码 → 读内部计数器），每次都写临时脚本、
每次都可能踩同一批坑（路径空格、blob 路径、反调试干扰、编码）。
**把它们做成一个控制台 = 把调试经验固化为工具。**

## 1. 依据：我们**实际反复做过**的调试动作（全部有实例）

| # | 动作 | 出现次数（实例） | 痛点 |
|---|------|----------------|------|
| ① | **map 符号解析**（`--map <file.map> --sym X`）| 5+（R3.2-a 判定点定位、DRILL8 RVA 对比、guard 验证）| 每次重写正则 |
| ② | **运行时地址换算**（链接时 VA + 模块基址，ASLR）| 4+（两次 patch 实验、读回验证、hits 读取）| 易错，需 `CreateToolhelp32Snapshot` 模板 |
| ③ | **写目标进程内存**（`31 C0 C3` patch）| 4+（DRILL7 手法复现、5 判定点验证）| 需 OpenProcess 权限 + 错误处理 |
| ④ | **读目标进程内存**（读序言、读计数器）| 3+（原序言读回、`g_guard_hits`）| 同上 |
| ⑤ | **退出码解释**（2989=0xBAD / 219=0xDB / 45323 / 11) | 8+ | 每次查 `protdef.h` |
| ⑥ | **selfcrypt 掩码区归属判定** | 3（R3.2-a、判定点分析、位置复核）| 需读 mask + 比对 |
| ⑦ | **进程启动参数**（`--vm-blob` 必须显式传）| 6+（perf_baseline、smoke、多次实验）| **踩过坑**：不传 -> rc=45323 |
| ⑧ | **结构化输出落盘**（JSON 证据）| 4（`r32a_verdict.json`、`guard_selftest.json`）| 格式不统一 |
| ⑨ | **反调试干扰的识别** | 1（**本轮**：219 由工具自身 OpenProcess 触发）| **最危险**：误判为"守卫有效/失效" |

## 2. 设计目标

```
一个 **单文件 CLI**（`tools/prot_dbg.py`），提供:
  $ prot_dbg sym <name>                  # ① 符号 -> 链接时 VA（+ .text 偏移 + 掩码区归属）
  $ prot_dbg run [--args ...]            # ⑦ 正确启动（自动补 --vm-blob，避免 45323 坑）
  $ prot_dbg patch <sym> [--pid P]       # ②③ 运行时 patch（ASLR 自动换算）
  $ prot_dbg read <sym> [--len N]        # ④ 读运行时内存
  $ prot_dbg watch <sym>                 # 读它（含 static 计数器）
  $ prot_dbg exit <code>                 # ⑤ 退出码解释（从 protdef.h 解析，不硬编码）
  $ prot_dbg mask <sym>                  # ⑥ 掩码区归属
  $ prot_dbg doctor                      # 环境体检（构建产物/符号/blob/权限）
```

### 2.1 **关键设计纪律**（都来自实际踩坑）

| 纪律 | 来源 |
|------|------|
| **退出码解释从 `protdef.h` 解析** | R1 的 `docclaim` 教训：硬编码会漂移 |
| **`--vm-blob` 自动补全** | perf_baseline 实测 rc=45323 |
| **路径一律用绝对路径 + 引号** | 仓库路径含空格（R2.3 四处缺陷） |
| **所有输出 `encoding='utf-8', errors='replace'`** | cl.exe 中文输出致 UnicodeDecodeError |
| **判据输出"命中计数"而非"进程是否死"** | **本轮 §10 教训**：进程死会被任何同向检测满足 |
| **显式提示"本工具自身可能触发反调试"** | **本轮**：219 由 OpenProcess 触发，差点误判 |
| **不改仓库状态**（只读 + 目标进程内写） | 自检纪律（自检不得改坏仓库） |

### 2.2 **与既有工具的分工**（**不重复造**）

| 已有 | 职责 | 本工具关系 |
|------|------|-----------|
| `tools/attacker/winpe_sympatcher` | 攻击者视角的符号解析 + 内存 patch（**演练用**）| **本工具是防御方调试用**；语义重叠处**直接复用**其 `symparse`/`mempatch` 思路，不新写解析器 |
| `tools/guard_selftest.py` | 特定守卫的行为自检（门禁项）| 本工具可**辅助其定位**（`sym`/`mask`/`watch`）|
| `tools/mutate_check.py` | 检查器变异测试 | 无关 |
| `-DPROT_INTEGRITY_DEBUG` 构建 | 内部诊断输出 | 本工具可**包装**该构建（见 §3 第 3 步）|

## 3. 分步计划

### 第 1 步 `doctor` + `exit` + `sym`（**只读，零风险**）

| 项 | 内容 |
|----|------|
| 做什么 | 环境体检（`build/demo.exe`/`demo.map`/`vm.blob`/符号可解析/权限）· 退出码解释（**从 `protdef.h` 解析**）· 符号查询（VA + `.text` 偏移 + **掩码区归属**）|
| 验收 | ① 对 `prot_license_verify` 输出与 R3.2-a 实测一致（rva `0x4770`，**在掩码区内**）② 退出码 `2989 -> PROT_EXIT_TAMPERED` ③ `--selftest`（含负向：不存在的符号必须报错退出）|
| 风险 | 低（纯读）|

### 第 2 步 `patch` / `read` / `watch`（**目标进程内写，需权限**）

| 项 | 内容 |
|----|------|
| 做什么 | 运行期 patch（ASLR 自动换算）· 读内存（序言/计数器）· `watch` 轮询计数 |
| 验收 | ① 复现本轮 5 判定点实验 **一条命令**完成 ② **patch 前后读回验证**（写入生效）③ 无权限时**明确报错**（不静默失败）|
| 风险 | 中（写远程内存；但**只作用于调试目标**）|

### 第 3 步 `run` + **诊断构建包装**（`-DPROT_INTEGRITY_DEBUG`）

| 项 | 内容 |
|----|------|
| 做什么 | `run` 自动补 `--vm-blob` 等参数；`run --debug-build` 触发 `-DPROT_INTEGRITY_DEBUG` 构建并**捕获 IDBG 输出**（当前需要手工改构建参数）|
| **为什么这步重要** | **R3.2 §10.4 的定位正需要它**："守卫是否被调用/调用几次/比对几项"目前**不可观测** -> 这是把不可观测变可观测的**必要工具** |
| 验收 | 跑一次 demo，能看到 `[IDBG] check_self: …` 与守卫的调用记录 |
| 风险 | 中（需改构建参数；诊断构建**不可发布**，工具须**显式标注**）|

### 第 4 步 **反调试干扰提示**（**本轮教训的固化**）

| 项 | 内容 |
|----|------|
| 做什么 | 使用 `patch`/`read`/`watch` 时**主动打印警告**：本工具用 `OpenProcess`/`ReadProcessMemory`，**可能被 demo 自身的反调试检测到**，导致退出码 `219`（`PROT_EXIT_DEBUG_DETECTED`）—— **该退出码不能作为"守卫有效/失效"的判据** |
| 为什么 | 本轮我**差点**把 `219` 误读为"守卫失效"，实际是**工具自身**触发反调试 |
| 验收 | 提示文本出现在 `patch`/`watch` 的输出里；`--quiet` 可关 |

## 4. **明确不做**

| 不做 | 理由 |
|------|------|
| 远程/内核调试 | 另一量级（`KERNEL_DRIVER_ASSESSMENT.md`）|
| GUI 界面 | CLI 足够；且**非交互环境可脚本化**（门禁要能用）|
| 替代 `winpe_sympatcher` | 那是**攻击者视角**的演练工具，两者定位不同、**共享思路不共享代码** |
| 自动"一键破解/一键验证防御" | 会掩盖判据问题（**本轮教训**：判据必须可独立解释）|
| 改动产品代码 | 本工具**只调试**，不改 `src/` |

---

## 5. 与 R3.2 的关系（**优先级**）

```
R3.2 §10.4 的定位（"守卫为何一次都没命中"）**正需要第 3 步**
=> 建议: **先做第 1 + 3 步**（`sym`/`mask`/`exit` + 诊断构建包装），
   用它把"不可观测"变"可观测"，**再回头解 R3.2 的谜**
   —— 否则只能靠猜（而猜测已被本轮证明不可靠）。
```
