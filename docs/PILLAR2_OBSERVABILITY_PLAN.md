# 配置不可观测（第二支柱）实施计划

> **方针（已确认）**：采纳"配置不可观测"作为**第二支柱**；
> 先做 **§4.1 + §4.3 + §4.4**；**接受产物变大的代价**。
> **上位方针**：完全开源 + 简化 VM + 抬高破解成本（`docs/STRATEGY_FULL_OPEN_SOURCE.md`）
> **问题来源**：`docs/OPEN_SOURCE_COMPENSATION.md`（实测发现三处可观测）
> **日期**：2026-09-21

---

## 0. 目标与验收（可机器检验）

### 0.1 核心目标

> **让攻击者无法从产物静态判断"这一次部署开了哪些防护"。**
> 他必须**动态摸底**才能知道 —— 而每个新构建都要重做一遍。

### 0.2 总验收指标（三条，全部可脚本检验）

| # | 指标 | 目标 | 检验方式 |
|---|------|------|----------|
| **A1** | **组合不可区分** | 4 个组合（`minimal`/`standard`/`hardened`/`full`）的 **节名集合**、**各节尺寸**、**文件尺寸** **完全一致** | 脚本比对 PE 节表 |
| **A2** | **配置串不可探测** | 产物中**不存在**可推断组合的特征串（`--dbiguard-policy`、`vm_hypervisor` 等） | 字符串扫描（含加密后） |
| **A3** | **标注不可自解释** | 产物中**不存在** `PROTCRC` 等自解释 magic（改为每构建随机） | magic 白名单比对 |

> **重要**：A1 的"完全一致"是**难度最高**的一条 —— 因为 `.text` 差异
> 来自"编进去多少代码"。本计划用**向上填充到统一基准**解决（见 §2）。

## 1. 现状实测（计划的事实基础）

### 1.1 组合可区分（实测）

固定种子，只变组合：

| 组合 | 文件字节 | 节数 | 特征 |
|------|---------|------|------|
| `minimal` | 215040 | **10** | **无 `.protcrc`** |
| `standard` | 226304 | 11 | 有 `.protcrc` |
| `hardened` | 229376 | 11 | + `vmdetect` |
| `full` | 229376 | 11 | + `vmdetect` |

**尺寸差异分解**（minimal vs full，共 14336 字节）：

| 节 | minimal | full | 差额 | 可否填充 |
|----|---------|------|------|----------|
| `.text` | 0x1EC00 | 0x20E00 | **+8704** | ✅ 向上填充 |
| `.rdata` | 0xCC00 | 0xDC00 | **+4096** | ✅ |
| `.pdata` | 0x1C00 | 0x1E00 | +512 | ✅ |
| `.protcrc` | **0** | 0x200 | **+512** | ✅（创建空节）|
| `.protxec` | 0x600 | 0x800 | +512 | ✅ |
| 其余 6 节 | — | — | **0** | 已一致 |

### 1.2 标注自解释（实测）

`.protcrc` 内容（512 字节，VSize=48）：

```
magic "PROTCRCP" + crc  -> .pdata
magic "PROTCRCD" + crc  -> .rdata
magic "PROTCRDP" + crc  -> .text
```

来源：`tools/hashpatch.py` 的 `MAGICS = (b'PROTCRCP', b'PROTCRCD', b'PROTCRDP')`

**覆盖范围**：仅 3 段；**未覆盖 8 节**（含 `.data` 与 `.protcry` 可写区）

### 1.3 检测项固定（实测）

`antidebug` 的 12 个检测项**硬编码**，每项 1-2 个赋值点：

```
peb_being_debugged / peb_nt_global_flag / debug_port / debug_flags
debug_object / hardware_breakpoints / timing_suspicious / kernel_debugger
debug_heap_flags / int3_honey / ppid_blacklist / clock_drift_sec
```

### 1.4 节名硬编码点（改造面）

| 文件 | 节名 |
|------|------|
| `src/antidebug.c` | `.protxec` |
| `src/crc32.c` | `.protxec` |
| `src/integrity.c` | `.protcrc`, `.protxec` |
| `src/selfcrypt.c` | `.protpad`, `.protcrypt`, `.protxec` |
| `tools/hashpatch.py` | `.protcrc` |
| `tools/selfcrypt_proto.py` | `.protcry`, `.protcrypt` |

### 1.5 ⚠️ 一条既有决策：**不用空桩**

`demo/gen/prot_modconfig.h` 明确写着：

> 未定义的模块: 既不编译也不链接（**P2: 不用空桩, 避免桩成为攻击面**）

**本计划的设计约束**：因此**不引入模块空桩**。
统一形态靠**只统一节（存在性 + 尺寸）**，不加任何模块代码（见 §2，已验证可行）。

## 2. 关键技术验证（已完成，方案据此设计）

| 验证 | 结果 | 意义 |
|------|------|------|
| **空节能否保留** | ✅ 用 `__declspec(allocate)` 1 字节占位即可 → `.protcrc` VSize=0x1 出现 | **无需模块空桩**即可统一节集合 |
| **尾部填充是否安全** | ✅ 追加 4096 字节后 `rc=0` 正常输出 | 可安全统一文件尺寸 |
| **构建插入点** | `selfcrypt_proto`(L315) → `hashpatch`(L333) → 签名 | 归一化步骤插在 **hashpatch 之后、签名之前** |

> **为什么插在 hashpatch 之后**：归一化会改变产物字节，
> 必须让**完整性 CRC 覆盖归一化后的最终形态**（否则 CRC 与产物不符）。

## 3. 阶段划分（5 阶段，每阶段独立可验收）

```
阶段 1  节名随机化（§4.4 部分）        —— 消除"看名字就知道"
阶段 2  组合归一化（§4.1）             —— 消除"节集合/尺寸差异"
阶段 3  标注去自解释（§4.4）           —— 消除 PROTCRC magic
阶段 4  完整性覆盖扩展（§4.4）         —— 扩大 + 随机化覆盖范围
阶段 5  检测项不可枚举（§4.3）         —— 随机子集 + 伪装
```

**依赖关系**：
```
阶段 1（节名随机）─┬─→ 阶段 2（归一化，需知道节名）
                   └─→ 阶段 3（magic 随机化，与节名同源）
阶段 4（覆盖扩展）── 独立（但需在阶段 2 之后，否则填充会破坏 CRC）
阶段 5（检测项）──── 独立
```

**建议顺序**：`1 → 2 → 3 → 4 → 5`

## 4. 阶段 1：节名随机化

### 4.1 目标
产物中的 `.protxec`/`.protcrc`/`.protcry`/`.protpad`/`.fptable` 等**自解释节名**
改为**每构建随机**（如 `.x7f3a91`）。

### 4.2 做法

| 步 | 动作 |
|----|------|
| 1.1 | `compose.py` 生成节名映射（每构建随机 8 字符），写入 `demo/gen/prot_sections.h` |
| 1.2 | 4 个 `.c` 文件的 `#pragma` 改用宏（如 `PROT_SEC_CRC_SEG`）|
| 1.3 | `hashpatch.py` / `selfcrypt_proto.py` 接受 `--section-map` 参数（由构建传入）|
| 1.4 | `build.ps1` 串联：生成映射 → 编译 → 后处理时传映射 |

### 4.3 验收
```
A3': 产物节名与上一构建**完全不同**（随机化生效）
A3'': 所有已知节名（.protxec/.protcrc/.protcry/.protpad/.fptable）**不再出现**
```

### 4.4 风险
| 风险 | 应对 |
|------|------|
| `#pragma section` 名长度限制（PE 节名 8 字节）| 用 8 字符内 |
| 工具侧硬编码节名遗漏 | grep 全仓库 + 加检查脚本 |
| `.protcry` 需可写属性 | 随机名 + 同样属性（映射表含属性）|

---

## 5. 阶段 2：组合归一化（**最关键，也最难**）

### 5.1 目标
4 个组合的**节集合 + 各节尺寸 + 文件尺寸完全一致**。

### 5.2 做法：**向上填充到统一基准**

```
基准 = 所有组合中每个节的**最大尺寸**（当前由 full 决定）
对每个组合: 把每节填充到基准尺寸（不足部分填随机字节）
```

| 步 | 动作 |
|----|------|
| 2.1 | **统一节集合**：让 `.protcrc` 在所有组合都存在（用 1 字节占位，已验证）|
| 2.2 | 新建 `tools/normalize_pe.py`：读 PE 节表 → 按基准扩展各节 RawSize → 同步修正文件偏移与 `SizeOfImage` |
| 2.3 | 填充内容用**每构建随机字节**（不是零）—— 避免"零区"成为特征 |
| 2.4 | `build.ps1` 在 hashpatch 之后调用它；基准值写入 `build/section_baseline.json` |
| 2.5 | 首次运行生成基准；后续构建读取（保证跨构建可比）|

### 5.3 验收
```
A1: 4 组合的 {节名集合, 各节VSize/RawSize, 文件大小} **完全一致**
    -> 脚本逐字段比对，任一不同即 FAIL
```

### 5.4 风险（**这是本计划最大的技术风险**）

| 风险 | 说明 | 应对 |
|------|------|------|
| **改 PE 结构可能破坏加载** | 改 RawSize/文件偏移需同步修正多处头字段 | 每步后**实测运行**；先做最小改动验证 |
| **`.text` 填充可能影响 selfcrypt** | 加密段页面关系（P2 教训：revoke 曾因同页自排除）| 填充**放在 hashpatch 之后** → selfcrypt 已定型；但需**实测**确认页关系未变 |
| **调试目录/校验和** | PE 的 `CheckSum` 与 `SizeOfImage` | 归一化后重算或置零 |
| 产物变大 | minimal 215040 → 约 229376+（+6.7%）| **已接受**（方针确认）|
| 填充破坏签名 | 归一化在签名**之前** → 无影响 | 顺序保证 |

### 5.5 诚实预判
> **`.text` 的填充可能不足以完全掩盖"代码量差异"** ——
> 填充区与真实代码区的**熵分布**不同（代码有指令模式，填充是随机）。
> 攻击者仍可能通过**熵分析/反汇编覆盖率**推测"有没有某模块"。
>
> **若出现这种情况，它是真实边界，应如实记录**（而非掩盖）。

## 6. 阶段 3：标注去自解释

### 6.1 目标
`.protcrc`（随机名）中的 `PROTCRCP/D/P` magic 改为**每构建随机**。

### 6.2 做法
| 步 | 动作 |
|----|------|
| 3.1 | `hashpatch.py` 的 `MAGICS` 改为从 `--magic-seed` 派生 |
| 3.2 | 生成侧与校验侧（`integrity.c`）用同一派生算法 |
| 3.3 | 派生结果写入 `demo/gen/prot_magics.h`（供 C 侧编译期使用）|

### 6.3 验收
```
A3: 产物中不含 PROTCRC 字面量；magic 每构建不同
```

## 7. 阶段 4：完整性覆盖扩展

### 7.1 目标
覆盖范围从"固定 3 段"改为"**更全 + 随机**"。

### 7.2 做法
| 步 | 动作 |
|----|------|
| 4.1 | 覆盖扩展到**全部节**（含 `.data` `.protcry` `.fptable` 等当前未覆盖区）|
| 4.2 | **每构建随机**选择覆盖哪些段（攻击者不知边界）|
| 4.3 | CRC **链式**：段间互相依赖（改一处须重算整链）|
| 4.4 | `.protcrc` 条目数随之变化（不再固定 3 条）|

### 7.3 验收
```
A4: 未覆盖节数 = 0（或按随机策略 ≥N）；两次构建的覆盖集合不同
```

### 7.4 风险
| 风险 | 应对 |
|------|------|
| 覆盖 `.protcry`（selfcrypt 密文区）会导致**自身改写触发误报** | 需排除"运行期必然变化的区域"，或改为"校验后再解密" |
| CRC 链式增加实现复杂度 | 先做"覆盖扩展"，链式作为可选增量 |
| 与阶段 2 填充冲突 | **顺序保证**：填充在归一化步骤（hashpatch 之前完成），CRC 覆盖最终形态 |

> ⚠️ **注意**：阶段 4 与阶段 2 的顺序需仔细设计 ——
> CRC 必须覆盖**归一化后**的字节，故 `normalize → hashpatch`。

## 8. 阶段 5：检测项不可枚举

### 8.1 目标
攻击者无法从源码/产物**确定这次查哪些项**。

### 8.2 做法
| 步 | 动作 |
|----|------|
| 5.1 | 每构建**随机选子集**（如 12 项中选 7-10 项，`compile-time` 随机）|
| 5.2 | **等价变体**：同一检测的多实现（读 PEB / 系统调用 / 时序），随机选 |
| 5.3 | **伪装**：未启用的检测项**保留代码**但返回固定值（形态一致）|
| 5.4 | 子集与变体选择写入 `demo/gen/prot_antidebug_sel.h` |

### 8.3 验收
```
A5: 两次构建的启用项集合不同；
    产物中 12 项的实现代码**都存在**（无法从静态判断哪项生效）
```

### 8.4 风险
| 风险 | 应对 |
|------|------|
| **降低检测强度**（子集少了漏检） | 设**下限**（如至少 8 项）；关键项（`peb_being_debugged`）**强制启用** |
| 伪装代码被优化掉 | 用 `volatile`/`#pragma optimize` 保留 |
| 与"简化 VM"张力 | 检测项伪装**增加**代码量，与简化方向相反 —— 但属**已接受的代价** |

## 14. 方案修订（2026-09-23 实测后）

> 阶段 2 的原始方案是"构建后读 PE 节表 -> 改 RawSize/文件偏移"。
> 本节记录实测后的**方案调整**：改用**源码级填充**，风险显著更低。

### 14.1 三条新证据（实测）

| # | 发现 | 数据 | 意义 |
|---|------|------|------|
| **1** | **组合名不进产物** | `full` vs `_probe_all`（同模块集、不同名）差异 **0 字节** | 只有**模块集**影响形态 -> 归一化的目标更明确 |
| **2** | **`.text` 可用源码级填充精确增大 VSize** | base `0x14D60` -> 加 8192 后 `0x16D50`（**正好 +8192**）| **无需改 PE 结构** |
| **3** | 各组合真实差异 | `minimal` 215040 vs `full` 229376 = **14336 字节（6.25%）** | 这就是"放弃体积收益"的量 |

**关于第 2 条的写法**（已验证 `/W4 /WX` 无警告）：

```c
#pragma section(".text")
__declspec(allocate(".text")) unsigned char g_pad[N] = { 0 };
```

### 14.2 方案调整对照

| 项 | 原计划 | **修订后** |
|----|--------|-----------|
| 统一节集合 | 用 1 字节占位创建空节 | ✅ 同（已在小验证中验证可行）|
| 统一节尺寸 | **改 PE 头**（RawSize/偏移）| **源码级填充到目标尺寸** |
| 统一文件尺寸 | 尾部追加填充 | 节尺寸统一后**自然统一** |
| 主要风险 | **改 PE 结构可能破坏加载** | 低（无结构改动，链接器自然产出）|

### 14.3 仍需验证（下一轮）

| # | 待验证 | 为什么重要 |
|---|--------|-----------|
| V1 | 填充**内容随机化** | 零区本身是特征（"这里是被填充的"）|
| V2 | 填充后 **selfcrypt/hashpatch 仍正常** | 二者都处理 `.text`，填充改变其形态 |
| V3 | `.rdata`/`.pdata` 是否同样可用源码填充 | 需多节统一 |
| V4 | 填充是否影响 **repro_check**（可复现性）| 随机填充 + 固定种子须仍可复现 |

### 14.4 本轮同时修掉的一个缺陷

**节名随机化曾破坏 I3 可复现构建**（我引入的）：

### 16.2 三个真实边界（全部实测定位）

#### 边界 1：填充的声明方式**必须与源码一致**

| 节 | 源码声明 | 我初版用 | 结果 |
|----|---------|---------|------|
| `.protxec` | `#pragma code_seg(...)` | `#pragma section(..., read, execute)` | ❌ **LNK4078** + 节被扭曲（0x48B -> 0x280）|

改用 `code_seg` 后：**0x47B -> 0x6FC（正好 +641），无警告** ✓

#### 边界 2：标准节**不能带属性**（MSVC 三种写法实测）

| 写法 | 结果 |
|------|------|
| `#pragma section(".text")` + `allocate` | ✅ **成功，VSize +4096** |
| `#pragma section(".text", read, execute)` + `allocate` | ❌ C4325（忽略标准节特性）|
| 仅 `allocate`（无 pragma） | ❌ C2341（用法前必须定义段）|

**结论**：`#pragma section("<标准节>")` **不带属性参数**才是正确写法。

#### 边界 3：工具链管理的节**不可填充** —— 这是真实边界

| 节 | 填充结果 | 原因 |
|----|---------|------|
| `.pdata` | ❌ LNK4078，节被分裂 | 展开信息，**随函数数增长** |
| `.reloc` | ❌ LNK4078 | 真节是 DISCARDABLE，属性无法用 pragma 匹配 |
| `.rsrc` | ⚠️ 见下 | — |
| `.data` | ⚠️ 部分生效 | 属性冲突 |

> **这些节的尺寸是"代码的派生量"**：`.pdata` = 每个函数的展开信息记录，
> 函数多则大。**正确的归一化方式是"增加函数"而非"塞数据"**。
>
> 剩余差异合计仅 **920 字节**（`.data` 144 + `.pdata` 708 + `.reloc` 68），
> 相比原始差异 14336 字节已消除 **93.6%**。

### 17.4 发现的残留可区分性（诚实记录，未解决）

`.protcrc` 节的内容形态在两种组合下**语义不同**：

| 组合 | `.protcrc` 前 16 字节 | 含义 |
|------|----------------------|------|
| `full`（含 integrity）| `5f74370633087e06 efdb3fe3 00000000` | magic + **真实 CRC**（`0xE33FDBEF`）|
| `minimal`（填充创建）| `1be2ddac2b603839 ba89c1b2 218efb7a` | **纯随机**（无结构）|

**两者静态看都是"16 字节随机"**（因 magic 本身已随机化，阶段 3 成果），
**故直接读内容无法区分** ✓

**但仍有一处残留**：攻击者可**重算 `.text` 的 CRC** 并与该字段比对 ——
`full` 的字段是真值（匹配），`minimal` 的是填充值（不匹配）
→ **能区分**。

**处理方向**（未实施）：
- 让无 integrity 的组合也**写入一个真实（但无意义）的 CRC**，使其"匹配"
- 或让 integrity 的校验**不落静态字段**（运行期现算）—— 与 §4.2 方向一致
