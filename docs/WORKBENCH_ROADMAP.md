## 1. 三件套的逐项差距（实测）

### 1.1 工作台（编排器）—— 现状 70%

| 能力 | 状态 | 证据 |
|------|------|------|
| 组合解析（`compositions/*.json`）| ✅ | 4 档预设 + 任意自定义 |
| 源文件清单输出 | ✅ | `--sources-out` |
| 条件编译头输出 | ✅ | `--header-out` → `prot_modconfig.h` |
| 依赖自动补入 | ✅ | `SUBSTRATE`（8 个宿主下限模块）|
| 源文件顺序固定 | ✅ | `SOURCE_ORDER`（15 项，影响 `.text` 布局）|
| **冲突检测** | ⬜ | 由 `modcheck` 承担（未内聚到编排器）|
| **拓扑排序** | ⬜ | 顺序硬编码在 `SOURCE_ORDER` |
| **按策略自动选模块** | ⬜ | 用户必须手写模块列表 |
| **构建计划结构化输出** | ⬜ | 只有文本清单，无带理由的计划 |

**差距**：编排器**只做"翻译"**（JSON → 编译参数），**不做"决策"**。
即：**用户选模块**，而非**用户选策略**。

### 1.2 模块协议 —— 现状 60%

对照"四层协议"，**字段级**实测：

| 协议层 | 实际字段 | 差距 |
|--------|---------|------|
| **阶段** | `phases`（`init`/`scan`/`decide`/`enforce`/`watch`）| ✅ 值域合理，5 个阶段全被使用 |
| **数据 consumes** | **（无）** | ❌ **缺** |
| **数据 produces** | `exports`（语义不同）| ⚠️ `exports` 是"导出符号"，非"产出资源" |
| **数据 modifies** | `modifies_text`（布尔）| ⚠️ **粒度粗**（只有 `.text` 有/无）|
| **效果 effects[]** | `caps` + `verifies_text` | ⚠️ **无独立 effects 数组** |
| **约束 requires** | `deps` | ✅ 有 |
| **约束 conflicts_with** | **（靠推导）** | ❌ **无显式声明** |
| **约束 ordering** | **（`SOURCE_ORDER` 硬编码）** | ❌ **无模块级声明** |
| **资源开销** | `known_limits`（自由文本）| ⚠️ **非结构化** |

**关键差距**：
- ❌ `conflicts_with` 缺 → 现在由 `modcheck` 用 `modifies_text × verifies_text` **隐式推导**（只覆盖 1 类冲突）
- ❌ `ordering` 缺 → `SOURCE_ORDER` 是**全局硬编码列表**，模块无法声明自己的先后约束
- ❌ `consumes`/`produces` 缺 → 无法做**数据流级**冲突检测

### 1.3 去模块化器 —— 现状 60%

| 手段 | 状态 | 实测 |
|------|------|------|
| 节名随机化 | ✅ | 残留仅 `.fptable`（MSVC 默认节，无语义暗示）|

| 特征串加密（检测项名）| ✅ | 19 项**全部消除** |
| 符号擦除 | ✅ | 模块函数名 **0/32** 可见 |
| 函数级间接化 | ✅ | `s_perm` 每构建变 |
| **代码内联/融合** | ⬜ | 未实现 |
| **布局随机化** | ⬜ | 未实现（节顺序固定）|
| **诱饵注入** | ⬜ | 未实现 |
| **元数据零泄露** | 🟡 | 组合名不进产物 ✓；但仍有 634 条可读串 |

### 1.4 ⚠️ 最关键的量化差距：**跨构建差异率仅 0.55%**

**实测**（同组合、随机种子构建两次）：

| 指标 | 实测 | 目标 | 差距 |
|------|------|------|------|
| **差异字节率** | **0.55%**（1256 / 229888）| **>30%** | **差 29.5 个百分点** |
| 差异块数 | 5 / 57（8.8%）| 均匀分布 | 集中（`0x23000` 占 1128/1256）|

**这是路线图中**最重要**的一项**：

> 攻击者拿到**两个构建** → 一次 binary diff → 差异集中在 **5 个 4KB 块**
> → **直接定位全部 per-build 秘密** → 定向分析。
>
> **"每构建变化"是开源方针的唯一强杠杆，而它目前只覆盖 0.55% 的产物。**

### 1.5 跨组合仍可区分（实测）

同种子下 `minimal` vs `full`：

| 项 | 结果 |
|----|------|
| 文件大小 | ✅ **相同**（229888）|
| 节名序列 | ❌ **不同**（`.wsllapv` 位置互换）|
| 节尺寸 | ❌ **3/11 相同**（`.rdata`/`.data`/`.pdata`/`.reloc` 等仍差）|

**含义**：尺寸归一化**消除了总量差异**，但**逐节仍有可区分性**（工具链管理的节无法填充）。

## 3. 路线图（六阶段，每阶段独立可验收）

> **原则**：**不追求快速，保留最大潜力**。
> 每阶段收尾必须：**门禁 14/14 + 文档同步 + 独立验收**。

```
阶段 W1  差异扩散（0.55% → >30%）      ← 最高优先，方针的命脉
阶段 W2  协议形式化（开放规范 + 版本）    ← 生态的地基
阶段 W3  编排器升级（策略 → 计划）        ← "用户选策略不选模块"
```

## 6. 诚实的风险与边界

| 风险 | 说明 |
|------|------|

| **维护者精力** | 开源项目最大的敌人（文档亦已提示）|

## 8. W1 实施记录（2026-09-23 完成）

### 8.1 成果：差异率 0.54% -> **67.85%**

| 验收 | 目标 | 实测 | 判定 |
|------|------|------|------|
| **V1 跨构建差异率** | > 30% | **67.85%** | ✅ |
| **V2 差异均匀性** | 均匀分布 | 差异块 **72/80 (90%)**；最密 4082 / 最疏 64（比值 63.8，旧版 **140**）| ✅ 显著改善 |
| **V3 跨组合大小一致** | 完全一致 | 4 组合**全部 327680 字节** | ✅ |
| **V4 功能完好** | rc=0 | rc=0 + `license: 1` | ✅ |
| **V5 可复现** | 同种子一致 | 两次构建 SHA 相同 | ✅ |

### 8.2 根因（实测定位）

**为什么原来只有 0.54%**：阶段2 的填充逻辑是"**补齐到基线即止**"，
而基线 = 各组合最大值 -> **`full` 无需填充** -> 差异扩散对它完全无效。
实测三档差异率：minimal 0.64% / standard 0.60% / full **0.54%**。

**per-build 变化的实际来源**（仅 1250 字节）：
```
0x023000  1122 字节  <- .rdata（期望值/字符串表）
0x02C000    60 字节  <- .rdata
0x000000    32 字节  <- PE 头
0x032000    28 字节  <- .pdata
0x02B000     8 字节  <- .rdata
```
即：**差异集中在 5 个块** -> 攻击者 diff 一次即定位全部秘密。

### 8.3 实现：**总量固定 + 分布随机**

**设计教训（我在实施中犯的错）**：初版按"每节 × ratio 再随机"实现，
结果**跨组合大小又不一致**（275456/278016/281088）—— 因为起点不同，
各自加随机增量后总量自然不同。

> **归一化与扩散并不矛盾**，只要区分：
> · **总量**必须固定（= 基线文件大小 × (1+ratio)，与组合无关）-> 归一化 ✓
> · **分布**每构建随机（增量随机分配到各节）-> 扩散 ✓
>
> **随机性作用于"分配比例"，而非"总量"。**

**三个机制**：
| # | 机制 | 说明 |
|---|------|------|
| M1 | **随机填充量** | 不再"补到刚好"，而是补到 `基线×(1+0.35)` |
| M2 | **随机分布** | 预算按**随机权重**分配到各可填节 |
| M3 | **文件尾精确填充** | `tools/normalize_tail.py` 补齐到固定目标（327680），消除节对齐粒度残余 |

**插入顺序**（关键）：`节填充 → selfcrypt → hashpatch → **尾部归一化** → 签名`
（尾部必须在 hashpatch 之后以免 CRC 不符，在签名之前以免签名失效）

### 8.4 顺带修掉的一个编译警告：D9026

**现象**：W1 后出现 `cl: 命令行 warning D9026 :选项应用于整个命令行`
（W1 之前无 —— 经 git stash 对照确认为**我引入的**）。

**定位**（抓取实际命令行逐参数分析）：
```
... demo\gen\expect_default.c
    /DPROT_SELFCRYPT_D2B /DPROT_RELEASE_CONCEAL     <-- 位置 33-34
    demo\genersion.res  demo\gen\prot_padding.c   <-- 源文件在 /D 之后
    /link ...
```
根因：`$scDef`（`/D` 选项）展开在**源文件列表之后**。
W1 之前 `$padSrc` 为空，其后只有 `version.res`；W1 之后多了
`prot_padding.c` —— **源文件出现在 `/D` 之后** -> MSVC 提示该 `/D`
"应用于整个命令行"。

**修法**：把 `$scDef`/`$resObj` 移到**源文件之前**（与 `/I`/`/D` 同区）。
**为什么必须修**：D9026 意味着**选项作用域不符合预期** ——
若某天 `/D` 需只作用于部分文件，这种写法会静默出错；
且项目纪律是 `/W4 /WX`，命令行警告同样应清理。

### 9.3 自检机制（负向测试）—— 直接来自门禁失效的教训

- 差异度量：相同→0%；构造 25% 差异→25%
- **稳定核**：构造"3072 稳定 + 1024 变化"→ 必须报出 3072
- 熵剖面：均匀随机 vs 重复代码必须可分
- 畸形输入不崩溃

> **纪律**：门禁曾因 PowerShell 数组恒真而 **7/13 项失效**

**自检立刻抓到我的一个错误**（见 9.4）。

### 9.4 修掉的真实缺陷 #1：熵阈值用了**理论值**

自检报 `均匀随机窗口熵 > 7.9` 失败。标定后发现：

| 窗口 | 均匀随机经验熵**实测均值** | 理论值 |
|------|--------------------------|--------|
| 1024 | **7.805** | 8.000 |
| 4096 | 7.954 | 8.000 |
| 256 | 7.176 | 8.000 |

> **Shannon 熵的经验估计在有限样本下有负偏差** —— 1024 字节窗口覆盖 256 个
> 符号时，经验熵只有 7.805，而非 8.0。我写 `> 7.9` 是**把理论值当经验值用**。
>

**同时发现一个真实边界**：`.text` 的**最大**窗口熵达 **7.759**，
与填充的最小值（7.758）**几乎重合** → 单窗口熵判据的**可分边际很窄**
（高熵压缩数据会被误判为填充）。故工具输出**剖面**而非单一判决。

### 9.5 修掉的真实缺陷 #2：填充产生**大段零区**（严重）

**发现方式**：W5 熵剖面直接暴露 —— 自定义节均值熵仅 **1.992**（应为 ~7.8）。

**根因**（我引入的）：
```c

    0x4C, 0x6A, /* ... 仅 64 个初值 ... */ 0
    /*  ↑ 剩余 19467 字节被 C 语言零初始化！ */
};
```

**实测后果**（修复前）：

| 节 | 熵 | 零字节% | 全常量窗口 |
|----|-----|---------|-----------|
| `.hyz8aoa` | 1.081 | 90.4% | **88%** |
| `.5rusy22` | 0.162 | 98.9% | **88%** |
| `.p7tqvqd` | 0.104 | 99.3% | **92%** |
| `.dlx1lap` | 0.050 | 99.7% | **95%** |

**为什么这是严重问题**：
> 攻击者一条**熵扫描**即可圈出全部零区 = **全部填充区** →
> 滤掉它们 → 只剩真实代码 →
> **"68% 差异率"的实际防护大幅缩水**（差异确实多，
> 但**差异的位置**被零区直接标出）。

**修法**：给出**与 need 等长**的随机初值（无零区）。
源码代价：每字节约 6 字符 → 19531 字节 ≈ 117KB 生成文件，**可接受**
（生成物不入仓库，无运行期成本）。

**修复效果**（实测对比）：

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 自定义节均值熵 | 1.992 | **5.989** |
| `.text` vs 自定义节差 | **-3.779** | **-0.210** |
| 整文件熵 | 5.158 | **6.799** |
| 填充数组零值个数 | 大量 | **0** ✓ |

**判定：填充现已不可被熵分析区分** ✓

## 10. W5 第二阶段：变异测试与门禁集成（2026-09-23）

**问题**：项目有 23 个检查器，但**没有一个能自证会抓错**。

## 11. W5.6 破解迁移成本度量（2026-09-23）

### 11.1 为什么这是方针的**最终验收指标**

方针是：**"让破解者明知道我们这么防御，还是要花大量时间和资源去破解"**。
但此前**从未量化过"迁移成本"** —— 即：
> 攻击者投大量资源逆向了构建 A（找到保护点、写出绕过/补丁），
> 拿到构建 B（同组合、不同种子）后，**有多少成果能复用？**

### 11.2 新工具 `tools/migration_cost.py`

| 维度 | 含义 | 期望 |
|------|------|------|
| **M1 地址稳定性** | 函数 RVA 是否跨构建变化 | 低（硬编码地址失效）|
| **M3 特征可匹配性** | 用 A 的字节特征能否在 B 中定位同一函数 | **低（最关键）** |
| **M4 结构稳定性** | 节布局是否变化 | 低 |

> **M3 是关键**：攻击者**不需要地址** —— 取 32 字节特征做模式扫描即可跨构建定位。

### 11.3 实测结果（两次构建，同组合不同种子）

| 指标 | 实测 | 评价 |
|------|------|------|
| **M1 地址复用率** | **1.1%**（31/2896）| ✅ **很好** |
| **M3 函数特征命中** | **48.5%**（509/1049）| ❌ 偏高 |
| **M3 保护函数命中** | **55.9%**（19/34）| ❌ **迁移成本低** |
| M4 节布局完全相同 | **0/11** | ✅ 很好 |

**特征扫描实证**：
```
prot_antidebug_scan 前 32 字节（A）:
  85 0c 13 00 00 66 89 85 c4 10 00 00 0f b6 85 0e 13 00 00 ...
在 B 中搜索该特征: **命中 @ 0x51E0**（即该函数的实际位置）
```
**=> 命中即定位 -> 攻击者的绕过可跨构建复用 -> 迁移成本低** ✗

### 11.4 根本原因（设计层面的发现）

> **随机化只作用于「数据」，不作用于「代码」。**

| 每构建**变化** | 每构建**不变** |
|---------------|---------------|
| 节名 / magic | **真实函数体的机器码** |
| 期望值 / 密钥 / 掩码 | —— |
| 填充区内容（噪声）| —— |
| 间接表（调用方式）| —— |

于是攻击者用**代码特征**就能跨构建定位全部保护函数。

**注意与 W1 的关系**：W1 的"跨构建差异率 67.85%"**只说明文件整体不同**，
**不保证关键函数不可定位**。两者是**独立**的度量 —— 这正是 W5 的价值。

### 11.5 ⚠️ 我在本轮犯的一个解析 bug（重要）

**现象**：修正后 M1 从 **18.2%** 变为 **1.1%** —— 差异巨大。

**根因**：我误把 MSVC `.map` 的**第 2 列**当映像 RVA。
```
map 行: 0001:00000020   probe_fn   0000000140001020 f  a.obj
         ↑节:节内偏移    ↑符号      ↑**绝对 VA**
第 2 列 = 节内偏移（0x20），不是映像 RVA（0x1020）
```
用错列 -> RVA 落在节外 -> "无法换算"计数虚高（264 个），
且 M1/M3 数字**全部失真**。

**修法**：用第 4 列绝对 VA − image base（从 PE 头读）。

**并加回归防护**（写入自检）：
```python
case('**不得**误用第 2 列（0x1000）', m.get('_main') != 0x1000, True)
```

> **教训**：**未经验证的解析会产生"看似合理但错误"的数字。**
> 我最初报的 18.2% 和 60.6% 都很"像样"，但它们建立在错误解析上。
> **这再次证明 W5 的意义：度量本身必须被度量。**

### 11.6 修法可行性验证：序言注入

要让 M3 下降，需让**函数体字节每构建变化**。实测三种写法：

| 写法 | 结果 |
|------|------|
| `__nop()` 序列 | ✗ **被 /O2 优化掉** |
| `volatile` 读 + 使用 | ✗ 被优化掉 |
| **volatile 读 + 永不成立的分支** | ✅ **有效（首 48 字节确实变化）** |

**有效写法**（实测字节对比）：

### 12.3 宏设计的**三次迭代**（全部实测）

| 设计 | 唯一字节序列 | 结果 |
|------|-------------|------|
| `__nop()` 序列 | —— | ✗ 被 `/O2` 完全优化掉 |
| `static volatile` + 分支 | 2/5 | ✗ 碰撞 |
| 直接用 salt 做分支条件 | 2/6 | ✗ 碰撞 |
| **局部 `volatile`** | **6/6** | ✅ **采用** |

**根因（逐字节定位）**：
```c
static volatile uint32_t s_ = SALT;   // ✗ 变量进 .data
// 函数体: 8b 05 <disp32>  = mov eax, [rip+disp]
//         ↑ 只是**取地址**；地址变不变取决于链接布局 -> 不可控
//         实测 0x11111111 与 0xAAAAAAAA 生成完全相同的机器码

volatile uint32_t k_ = SALT;          // ✓ 局部
// 函数体: c7 44 24 08 <imm32>  = mov dword [rsp+8], imm32
//         ↑ salt 作为**函数体内立即数** -> 任意 salt 都改变机器码
```

**最终宏**（`include/protect/prot_noise.h`）：
```c
#define PROT_NOISE()                                    \
    do {                                                \
        volatile uint32_t prot_k_ = PROT_BUILD_SALT;    \
        uint32_t prot_v_ = prot_k_;                     \
        if (prot_v_ == 0xDEADBEEFu) { __nop(); }        \
        (void)prot_v_;                                  \
    } while (0)
```

排除 `static` 内部函数（不可定位，注入无意义且增开销）。


```
恢复后        -> M3 = 5.9%        -> PASS ✓
```

### 13.4 顺带修复：**签名依赖公网时间戳**（间歇性构建失败）

**现象**：门禁中 `Release 构建` **间歇性**失败（`signtool sign`），
而手动跑同一条命令总是成功 —— 典型网络抖动特征。

**根因**：`build.ps1` 的签名命令带
`/t http://timestamp.digicert.com` —— 指向**公网时间戳服务器**，
网络抖动/服务不可达时 signtool 返回非 0 -> **整个构建失败**。

**为什么必须修**：
- **构建不应依赖公网**（离线环境、CI 无网、时间戳服务故障都会失败）
- 本项目定位是**可复现构建** + 本地离线授权 —— 依赖公网时间戳自相矛盾
- RFC3161 时间戳会让签名**每次不同** -> 反而**破坏**字节级可复现
- 此处证书是**自签 demo 证书**，时间戳无实际信任价值

**修法**：时间戳改为**可选**（默认关闭，`$env:PROT_TIMESTAMP_URL` 可开启），
并给出**区分"证书问题"与"时间戳问题"**的诊断提示。

**复验**：签名仍 `Valid`，连续 3 次构建全部 `DONE`。

## 15. W3.3 编排器拓扑排序（2026-09-23）

### 15.1 成果：硬编码 `SOURCE_ORDER` -> **协议驱动的拓扑排序**

| 环检测 | 无 | 有（且**不静默**，报告后继续）|

**关键硬约束**：compose.py 明确写道"顺序决定 `.text` 布局，进而决定加密段与

### 15.2 ⚠️ 验证暴露的**三个真实缺陷**（全部是我引入的）

#### 缺陷 1：**真实语义环**（W2 数据错误）

```
compose: 警告: ordering 成环 integrity, selfcrypt
```

**根因**：`integrity.deps` 含 `selfcrypt`
（它需要 selfcrypt 的**掩码豁免** —— 运行时**能力依赖**），
而我给 `selfcrypt.ordering.after` 却含 `integrity`（**链接顺序**）。
→ 两个**语义不同**的关系被混在一张图里 → 报"环"。

> **关键区分**：
> - `deps` = **能力依赖**（运行时："我需要 X 的能力"）
> - `ordering` = **链接顺序**（"X 必须在我之前编译"）
>
> **二者语义不同，不可混用。** 链接顺序只由 `ordering` + `priority` 决定。

#### 缺陷 2：**priority 量纲混用**

有 `ordering` 声明的模块用 priority `10~90`，
无声明的模块用 `SOURCE_ORDER` 的 index `0~14`
→ 量纲冲突 → 顺序错乱。

**修法**：`default_prio` 改为 `index × 10`，与声明同量纲。

#### 缺陷 3：`selfcrypt` 的**万能声明**

我最初把 `selfcrypt.ordering.after` 写成**列出全部 14 个模块**

### 16.5 ⚠️ 实现中发现的**真实缺陷**（我引入的）

**现象**（首次跑 balanced 策略时）：
```

排除模块 (4):  ..., selfcrypt  能力 ['conceal'] 与所需 [...] 无交集
                   syscall   能力 ['conceal'] 与所需 [...] 无交集
```
**同一模块既在"选中"又在"排除"** —— 计划**自相矛盾**，会误导用户。

**根因**：`excluded[n]` 在"能力不匹配"时写入，之后**依赖闭包**把该模块补入
`reasons`/`selected`，却**没有从 `excluded` 删除**。

**修法**：依赖补入时 `excluded.pop(n)`，并在理由中**保留**原判信息
（改述为"依赖闭包自动补入（原判: ...）"）—— **不丢信息**。

**并加回归自检**：
```python
case('selected ∩ excluded 为空', sorted(overlap), [])
case('全部策略均无重叠', bad, [])
```

### 17.2 新工具 `tools/identity.py`（HKDF 分层派生）

```
发行方主密钥（来自 build/keys/license_priv.json 的**材料哈希**）
  ↓ HKDF-Extract(salt=project)
项目密钥
  ↓ HKDF-Extract(salt=version)
构建密钥
  ↓ HKDF-Expand(info=user_id|purpose)
用户种子（32 字节）
  ↓ 分段
  [0:8]   节名/magic    [8:12]  序言噪声盐
  [12:20] 字符串加密    [20:28] 间接表置换
```

**设计要点**：
| 决策 | 理由 |
|------|------|
| 用**材料哈希**而非私钥本身 | 不把 RSA 私钥牵进派生链（虽不可逆，但无必要）|
| **分层 Extract**（非单层 Expand）| 各层强隔离：泄露一层不影响其它项目/版本 |
| 镜像种子用 **HMAC(user_seed, image_name)** | 各 VM 镜像独立（一个泄露不影响其它）|
| **分段**而非逐维再派生 | 简单、确定性、各段独立（便于单独重派生）|

**优先级**：`-SeedsFile` > `-UserId` > 系统随机（保持 I3 可复现性）

### 17.3 自检（含 RFC 5869 官方测试向量）

```
=== 确定性 ===
  ok  同输入两次派生相同
=== 隔离性 ===
  ok  换用户 -> 变      ok  换项目 -> 变
  ok  换版本 -> 变      ok  换用途 -> 变
  ok  换主密钥 -> 变
=== 输出质量 ===
  ok  输出 32 字节      ok  非全零
```

### 17.4 ⚠️ 实现中暴露的**三个真实缺陷**（全部是我引入的）

#### 缺陷 1：`$py` 未定义（派生**静默失败**）
`$py` 由 `Find-Python` 在文件**中部**定义，而我把派生段写在**文件开头**
-> `$py` 为空 -> 派生命令失败但**没有报错** -> 两个用户产物**完全相同**。

**发现方式**：实测"两个用户 SHA 相同" —— **若只做静态检查会漏掉**。

**修法**：派生段移到 `$py` 定义**之后**（标注 `$userIdPending` 延后）。

#### 缺陷 2：`indirect` 种子分支**位置错误**
我插入的 `if ($userIndirectSeed ...)` **嵌进了**
`if ($RecordSeeds ...)` 块内部 -> **未传 `-RecordSeeds` 时用户种子不生效**
-> `indirect_table.c` 每次都变 -> 同用户不可复现。

**发现方式**：逐中间产物对比（`indirect.c` sha 不同，而 `strings.c` 相同）。

#### 缺陷 3：`blob` **完全没接**用户种子
`vm.blob` 由 `Get-SeedArgs` 取种子，而该函数**只读 `SeedsFile`**
-> 用户模式下返回空 -> blob 每次不同 -> 同用户不可复现。

**发现方式**：同上逐产物对比（`blob` sha 不同）。

**修法**：`Get-SeedArgs` 增加用户种子回退 —
`HMAC-SHA256(user_seed, "shardvase-image|<name>")` 派生 `key0`/`key1`。

**修复复验**（6 项中间产物全部相同）：
```
.blob ✓   sec.json ✓   strings.c ✓   indirect.c ✓   pad.c ✓   .exe ✓
```

> **教训**：**"跨用户唯一"与"同用户可复现"是一对约束，必须同时验证。**
> 我最初只验证了"跨用户不同"（V1 通过），若不验证 V2，
> 会得到一个"每次都变"的实现 —— 那样**破坏 I3 可复现性**，
> 而 I3 是项目既有属性（repro_check 门禁项）。

### 18.2 W6.4 模块成熟度分级（**本轮最有价值的发现**）

### 19.1 W3.5 成果：冲突检测的**单一实现**

**改动前的问题（规则分叉）**：


**两类冲突（语义不同，必须区分）**：

| 类型 | 来源 | 例 |
|------|------|-----|
| **声明式** | `conflicts_with` 字段 | selfcrypt ↔ integrity（含 resolution）|

**compose 的新行为**（此前无）：
```

compose: [冲突] 推导式冲突: 多个模块要求页对齐 integrity, selfcrypt —— 需确认各自落在独立页
compose: [共存条件] integrity <-> selfcrypt: 同 selfcrypt: 掩码豁免
compose: [共存条件] integrity <-> selfcrypt: 需确认各自落在**独立页**（S1 已证明同页会导致 VirtualProtect 自伤）
```

## 22. DIY 路径实测（2026-09-23）—— 发现一个**阻断级缺陷**

### 22.2 ❌ 关键发现：**骨架路径完全不可用**（阻断级）

**现象**：
```

```

**根因**（**我在 §15 引入的**）：

## 28. L4 完成：平台契约测试 + 间接槽位解耦（2026-09-23）

按项目纪律（**未验证 != 通过**），**不能**写"看起来对"的 Linux 实现
并声称完成。**故 L4 改为做两件可真正验证的事。**

### 28.2 L4-A: 平台层**契约测试** ✅（**关键设计**）
> **任何平台实现，只要能通过本测试，就视为契约合规。**
> **=> 把"实现 Linux"从【写代码】变成【通过测试】。**

新增 `tests/platform_conformance.c`（**32 项断言**）:
C1 capabilities 自洽 / C2 页管理往返 / C3 调试原语契约 /
C4 进程枚举容量语义 / C5 模块枚举 / C6 单调时钟 / C7 自身映像路径

**设计**: 只测**契约**不测实现细节；平台差异通过 `capabilities()`
**声明** -> 测试**按能力条件断言**（Linux 无硬件断点 -> C3.5 要求
该字段为 0，而非"必须支持"）。

**验证**: 正向 **32/32** ✅ / 负向（注入缺陷）**抓到** ✅ /
门禁连跑 2 次**稳定** ✅

### 28.3 契约测试抓到的问题（**而其中一个其实是测试的错**）
第一次在门禁环境运行 -> 失败 2 项:
```
[FAIL] C4.4 ... (capacity=1 -> 296, NULL/0 -> 298)
```

**结论**: 是**我的断言写错了** ——
> 我断言 `got == total`，**隐含假设"枚举瞬间稳定"**。
> 但真实系统上**进程随时创建/退出** -> 总数**可能不同**（差 2）。
> **这测的是【系统状态】，不是【平台层契约】。**

**修正**（改断言而非改实现）: 容差断言 + 关键区分
（若真受容量限制，NULL/0 应返回 0 —— 实际远大于 0）。

**同时完善接口文档**: 把返回值语义写成**明确契约**
