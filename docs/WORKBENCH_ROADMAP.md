> **日期**：2026-09-23
> **关联**：`docs/STRATEGY_FULL_OPEN_SOURCE.md`（方针）、
> `docs/PILLAR2_OBSERVABILITY_PLAN.md`（第二支柱）、

| 判断 | 内容 |

## 1. 三件套的逐项差距（实测）

### 1.1 工作台（编排器）—— 现状 70%

| 能力 | 状态 | 证据 |
|------|------|------|
| 组合解析（`compositions/*.json`）| ✅ | 4 档预设 + 任意自定义 |
| 源文件清单输出 | ✅ | `--sources-out` |
| 条件编译头输出 | ✅ | `--header-out` → `prot_modconfig.h` |
| 依赖自动补入 | ✅ | `SUBSTRATE`（8 个宿主下限模块）|
| 源文件顺序固定 | ✅ | `SOURCE_ORDER`（15 项，影响 `.text` 布局）|
| **冲突检测** | ⬜ | 由 `modcheck` 承担（未内聚到编排器）|
| **拓扑排序** | ⬜ | 顺序硬编码在 `SOURCE_ORDER` |
| **按策略自动选模块** | ⬜ | 用户必须手写模块列表 |
| **构建计划结构化输出** | ⬜ | 只有文本清单，无带理由的计划 |

**差距**：编排器**只做"翻译"**（JSON → 编译参数），**不做"决策"**。
即：**用户选模块**，而非**用户选策略**。

### 1.2 模块协议 —— 现状 60%

对照"四层协议"，**字段级**实测：

| 协议层 | 实际字段 | 差距 |
|--------|---------|------|
| **阶段** | `phases`（`init`/`scan`/`decide`/`enforce`/`watch`）| ✅ 值域合理，5 个阶段全被使用 |
| **数据 consumes** | **（无）** | ❌ **缺** |
| **数据 produces** | `exports`（语义不同）| ⚠️ `exports` 是"导出符号"，非"产出资源" |
| **数据 modifies** | `modifies_text`（布尔）| ⚠️ **粒度粗**（只有 `.text` 有/无）|
| **效果 effects[]** | `caps` + `verifies_text` | ⚠️ **无独立 effects 数组** |
| **约束 requires** | `deps` | ✅ 有 |
| **约束 conflicts_with** | **（靠推导）** | ❌ **无显式声明** |
| **约束 ordering** | **（`SOURCE_ORDER` 硬编码）** | ❌ **无模块级声明** |
| **资源开销** | `known_limits`（自由文本）| ⚠️ **非结构化** |

**关键差距**：
- ❌ `conflicts_with` 缺 → 现在由 `modcheck` 用 `modifies_text × verifies_text` **隐式推导**（只覆盖 1 类冲突）
- ❌ `ordering` 缺 → `SOURCE_ORDER` 是**全局硬编码列表**，模块无法声明自己的先后约束
- ❌ `consumes`/`produces` 缺 → 无法做**数据流级**冲突检测

### 1.3 去模块化器 —— 现状 60%

| 手段 | 状态 | 实测 |
|------|------|------|
| 节名随机化 | ✅ | 残留仅 `.fptable`（MSVC 默认节，无语义暗示）|
| magic 去自解释 | ✅ | `PROTCRC*` 已消除 |
| 差异扩散（填充统一尺寸）| ✅ | 文件尺寸**完全一致**（229888 = 229888）|
| 特征串加密（检测项名）| ✅ | 19 项**全部消除** |
| 符号擦除 | ✅ | 模块函数名 **0/32** 可见 |
| 函数级间接化 | ✅ | `s_perm` 每构建变 |
| **代码内联/融合** | ⬜ | 未实现 |
| **布局随机化** | ⬜ | 未实现（节顺序固定）|
| **诱饵注入** | ⬜ | 未实现 |
| **元数据零泄露** | 🟡 | 组合名不进产物 ✓；但仍有 634 条可读串 |

### 1.4 ⚠️ 最关键的量化差距：**跨构建差异率仅 0.55%**

**实测**（同组合、随机种子构建两次）：

| 指标 | 实测 | 目标 | 差距 |
|------|------|------|------|
| **差异字节率** | **0.55%**（1256 / 229888）| **>30%** | **差 29.5 个百分点** |
| 差异块数 | 5 / 57（8.8%）| 均匀分布 | 集中（`0x23000` 占 1128/1256）|

**这是路线图中**最重要**的一项**：

> 攻击者拿到**两个构建** → 一次 binary diff → 差异集中在 **5 个 4KB 块**
> → **直接定位全部 per-build 秘密** → 定向分析。
>
> **"每构建变化"是开源方针的唯一强杠杆，而它目前只覆盖 0.55% 的产物。**

### 1.5 跨组合仍可区分（实测）

同种子下 `minimal` vs `full`：

| 项 | 结果 |
|----|------|
| 文件大小 | ✅ **相同**（229888）|
| 节名序列 | ❌ **不同**（`.wsllapv` 位置互换）|
| 节尺寸 | ❌ **3/11 相同**（`.rdata`/`.data`/`.pdata`/`.reloc` 等仍差）|

**含义**：尺寸归一化**消除了总量差异**，但**逐节仍有可区分性**（工具链管理的节无法填充）。

### 1.6 每用户唯一 —— 现状 20%

| 项 | 状态 |
|----|------|
| 每构建随机种子 | ✅ |
| 确定性种子（可复现 I3）| ✅ |
| **用户主密钥** | ❌ **全仓库无此概念**（实测搜索无命中）|
| 模块随机子集选择 | ❌ 未实现（阶段5）|
| 模块顺序随机化 | ❌ 未实现 |

## 3. 路线图（六阶段，每阶段独立可验收）

> **原则**：**不追求快速，保留最大潜力**。
> 每阶段收尾必须：**门禁 14/14 + 文档同步 + 独立验收**。

```
阶段 W1  差异扩散（0.55% → >30%）      ← 最高优先，方针的命脉
阶段 W2  协议形式化（开放规范 + 版本）    ← 生态的地基
阶段 W3  编排器升级（策略 → 计划）        ← "用户选策略不选模块"
阶段 W4  每用户唯一（主密钥派生）         ← 商业模式的支点
阶段 W5  验证框架（可观测性度量）         ← **真正的护城河**
阶段 W6  协议治理（版本化 + 兼容套件）    ← 生态可持续
```

### 阶段 W1：差异扩散（0.55% → >30%）

**为什么最高优先**：这是**完全开源方针的唯一强杠杆**，实测仅 0.55%。

| 步 | 动作 | 验收 |
|----|------|------|
| W1.1 | 扩展填充到**全部可填节**（现只填 `.text`/`.rdata`/`prot*`）| — |
| W1.2 | 填充量**随机化**（不再"补到刚好"，而是补到**目标 + 随机量**）| — |
| W1.3 | 引入**诱饵节**（内容形态与真实节不可区分）| — |
| W1.4 | 节顺序随机化（在合法范围内）| — |
| W1.5 | **量化验收**：两次构建差异率 **>30% 且均匀** | 新增检查脚本 |

**风险**：产物膨胀（已接受）；填充可能被熵分析识别（真实边界，如实记录）。

### 阶段 W2：协议形式化

| 步 | 动作 | 验收 |
|----|------|------|
| W2.1 | 补 `conflicts_with` 字段（显式声明，替代隐式推导）| `modcheck` 用它 |
| W2.2 | 补 `ordering` 字段（模块级先后约束）| 编排器按它排序 |
| W2.3 | 补 `consumes`/`produces`（数据流声明）| 支持数据流冲突检测 |
| W2.4 | 加 `abi_version`（协议版本）| W2.5 |
| W2.5 | 抽出 `docs/MODULE_PROTOCOL_SPEC.md`（**独立于实现的规范**）| 版本号 + 变更日志 |
| W2.6 | 写**兼容性测试套件**（通过即宣称兼容）| 第三方可自测 |

### 阶段 W3：编排器升级

| 步 | 动作 | 验收 |
|----|------|------|
| W3.1 | 用户输入**策略**（强度/性能预算/平台/威胁）| 新 CLI |
| W3.2 | 策略 → 模块集（基于 `caps`/`phases`/`conflicts` 求解）| — |
| W3.3 | 拓扑排序（用 `ordering` 替代 `SOURCE_ORDER` 硬编码）| 顺序仍正确 |
| W3.4 | **构建计划结构化输出**（含"为何选它"）| 可审计 JSON |
| W3.5 | 冲突检测内聚到编排器（复用 `modcheck` 逻辑）| 单一入口 |

### 阶段 W4：每用户唯一

| 步 | 动作 | 验收 |
|----|------|------|
| W4.1 | **用户主密钥**生成（首次运行，加密存储）| — |
| W4.2 | 主密钥 → 派生**每项目/每构建**种子 | 同用户跨项目不同 |
| W4.3 | 种子驱动**模块选择**随机化 | 同策略不同模块集 |
| W4.4 | 种子驱动**模块参数**随机化 | — |
| W4.5 | **量化验收**：跨用户产物相似度 < 阈值 | 检查脚本 |

### 阶段 W5：验证框架（**护城河**）

> **为什么是护城河**：别人可以抄协议、抄模块，但**抄不走"已被验证的实证积累"**。

| 步 | 动作 | 验收 |
|----|------|------|
| W5.1 | **可观测性度量**：跨构建差异率/分布均匀性 | 自动报告 |
| W5.2 | **跨用户相似度**度量 | — |
| W5.3 | **静态识别率**测试（用 strings/节表/导入表能否定位模块）| 负向测试 |
| W5.4 | **破解迁移成本**测试（改一个构建的成果能否用于下一个）| — |
| W5.5 | 集成到门禁（作为**必过项**）| 门禁新增 N 项 |

**关键纪律**（本轮教训）：
> **验证器自身必须被验证**。门禁曾因 PowerShell 数组恒真而 7/13 项失效
> （实测: 必然失败的工具被报 `[ok]`）。**每个新检查器都要有负向测试**。

### 阶段 W6：协议治理

| 步 | 动作 |
|----|------|
| W6.1 | 协议版本化 + 变更流程（重大变更需讨论）|
| W6.2 | 兼容性测试套件发布（第三方可自证兼容）|
| W6.3 | 明确"什么进核心、什么留扩展" |
| W6.4 | 模块质量分级（官方认证/社区验证/实验性）|

## 4. 优先级与依赖

```
W1 差异扩散 ────────────────┐
                            ├──→ W5 验证框架（需 W1 的可度量指标）
W2 协议形式化 ──→ W3 编排器 ─┤
                            │
W4 每用户唯一 ───────────────┘
                            │
                            └──→ W6 协议治理
```

| 优先 | 阶段 | 理由 |
|------|------|------|
| **1** | **W1 差异扩散** | 方针的命脉；实测差距最大（0.55% vs >30%）|
| **2** | **W5 验证框架** | **护城河**；且它是"证明 W1 有效"的前提 |
| 3 | W2 协议形式化 | 生态地基（不阻塞前两项）|
| 4 | W3 编排器升级 | 依赖 W2 |
| 5 | W4 每用户唯一 | 商业模式支点（依赖 W3）|
| 6 | W6 协议治理 | 最后（依赖前五项）|

> **建议：W1 + W5 并行推进。**
> W1 改产物，W5 建度量 —— 两者互补，且 W5 能立即验证 W1 的效果。

## 5. 明确不做（Non-Goals）

| 不做 | 理由 |
|------|------|
| **推倒重来** | 已有 60-70%，重写会丢失实证积累 |
| **追求"不可破解"** | 用户态做不到（白盒密码学结论）|
| **运行时插件式模块化** | 等于给攻击者一张攻击地图（B5 边界）|
| **先做跨平台** | 与"抬高破解成本"方针正交；会分散精力 |
| **协议一次性定稿** | 应版本化演进（W6）|

## 6. 诚实的风险与边界

| 风险 | 说明 |
|------|------|
| **>30% 差异可能不可达** | 填充有上限（工具链管理的节不可填，实测 920 字节差异）→ 若不可达，**如实记录为边界** |
| **填充可能被熵分析识别** | 填充区与代码区熵分布不同（已在计划 §14.5 预判）|
| **动态 dump 仍是瓶颈** | 秘密最终出现在内存（窗口解密有窗口期）|
| **协议表达力 vs 易用性张力** | 太简单检测不出软冲突；太复杂生态起不来 |
| **验证框架自身可能失效** | 本轮已实证（门禁 7/13 曾失效）→ **必须负向测试** |
| **维护者精力** | 开源项目最大的敌人（文档亦已提示）|

## 7. 一句话总结

> **你的构想不是"要做"，而是"已经做了 60-70%"** ——
> 三件套里**工作台、协议、去模块化器**都有实质实现且经实测。
>
> **真正的缺口是三件事**：
> ① **跨构建差异率只有 0.55%**（方针命脉，目标 >30%）
> ② **没有验证框架**（无法证明产出真的不可观测）
> ③ **没有每用户唯一**（无法形成商业支点）
>
> **而其中最重要的不是协议设计，是"可验证性"** ——
> 本轮门禁失效事件恰好证明：**一个会撒谎的验证体系，
> 会让"配置不可观测""去模块化""组合编排"全部无法被证明有效。**
> **能证明自己有效的框架，才是别人抄不走的护城河。**
