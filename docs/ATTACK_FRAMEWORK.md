# 攻击技框架（Attack Framework）— 攻防契约层对称

> **目标**：破 BLUEPRINT §3.4.3 **边界③**
> ——"攻防双侧不同层（**数据层**对称，非**框架层**对称）"。
>
> **状态**：✅ 契约层已建立（`attacks.json` + `attackcheck.py`）
> **日期**：2026-09-23

---

## 1. 问题：什么是"数据层对称"

原文 §3.4.3：

> **攻防双侧不同层** | 攻击工具在 `tools/attacker/`、演练在
> `tests/attack_*.py` | 是**数据层**对称（drills 记录），
> 非**框架层**对称

**实测诊断**（本轮）：

| 机制 | 防御侧 | 攻击侧（改动前）|
|------|--------|---------------|
| 能力注册表 | `modules.json`（13 模块 × 19 字段）| **无** |
| 契约校验 | `modcheck` R1–R19 | **无** |
| 准入自证 | `conformance.py` | **无** |
| 组合/编排 | `compose.py` + 策略求解 | **无**（脚本硬编码）|
| 顺序声明 | `ordering` 字段 | **无** |
| 成熟度 | `maturity`（证据分级）| 部分（drill 记录）|
| 回归门禁 | 18 项 | 仅 `attacks A1-A12` 一项 |

**具体症状**：

| 症状 | 实测 |
|------|------|
| 攻击技**无法被组合** | 5 个 `attack_drill*.py` 各自带 `main()`，共 57 个 `drill_*` 函数 |
| 攻击**不被门禁按能力调用** | 门禁只跑 `tests/attacks.py`，5 个 drill 脚本**都不在门禁里** |
| 新增攻击技**成本不对等** | 模块：写契约 + `conformance` 通过；攻击：**写一个 700 行脚本** |
| `drills/` 记录**无法反向驱动攻击** | `_schema.json` 的 `method`/`prerequisite` 是**描述**，无可执行对应物 |

## 2. 方案：攻击技注册表（`attacks.json`）

### 2.1 与 `drills/` 的关系（**关键区分**）

```
attacks.json    = 攻击技的【契约】 —— "能做什么"
                  可执行入口 + 目标模块 + 分类 + 前置条件
drills/*.json   = 演练的【记录】 —— "做过什么、结果如何"
                  结果 + 证据 + 日期
```

> **前者是能力清单，后者是实验记录。**
> 此前只有后者 —— 所以"攻防对称"只到了数据层。

### 2.2 字段设计（对照 `modules.json`，**务实简化**）

| 字段 | 含义 | 对应防御侧 |
|------|------|-----------|
| `script` / `func` | **可执行入口** | `source` |
| `taxonomy` | 攻击类别（11 类）| `caps` |
| `targets` | 目标模块 | `deps`（反向）|
| `round` | 演练轮次 | —— |
| `evidence` | 演练文档 | `evidence` |
| `prerequisite` | 前置条件 | `known_limits` |
| `code` | 代号（如 `D3-2`）| —— |

### 2.3 实测规模

| 项 | 数量 |
|----|------|
| **攻击技** | **57** |
| 分类法 | 11（**沿用** `drills/_schema.json`，**未新增**）|
| 有 `targets` | **37**（其余 20 条无对应演练记录 —— **如实留空**）|
| 有 `evidence` | **57**（100%）|

**按分类分布**：
```
patch_data            20     memory_dump            5
patch_function_head    7     injection              4
toolchain_abuse        6     symbol_resolution      4
license_forge          6
collection_channel     5
```

## 3. 契约校验（`attackcheck.py`）

### 3.1 规则 A1–A8

| 规则 | 内容 | 级别 |
|------|------|------|
| A1 | 结构（顶层键 + `attacks` 对象）| error |
| A2 | `script` 文件存在 | error |
| **A3** | **`func` 在 script 中真实定义** | error |
| A4 | `taxonomy` 在既有 11 类内 | error |
| A5 | `round` 为 0–99 整数 | error |
| **A6** | **`targets` 必须是真实模块**（在 `modules.json` 中）| error |
| **A7** | **有 `targets` 必须有 `evidence`**（可追溯）| error |
| A8 | 未知字段 -> 警告（前向兼容）| warning |

> **A3 与 A6 是最有价值的两条**：
> A3 防"登记了不存在的攻击技"（文档漂移）；
> A6 把攻防两侧的**模块名空间**绑定 —— 攻击技只能针对真实存在的防御模块。

### 3.2 负向测试

`python tools/attackcheck.py --selftest` -> **7/7 通过**
（A2/A3/A4/A5/A6/A7 逐条用已知违规输入验证；A8 验证"只警告不报错"）。

## 4. 实现中的**两个错误**（我引入的，如实记录）

### 错误 1：**假设**了 drill id 格式

初版按 `drill<N>.<M>` 拼 id 去匹配 `targets` -> **全部 57 条 targets 为空**。

实际格式是 `<前缀>.<代号>`（如 `drill220260825final.D3-2`）。

> **根因**：我**假设**了格式而没先看实际数据 ——
> 违背项目纪律"**测量优先于推测**"。
> 修法：改按**代号**匹配（`D3_2` -> `D3-2`），37/57 匹配成功。

### 错误 2：**假设**了 evidence 文件名

初版按 `ATTACK_DRILL<N>.md` 拼 -> 9 条警告（第 1 轮实际叫
`ATTACK_DRILL.md`，**无数字**）。

> **同类错误**（又一次假设格式）。修法：先扫真实文件清单再匹配。

**教训**：**两个错误同一性质** —— 在"注册表内容"这种**必须如实**的场景下，
我连续两次靠推测而非测量。**注册表的可信度完全取决于它是否如实**，
故这类场景应**强制先扫描、后生成**。

## 5. 收益与诚实边界

### 5.1 收益

| 项 | 改动前 | 改动后 |
|----|--------|--------|
| 攻击技**清单** | 隐含在 5 个脚本里 | **`attacks.json` 可查询** |
| 攻击技**校验** | 无 | **A1–A8 可机器执行** |
| **攻防模块空间绑定** | 无 | **A6 强制攻击技只针对真实模块** |
| **可追溯性** | 部分 | **A7 强制有 targets 必有 evidence** |
| 新增攻击技 | 写脚本（无准入）| 写脚本 + **登记契约 + 过校验** |

### 5.2 诚实边界（**未做到的**）

| 边界 | 说明 |
|------|------|
| **攻击技不可"组合"** | 仍无 `attackkit.py`（对应 `compose.py`）—— 每个 drill 仍是独立函数 |
| **攻击技无"顺序声明"** | 无 `ordering` 对应物（如"先 dump 再 patch"的链式关系）|
| **20 条无 targets** | 这些 drill 无对应演练记录 -> targets 留空（**如实**）|
| **未重写脚本** | 只登记 + 校验；57 个 `drill_*` 函数仍在 5 个脚本里 |
| **攻击侧无 maturity** | 未按证据给攻击技分级（防御侧有 `maturity`）|
| **仍未"框架层完全对称"** | 达成了**契约层**对称；编排层、执行层未做 |
