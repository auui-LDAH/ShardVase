# 防护 vs 扩展性 — 平衡方案

> **问题**：完全开源面向社区后，需要模块协议让模块可替换/升级
> （甚至全部替换仍能运行）；但协议会引入"可被静态发现的结构"，
> 与反逆向保护的初衷冲突。**如何平衡？**
>
> **方法**：先用实测确定"暴露面到底在哪、代价多大"，再据数据设计，
> 而不是凭直觉折中。

---

## 1. 实测：暴露面到底在哪（这是设计的依据）

### 1.1 关键发现 — 符号名**不增加任何暴露**

| 测量 | 结果 |
|------|------|
| 模块导出函数名总数 | 32 |
| **出现在 exe 中的个数** | **0 / 32** ✓ |
| indirect 表内函数名可见数 | **0 / 8** ✓ |

**原因**：C 语言没有元数据 —— 函数名只在编译期用于链接，**不进二进制**
（`/DEBUG:NONE` 已剥离调试目录）。

→ **推论（本方案基石）**：**「符号约定」式协议的开销与暴露 = 0**。
约定"模块必须提供 `prot_<name>_scan`"不会让攻击者多知道任何东西。

### 1.2 对比：什么东西**会**增加暴露

| 元素 | 暴露代价 | 实测 |
|------|----------|------|
| 符号约定（函数名） | **无** | 0/32 可见 |
| 描述符表含**模块名**字符串 | **有** —— 明示模块清单 | 12/13 可见 |
| 描述符表含**函数指针** | **有** —— 直接给出入口地址 | 13 个明文 |
| 描述符表含 `known_limits` 文本 | **有** —— 等于附赠"哪里最弱"清单 | — |
| 描述符表含**位掩码** | **低** —— 数字无语义，需逆向才懂 | — |

### 1.3 描述符的体积代价（次要因素，但需量化）

最小实验（同一程序 + 13 个模拟模块）：

| 策略 | 大小 | `.text` | `.rdata` | 名可见 | vs 基线 |
|------|------|---------|----------|--------|---------|
| S0 基线（无描述符） | 140800 | 85328 | 43098 | 0 | — |
| **S1 全量（名 + 函数指针）** | 142336 | 85648 | 44378 | **12** | **+1536** |
| **S2 元数据（名，无指针）** | 141824 | 85728 | 43738 | **12** | **+1024** |
| S3 仅位掩码（无名） | — | — | — | 0 | 约 +600（推算） |

**关键**：S1 → S2 只省 **512 字节**。**体积不是决定性因素**，
**暴露面才是**。

> 结论：**不该按"体积"折中，应按"暴露什么"折中。**

## 2. 核心洞察：把"协议"与"实现"分离到不同构建

实测数据指向一个明确的解法：

> **协议**（元数据、命名约定、校验规则）与**运行时发现**是可以分开的。
> 前者给开发者与工具，后者给运行期。

由此得到**三层分离**：

```
┌────────────────────────────────────────────────────────────┐
│ L-A 元数据层（开发期/构建期）                                 │
│   modules.json + 描述符（名字/能力/依赖/边界）                 │
│   · 供 modcheck / compose.py / 第三方工具读取                 │
│   · **不进发布产物**（或只进剥离版）                           │
├────────────────────────────────────────────────────────────┤
│ L-B 接口层（编译期）                                         │
│   符号约定：prot_<module>_<verb>                             │
│   · 零运行时开销、零额外暴露（符号名不进二进制）                 │
│   · 这是"可替换性"的真正载体                                  │
├────────────────────────────────────────────────────────────┤
│ L-C 运行期层（发布产物）                                      │
│   入口经既有 indirect 通道（s_fn[] + s_perm 置换）             │
│   · 无明文函数指针表、无模块名清单                             │
│   · 复用已成熟的保护机制                                      │
└────────────────────────────────────────────────────────────┘
```

**这样"可替换"与"不可静态定位"不再矛盾** —— 它们在**不同层**成立。

## 3. 推荐方案：**符号约定 + 构建期描述符 + 运行期间接化**

### 3.1 三层各自承担什么

| 层 | 承担 | 不承担 |
|----|------|--------|
| **L-A 元数据** | 组合校验、依赖检查、覆盖率统计、文档生成 | **运行期发现** |
| **L-B 接口** | 替换性（第三方实现同名符号即可替换）| 运行期枚举 |
| **L-C 运行期** | 调用（经 indirect）| 自省/枚举 |

### 3.2 具体做法

**a) 接口用符号约定，不用函数指针表**

```c
/* 约定（写进 MODULE_GUIDE，由 modcheck 静态检查）：
 *   每个模块必须导出：
 *     prot_status prot_<name>_scan(prot_<name>_report* out);
 *     uint32_t    prot_<name>_suspicious(const prot_<name>_report*);
 *   可选：
 *     prot_status prot_<name>_apply_policy(prot_policy);
 *     prot_status prot_<name>_init(void);
 *     prot_status prot_<name>_fini(void);
 */
```

- **代价**：无（符号名不进二进制）
- **收益**：第三方实现同名函数即可替换 → **满足 L1/L2**
- **弱化点**：无编译期类型检查 → 由 `modcheck` 补（它已有 `FN_DECL` 正则雏形）

**b) 描述符只用于构建期，不嵌入发布产物**

```c
/* include/protect/module.h —— 描述符类型定义（供工具与开发构建）*/
typedef struct prot_module_desc { ... } prot_module_desc;

#ifdef PROT_BUILD_WITH_MODULE_TABLE
extern const prot_module_desc* const g_prot_modules[];  /* 开发构建才有 */
#endif
```

- `modcheck` / `compose.py` 通过 `modules.json` 工作，**不依赖产物中的表**
- 发布构建 `PROT_BUILD_WITH_MODULE_TABLE` 未定义 → 产物**无描述符表**
- **代价**：+1024 字节仅在开发构建；发布构建 **0**
- **收益**：发布产物不含模块清单

**c) 运行期入口仍走既有 `indirect`**

- 已有 `s_fn[] + s_perm` 置换机制，跨构建 seed 变化
- 宿主改为按**能力位**选择调用哪些入口，而非硬编码模块名

**d) 元数据按需剥离（发布构建）**

| 元素 | 开发构建 | 发布构建 |
|------|----------|----------|
| 描述符表 | ✅ 有 | ❌ 无 |
| 模块名字符串 | ✅ | ❌（现有产物本就几乎没有）|
| 能力位 | ✅ | ✅（数字无语义） |
| `known_limits` 文本 | ✅ | ❌ |
| 命名约定 | ✅ | ✅（不进二进制）|

## 4. 这个方案如何满足四个目标

| 目标 | 如何满足 | 验证方式 |
|------|----------|----------|
| **L1 单模块替换** | 第三方实现同名符号 → 链接即替换 | T-L1 |
| **L2 零改动升级** | 模块内部重写，符号不变 | T-L2（断言调用方 diff 为空）|
| **L3 全替换仍运行** | 全部符号按约定实现 → 链接期成立 | T-L3 |
| **防护不削弱** | ①符号名不进二进制 ②发布产物无描述符表 ③入口走 indirect | 静态扫描产物断言 |

### L3 的诚实预判（不变）

`selfcrypt`/`integrity` 这类与 `.text` 布局强耦合的模块，
**桩替换很可能失败** —— 因为 selfcrypt 的 mask 与 hashpatch 的 CRC
按**具体产物**生成。若失败，那就是**真实边界**，应如实记录。

## 5. 与既有机制的复用关系（不重复造）

| 需求 | 已有机制 | 复用方式 |
|------|----------|----------|
| 函数入口间接化 | `indirect.c`（`s_fn[]` + `s_perm`） | 直接复用，协议不另起 |
| 依赖闭包检查 | `modcheck` 已实现 | 扩展它，不改设计 |
| 冲突检查（`.text`/页） | `modcheck` + `selfcrypt_proto` | 已实现，直接适用 |
| 符号声明校验 | `modcheck` 的 `FN_DECL` 正则 | 扩展为"命名约定检查" |
| 组合解析 | `compose.py` | 不变 |
| 边界声明 | `known_limits`（P4 强制） | 不变 |

**新增的只有**：命名约定 + 构建期描述符 + 剥离策略。
**没有推翻任何既有设计。**

## 6. 需要你决策的关键点

| # | 问题 | 我的建议 | 理由 |
|---|------|----------|------|
| **Q6** | 元数据在发布构建中是否保留？ | **剥离描述符表**（开发构建保留） | 实测：仅开发构建 +1024 字节；发布 0 暴露 |
| **Q7** | 接口用符号约定还是函数指针表？ | **符号约定** | 实测：符号名 0/32 可见，暴露为 0 |
| **Q8** | 是否要求第三方模块提供 `known_limits`？ | **要求**，但发布构建剥离文本 | 保持 P4（诚实边界），同时不泄露弱点 |
| **Q9** | 命名规范是否强制统一（`detected` vs `suspicious`）？ | **新模块强制**；现有模块**加别名过渡** | 避免破坏既有 ABI（改名 = 破坏性）|

## 7. 局限（诚实说明）

| 局限 | 说明 |
|------|------|
| 未做**真实攻击演示** | "剥离描述符表即安全"是**静态分析**结论，未构造读取攻击 |
| T-L3 边界是**预判** | 未实测（需实施后验证）|
| 未评估**性能** | 按能力位选择入口 vs 直接调用的开销未测（预计可忽略）|
| S3 数据为**推算** | 测试中 S3 变体因 C 常量表达式问题未跑通，故标"推算"而非实测 |

> 未验证项**不写入结论**，标注"待实施时验证"。

---

## 8. 一句话总结

> **把"协议"与"运行期发现"分开**：
> 接口用**符号约定**（零暴露，实测 0/32 可见），
> 元数据只进**开发构建**（发布构建剥离），
> 入口仍走**既有 indirect**。
> 这样"可替换"与"不可静态定位"在不同层各自成立，**不再矛盾**。
