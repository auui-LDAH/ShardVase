# 内核驱动可行性评估

> **性质**：可行性评估（**只评估，不实施**）。
> **结论**：❌ **建议不做** —— 理由与实探证据见下。
> **日期**：2026-09-21

---

## 0. 结论先行

> **内核驱动不是本项目的"扩展"，而是**一个独立的新项目**。**
> 技术栈零复用、有**签名硬门槛**、收益不确定，且引入蓝屏风险。
> **建议搁置**，并如实记录理由（而非静默丢弃）。

| 维度 | 评估 |
|------|------|
| 技术栈复用 | **0%**（WDK/KMDF vs 用户态 CRT/Win32）|
| 签名门槛 | **硬门槛**：需 EV 证书（年费）+ 微软 attestation/WHQL |
| 收益确定性 | 低（驱动可被更底层绕过）|
| 新增风险 | **蓝屏**（用户态项目无此风险）|
| 与本项目定位 | 冲突（现定位"用户态保护框架"，B5 已公开声明边界）|
| 机会成本 | 高（同投入放 .NET / 在线授权 / 协议回报更高）|

---

## 1. 实探证据（本机，2026-09-21）

### 1.1 驱动开发环境：**不具备**

```
真 WDK 探测（Windows Kits\10\Include\<ver>\km\ntddk.h）:
  ✗ 不存在

Include\10.0.26100.0 下实际只有:
  cppwinrt / shared / ucrt / um / winrt
  ^^ 无 km（内核模式）目录

KMDF 库（WdfDriverEntry.lib）:
  ✗ 未找到

驱动构建工具:
  ✗ stampinf.exe   ✗ inf2cat.exe
```

**唯一的 `ntddk.h` 来自 MinGW（strawberryperl 附带）**：

```
D:\environment\strawberryperl\...\x86_64-w64-mingw32\include\ddk\ntddk.h
```

> **它不能用于生产**：MinGW 缺 WDF 框架与 MSVC 驱动工具链，
> 且其产物**无法通过微软签名**。

### 1.2 签名能力：**不具备**

```
现有证书: build\keys\codesign.pfx（自签）
  -> 仅用于**用户态 exe** 的测试签名

内核驱动需要:
  · EV 代码签名证书（商业 CA，年费）
  · 微软 attestation 签名（或 WHQL 认证）
  -> **自签证书无法加载驱动**（除非启用测试签名模式）

测试签名模式:
  未启用（需管理员权限）
```

> **硬门槛的含义**：即使技术上写出驱动，**没有 EV 证书就无法部署到用户机器**。
> 这不是"开发工作量"能绕过的。

## 2. 技术障碍（为什么说"不是扩展"）

### 2.1 技术栈零复用

| 维度 | 用户态（本项目现状）| 内核态（驱动）|
|------|-------------------|--------------|
| 框架 | Win32 API + CRT | WDK / KMDF / WDM |
| 标准库 | 有（`stdio`/`string`）| **无 CRT**（`ExAllocatePool` 等）|
| 入口 | `main()` | `DriverEntry` |
| 构建 | `cl.exe` | MSBuild + WDK（`.vcxproj` + `.inf`）|
| 调试 | 用户态调试器 | WinDbg + 双机调试（或 VM）|
| 崩溃后果 | 进程退出 | **蓝屏（BSOD）** |

**结论**：本项目的 990 行保护壳、13 个模块、构建链**全部无法复用**。

### 2.2 驱动能做/不能做什么（诚实清单）

| 驱动**能做** | 驱动**不能做** |
|--------------|----------------|
| 阻止 `OpenProcess` 到受保护进程 | ❌ 防 HyperVisor 级（VBS/HVCI 下更难）|
| 隐藏内存区域（反 dump）| ❌ 防 DMA 攻击（需 IOMMU/硬件）|
| 拦截系统调用 | ❌ 防 Bootkit（更早加载）|
| 检测内核级调试器 | ❌ 防物理内存采集 |

> **关键认知**：驱动提升**对抗层级**，但**不提供"绝对安全"** ——
> 总存在更底层的手段。这与本项目"成本非对称"的定位一致，但**层级更高、
> 成本也更高**。

### 2.3 与现有公开边界的关系

本项目已在 `publish/06-诚实边界.md` 公开声明：

> **B5**：用户态无法防内核级攻击 | 驱动级 dump/hook 不在覆盖 |
> 反调试对内核调试器有检测位；深度对抗需驱动（**未提供**）

即：**"不做驱动"是已公开的、有意识的定位选择**，不是疏漏。
做驱动会**改变项目定位**（从"用户态保护框架"变成"含内核组件的方案"），
需要重新处理文档、边界声明、攻击矩阵。

## 3. 若要做：最小可行路径（备选，**不建议现在执行**）

> 以下仅在明确要求时执行。**前置条件不满足则属硬阻塞。**

### 3.1 前置条件（**硬阻塞项**）

| # | 条件 | 现状 |
|---|------|------|
| 1 | 安装 WDK（Windows Driver Kit）| ❌ 未装 |
| 2 | 双机调试环境或 VM（驱动调试必需）| ❓ 未确认 |
| 3 | **EV 代码签名证书**（或至少测试签名能力）| ❌ 无 |
| 4 | 接受蓝屏风险与测试成本 | 需你确认 |

> **第 3 项是商业门槛**。没有它，做到最后也**无法部署**。

### 3.2 最小方案（若条件具备）

```
阶段 K1  环境: 装 WDK + 配双机调试（VM 快照必备）
阶段 K2  最小示例: 一个 KMDF 驱动, 仅做"拒绝 OpenProcess 到目标进程"
阶段 K3  接口: 用户态壳 <-> 驱动通信（IOCTL 设计）
阶段 K4  签名: 测试签名跑通 -> 评估 EV 证书成本
阶段 K5  评估: 对比"引入驱动后的实际防护增益 vs 成本"
```

**预计工作量**：远大于本项目**任何一个已完成阶段**（含 A 阶段历史重写）。

## 4. 建议

### 4.1 **建议不做**（主建议）

| 排序 | 理由 |
|------|------|
| 1 | **签名硬门槛**：无 EV 证书则无法部署 —— 技术之外的门槛 |
| 2 | **技术栈零复用**：相当于从零做新项目 |
| 3 | **收益不确定**：驱动可被 HyperVisor/Bootkit 绕过 |
| 4 | **新增蓝屏风险**：用户态项目无此风险，且蓝屏在生产环境是严重事故 |
| 5 | **改变项目定位**：与 B5 已公开的边界声明冲突 |
| 6 | **机会成本**：同投入放 .NET（**已完成**）、在线时间锚点、跨平台回报更高 |

### 4.2 如果目标是"防 dump"

有**用户态内的替代手段**，成本远低于驱动：

| 手段 | 现状 |
|------|------|
| `ThreadHideFromDebugger` | ✅ 已实现（L3c）|
| 反调试 12 维 | ✅ 已实现 |
| selfcrypt（代码加密）| ✅ 已实现 —— **提高 dump 后理解的成本** |
| 完整性校验（3 段 CRC + watchdog）| ✅ 已实现 |
| VM 自加密 + 外部 blob 装载 | ✅ 已实现（exe 内无 VM 逻辑）|

> **本项目的现有策略是"提高 dump 的**价值衰减**"**（dump 出来也难理解、
> 且每构建变化），而非"阻止 dump"。这是在用户态内**已经做到的上限**。

### 4.3 什么时候该重新考虑驱动？

| 触发条件 | 说明 |
|----------|------|
| 有客户明确要求内核级防护并愿意承担成本 | 商业驱动 |
| 已获得 EV 证书（用于其它产品）| 门槛已跨过 |
| 出现针对本方案的**自动化 dump 工具** | 说明现有层级不足 |

**当前三者均不满足**。

## 6. 一句话总结

> **不建议做内核驱动。** 它是新项目而非扩展，有 EV 证书这一硬门槛，
> 收益可被更底层手段绕过，并引入蓝屏风险 —— 而本项目在用户态内
> **已实现"提高 dump 成本与价值衰减"的策略**，这正是 B5 公开声明的边界。
> 若目标是"防 dump"，现有手段已是用户态内的合理上限。
