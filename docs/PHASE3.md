# 阶段 III — 服务端执行计划 (PHASE3)

> 版本：2026-08-19 v1 · 归属：BUSINESS 阶段 III（可选）· 前置：阶段 I 完成 +
> **决策点 D2 拍板"是否做服务端"**。若选择"离线优先"（推荐），本文件降级为
> 规格预留，仅保留 §3 API 与 §5 吊销流程（离线已有，OPS §5）。
> 技术基础：`docs/OPS.md` §6（在线 API 规格初稿）、`src/revoke.c`（离线吊销，
> 在线 provider 的挂载点）、`tools/vmenc.py`（RSA 签名核心，服务端复用）。
> 执行前提：极低规格 VPS（单核 512MB）+ 域名 + TLS 证书。

## 1. 目标与范围

- **目标**：把"离线黑名单 + 本地降级"扩展为**可选在线能力**：集中签发中心、
  在线验证/吊销、审计日志，同时**保持离线优先语义**（服务不可达 ≠ 锁死客户）。
- **范围**：
  1. 签发中心（复用 vmenc 签名核心 + 审计日志）
  2. 在线验证 API（`/v1/check`）
  3. 吊销 API（管理面 `/v1/revoke`）
  4. 客户端 online provider（revoke.c 扩展）
- **不在范围**：客户门户/计费（M3.3 可裁剪）；多租户（每客户独立构建已隔离）。

## 2. 架构

```
[客户端 demo.exe]  --TLS-->  [签发中心/VPS: nginx + Python 服务]
  |                               |-- 验证: 公钥验签 (离线能力, 服务端不参与)
  |-- 在线 check (可选): serial+mid+tier+build
  |-- 离线回退: revoke.blob 黑名单 (OPS §5, 始终有效)
```

- **核心原则**：**验证永远在本地完成**（RSA 公钥 + VM 门控）。服务端只回答
  "这个授权是否仍有效/未吊销"。即使服务端被攻破，攻击者也只能制造"撤销"，
  不能"授权"（无私钥）。
- 服务端**不持有**签发私钥（签发在离线签发机，OPS §3 分级）；服务端只持
  吊销名单 + 可选公钥。

## 3. API 规格（v1）

### 3.1 在线验证（客户端 → 服务端）
```
GET /v1/check?serial=<s>&mid=<hex>&tier=<n>&build=<ver>
-> 200 {"status":"ok",    "tier":1, "expires":"2027-01-01"}
-> 200 {"status":"revoked","reason":"refund"}
-> 404 {"status":"invalid"}
```
- 幂等、只读、无状态；TLS 必选；限流（IP/序列号维度，如 60 req/min）。
- 响应可选加 **HMAC/签名**（服务端密钥），防中间人篡改"ok→revoked"以外的
  方向——离线语义下非必需，M3.2 评估。

### 3.2 吊销管理（管理面）
```
POST /v1/revoke  {serial, tier?, reason}     # 需管理令牌 (API key)
GET  /v1/revoke/status?serial=...            # 查询
```
- 每次吊销：写审计日志（append-only）+ 触发黑名单版本号 +1（与离线渠道同步，
  见 OPS §5）。

### 3.3 错误与降级约定
- 客户端任何网络/5xx/超时 → **回退本地黑名单 + 本地告警**（不锁死）。
- 超时：3s 连接 + 3s 读取；失败即降级（不做重试风暴）。

## 4. 客户端集成（src/revoke.c 扩展）

- `prot_revoke_check` 增加 **online provider** 钩子（默认 offline，编译期开关
  `PROT_ONLINE_ENABLED`）：
  ```
  启动时: 本地黑名单检查 (现逻辑) -> 未命中且启用在线 -> GET /v1/check
  在线返回 revoked -> 按 strict/warn 策略处理 (与离线一致)
  在线不可达 -> 静默降级 (本地黑名单已是最新版本时无需告警)
  ```
- 配置：`--check-url <https://...>`（缺省不启用在线，保持现状）。
- **验收**：e2e 扩展 T20/T21（本地 mock server）：
  - T20 在线 revoked → 0xB1E4（strict）
  - T21 在线不可达 → 降级通过（离线优先不锁死）

## 5. 部署步骤（本地 mock → VPS）

### M3.1 本地 mock（可完全离线开发+测试）
- `tools/mock_server.py`（新，stdlib http.server）：实现 §3 API，内存/JSON 存储。
- e2e 集成：起 mock → 跑 demo → 断言；随 verify 可选执行。
- **验收**：T20/T21 全绿；mock 与真实服务端行为一致（同一 handler 代码）。

### M3.2 VPS 上线（需要：VPS + 域名 + TLS）
- nginx 反代 + `python` 服务（复用 mock handler）+ certbot TLS。
- 部署检查：`curl /v1/check` 各分支；限流生效；日志轮转。
- 真机（阶段 II 的 P2-6）扩展：在线吊销真机行为。
- **验收**：线上 API 与 mock 行为一致；离线降级在断网/服务停时验证通过。

### M3.3 客户门户（可裁剪）
- 简单 Web（签发申请/吊销查询），复用管理 API；可后置。
- **验收**：按需。

## 6. 密钥与安全

| 项 | 说明 |
|----|------|
| 签发私钥 | 留在离线签发机（OPS §3），服务端无 |
| 在线响应签名（可选） | 服务端独立密钥；客户端内置公钥；仅防响应篡改 |
| 管理 API key | 环境变量/文件注入，不入库 |
| 审计日志 | append-only；含时间/操作/对象/来源 IP |
| TLS | certbot 自动续期；禁用 TLS1.0/1.1 |

## 8. 风险与决策点

| 项 | 说明 | 决策 |
|----|------|------|
| 在线依赖风险 | 客户断网/服务故障被误锁 | **离线优先已架构保证**（§2/§3.3） |
| 运营成本 | VPS + 域名 + TLS 维护 | D2 拍板；M3.3 可裁剪 |
| 服务端被攻破 | 只能撤销不能授权（无私钥） | 已架构隔离 |
| 响应篡改 | 中间人改 ok↔revoked | M3.2 评估响应签名 |
| 数据合规 | serial/mid 上传 | EULA 明示（OPS §7 已含）；可做匿名化（哈希） |

> **建议**：若为个人/小规模商业，推荐**保持离线优先**——阶段 III 仅实现
> M3.1（mock + 客户端 provider + T20/T21），作为"未来接线上"的完整可测底座；
> M3.2/M3.3 在有客户/收入后启动。对应 BUSINESS D2。
