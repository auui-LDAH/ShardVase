## 1. 这条战略主张什么

原始构想的四个要点（保留原意）：

1. **破解不可避免** —— 与其阻止破解，不如经营「破解之后」；
2. **密钥是消耗品** —— 持续轮换，使既有破解成果失效；
3. **全开源「阳谋」** —— 机制公开，消灭攻击者的信息优势；
4. **杠杆** —— 防御方低成本轮换，迫使攻击方高成本重来。

原始论证的关键句：

> 「当攻击者花了两周时间，终于逆向了你的核心算法，你突然通过模块化组件轮换了
> 一次密钥，攻击者之前投入的 14 天直接归零。」

**本文的核心工作就是检验这一句。** 结论：该论证对**一类**攻击成立，对**另一类**
不成立——而项目自己的 `ATTACK_DRILL7` 已经给出了反例。

## 2. 关键修正：轮换密钥挡不住什么

### 2.1 实证反例（`docs/ATTACK_DRILL7.md` §3.2）

| 步骤 | 攻击动作 | 结果 |
|------|----------|------|
| 2 | 写判定布尔 `is_debugger_attached=0` | 写入成功，**盾仍检测**（下轮 scan 重算覆盖） |
| 3 | patch `prot_antidebug_scan` 函数头 | 写入成功，盾仍检测 |
| 4 | **patch `prot_antidebug_detected` 函数头** (`31 C0 C3`) | ✅ **盾失效：DETECTED → clean（持续）** |

第 4 步只写了 **3 字节**：`xor eax,eax; ret`。攻击者没有解密任何东西，
**没有用到任何密钥**。

### 2.2 为什么密钥轮换对它无效

必须区分两种攻击面：

| 攻击面 | 形态 | 密钥轮换是否有效 |
|--------|------|------------------|
| **数据面** | VM 字节码密文、blob、字符串表 | ✅ 有效——轮换即让抓到的密文失效 |
| **代码面** | 宿主机器码的函数头、分支、判定点 | ❌ **完全无效**——攻击者 patch 的是指令，不是密钥 |

`src/vm_rekey.c` 保护的是**数据面**（`cc'[i] = cc[i] ^ B(key) ^ B(new)`）。
它对「patch 函数头」这类代码面攻击的杠杆系数是 **0**。

### 2.3 结论

> **「轮换密钥 ⇒ 攻击者投入归零」是不成立的。**
> 正确的表述是：**轮换密钥让「解密型攻击」的成果过期，但不影响「补丁型攻击」。**

而 `ATTACK_DRILL7` 恰好证明：在用户态保护里，**补丁型攻击是成本最低的那一类**
（3 字节写入 vs 两周逆向）。

## 3. 仓库已有资产盘点（这条战略不是从零开始）

原始构想以为是新方向，实际上**大半机件已存在**：

| 构想要素 | 仓库现状 | 位置 |
|----------|----------|------|
| 密钥当消耗品、持续轮换 | ✅ 已实现：装载后差分流重编码，每次运行密钥域不同 | `src/vm_rekey.c`（S2） |
| 轮换使成果失效 | ✅ 实证两次运行密钥域不同（`0x...a24899` vs `0x...c3c07683`） | `docs/HANDOVER.md` §2.5 |
| 缩小明文窗口（等效于"让 dump 过期"） | ✅ D2b 调用级解密（Release 默认） | `src/selfcrypt.c` |
| 会话级不可复用 | ✅ N5 服务端下发会话期望值，patch 只对当次会话有效 | `demo/main.c`、`tools/mock_server.py` |
| 开源「阳谋」 | ✅ 已有能力文档、诚实边界、攻击侧工具链、公开攻防记录 | `publish/`、`tools/attacker/` |
| 成本量化 | ⚠️ **部分**：`THREATMODEL.md` §3 有中位工时矩阵，但未做杠杆比 | `docs/THREATMODEL.md` |
| 模块化（去中心组合） | ❌ **空白**：当前是单体套件 + SDK 骨架，非可组合原语 | `prot_sdk/` |
| 攻击成本计算器 | ❌ **空白** | — |
| 跨构建布局随机化（针对代码面） | ⚠️ 部分：opcode 置换/语义变异是**数据面**；代码面仅 `/OPT:ICF` | `build.ps1` |

**结论**：数据面的消耗战已基本建成；**代码面的消耗战是真空**，
而代码面恰是最廉价的攻击路径。

## 4. 真正的杠杆表（基于实证，非推测）

按「攻击者成本 / 防御者成本」的实际杠杆排序。标注依据来源。

| # | 攻击手法 | 防御动作 | 杠杆 | 依据 |
|---|----------|----------|------|------|
| 1 | 改判定布尔 / 改 result | **周期重算**（看门狗 ±40% 抖动） | **高** | ✅ DRILL7 步骤 2、DRILL2 P4-2 实证有效 |
| 2 | 内存 dump 取明文 | **D2b 调用级解密**缩小窗口 | **高** | ✅ 已落地，窗口从常驻降为调用周期 |
| 3 | 单镜像还原后跨版本复用 | **S2 rekey + 构建指纹变异** | **高** | ✅ 实证密钥域每次不同 |
| 4 | 重放 / 固定期望值 patch | **N5 会话级期望值** | **高** | ✅ 已落地，e2e T25/T26 |
| 5 | **patch 函数头（3 字节）** | **跨构建代码布局随机化** | ✅ **已落地（实测）** | ✅ **DRILL8（2026-09-29）**: 两次构建 **95.2% 同名符号 RVA 变化**（`prot_` 函数 **63/63 = 100%**）-> 攻击者 v1 的定位对 v2 失效（**成果无保质期**）|
| 6 | 换公钥自签 | ACL 只读部署 | 中（部署约束） | DRILL6 `L3_pubkey_swap` BREACHED |
| 7 | 回拨系统时钟 | 在线时间锚点 | 低（未做） | DRILL6 `L4_clock_rollback` BREACHED |
| 8 | 暂停 watchdog 线程 | 多线程交叉校验 | 中 | DRILL3 `C3` BLOCKED |
| 9 | 符号表定位（MAP/PDB） | RELEASE 无符号 | 中 | DRILL7 §3.3 边界 |
| 10 | **patch 判定点 + 重算段 CRC** | **判定点序言快照（`check_guards`）** | **高（第二道独立成立）** | ✅ **DRILL9（2026-10-02）**: 出厂 EXIT 策略下重算 `.text` CRC 并写回（`2087216295 -> 3467459129`）-> 仍被 **`0xBAD`** 终止；对照用例 D 反证重算确实生效；CONTINUE 下 `g_guard_hits=4` 佐证。⚠️ **但守卫检查器自身在 `.protxec`（不在 CRC 覆盖内）-> 可先 patch 它再 patch 守卫（用例 H，见 DRILL9 §5）** |

> **杠杆的真相**：真正在起作用的不是「轮换密钥」这一条，而是
> **「让攻击成果有保质期」这一族**——周期重算、会话值、运行期 rekey、跨构建变异。
> 密钥轮换只是这一族里的一员，且只覆盖数据面。

## 5. 杠杆比：可量化的部分

原始构想缺一个数字。基于现有演练记录，可先做**粗粒度**估算（标注为估算，非实测）：

| 维度 | 攻击方 | 防御方 |
|------|--------|--------|
| 定位判定点（有 MAP） | 分钟级 | — |
| 绕过单层检测（ScyllaHide 类） | 小时级 | — |
| 还原 1 个 VM 语义 | 天级 | — |
| 通用还原器 | 周～月级 | — |
| **3 字节函数头 patch** | **分钟级** | 跨构建布局随机化 ≈ **构建时自动，0 人工** |
| 制造合法授权（keygen） | **私钥不可得** | 签发一次 ≈ 秒级 |

**两个真正的断点**：

1. **密码学断点**（`THREATMODEL.md` §4）——无私钥造不出合法授权。
   这是唯一信息论上成立的"断源"，与密钥轮换无关。
2. **自动化断点**——若防御方的"重来"是**构建管线自动完成**（0 人工），
   而攻击方的"重来"需要**人工逆向**，则杠杆比为正。

> **杠杆比公式（建议纳入成本计算器）**：
> ```
> L = (攻击方重来成本 · 攻击方技能门槛) / (防御方重来成本 + 用户迁移成本)
> ```
> 分母里的**用户迁移成本**是关键约束——见 §6.1。

## 6. 工程暗礁（用仓库实证校准原始构想）

原始记录提了三点，逐条对照项目实际：

### 6.1 轮换不能伤及合法用户（记录的第 3 点）

原始构想：「如果每次密钥轮换都需要用户重新下载整个软件包……会被用户抛弃。」

**仓库现状**：S2 的做法是**聪明的**——`prot_vm_rekey` 只改内存，**blob 文件与
RSA 签名不变**（`src/vm_rekey.c` 头注释明确）。这是"运行期轮换"而非"分发期轮换"，
用户迁移成本 ≈ 0。

**但这也是它的局限**：运行期轮换只对抗「同一进程内两次 dump 对比」，
不对抗「抓一次样本离线慢慢啃」。

> ⚠️ **附带技术观察**：`rekey` 的熵源是
> `GetTickCount64() ^ (pid << 32) ^ (uintptr_t)bp`（`demo/main.c:642`）。
> 三个分量都可用，但真实熵有限（tick 分辨率 + 小 pid + 单个指针）。
> 「每次运行不同」成立；「密钥域足够大」未经量化，建议补测量。

### 6.2 模块间兼容性（记录的第 1 点）

原始构想担心「A 轮换了密钥，B 还在用旧密钥校验」。

**仓库现状**：该项目**用相反的策略规避了它**——不是"提供原语让用户拼"，
而是"提供一个已验证的整体 + 细粒度构建期开关"：

```
build.ps1 的开关面：-Config / -D2b / -NoD2b / -Drill /
                    -ExtraSelfCrypt / -SeedsFile / -SkipSign / -SkipSmoke /
                    -MachineId / -VcVars / -Python / -RecordSeeds
prot_sdk/wizard      : key_mode = new | pub（二选一）+ lite 精简单开关
```

**这是一个被验证过的设计选择**，而非缺陷。`examples/tool_demo/README.md:77` 明确写：
保护重点是"授权校验 + 1-2 个核心功能开关"，**整个工具搬进 VM 成本高、性能损失大，不建议**。

> 所以「去中心模块化」与现有「整体 + 开关」之间需要一次明确取舍——
> 见 §7 的决策点。

### 6.3 组合脆弱性

原始构想担心「模块 A 和 B 单独安全，组合起来失败」。

**仓库已实证过这个风险**：S1 的 `revoke` 加密因**与 `main` 同页**
（VirtualProtect 页粒度自伤）被**永久排除**（`docs/DEFENSE_DEEPEN_PLAN.md`）。
这正是"组合导致脆弱"的真实案例——**两个各自正确的机制，放在一起就崩**。

**结论**：模块化会放大此类风险。当前"整体验证 + 3 连建门槛
（`mask_stability_test.ps1`）"的纪律，正是为了捕捉组合性问题而建立的。

## 7. 落点：三档可选路线

按「验证成本递增」排列。**建议先做 A，用数据决定是否进入 B/C。**

### 路线 A —— 成本计算器（最小、最接近变现）

把已有 9 轮演练 + 3 组矩阵数据，量化成对外可用的成本证据。

- 输入：`docs/ATTACK_DRILL*.md`、`archive/attack-drill-*.json`
- 输出：`tools/cost_model.py` + 一份「攻击成本估算表」
- 价值：**直接可对外**（`publish/` 已有 7 篇，这是第 8 篇的素材）
- 成本：低；无需改核心代码
- 风险：需诚实标注"估算"与"实测"的边界，避免过度承诺

### 路线 B —— 补齐代码面消耗战（**机制已落地，见 DRILL8**）

> **状态更新（2026-09-29, DRILL8）**: "让函数头 patch 不再一次成功"的
> **核心机制（构建期布局随机化）已落地并实测** —— 两次构建 **95.2% 同名符号 RVA 变化**（`prot_` 函数 100%）。
> 下表机制 **1（顺序/填充随机化）已实现**；机制 **2/3/4 仍未做**。

候选机制（按可行性）：

| 机制 | 说明 | 难度 |
|------|------|------|
| 构建期函数顺序/填充随机化 | 已有 `/OPT:ICF` 与种子体系，可扩展到 `.text` 布局 | 低 |
| 关键判定点的冗余副本 + 交叉校验 | 攻击者需 patch 多处 | 中 |
| 判定逻辑下沉进 VM（`// @vmcalc` 已有） | 把 `prot_antidebug_detected` 的聚合搬进 VM | 中 |
| 周期重算扩展到更多判定点 | DRILL7 已证重算有效，扩大覆盖面 | 低 |

- 价值：**可实测的能力增量**，且能写进 `ATTACK_DRILL8` 作为新证据
- 成本：中；需过 3 连建门槛 + 回归全绿
- 风险：S1 已证明"布局敏感"是本项目的**已知雷区**（`revoke` 同页、
  `.text` CRC 原子性缺陷），布局随机化会直接踩进来

### 路线 C —— 去中心模块化框架（原始构想，最重）

把套件拆成可组合原语 + 通信契约 + 参考拼装图。

- 价值：理念最完整，传播潜力最大
- 成本：**高**——需要重新设计模块契约，且会放大 §6.3 的组合脆弱性
- 风险：**这是研究项目，不是变现路径**（原始记录自己也提示了财务压力）
- 建议：**不作为当前主线**；待路线 A 产出的成本数据能证明其必要性后再评估

## 9. ✅ 技术债**已清除**（R1 复核 2026-09-29）

> **原文（2026-08-30）**："`src/selfcrypt.c` 的 `[SCDBG]` 日志**无编译开关**，
> 在 Release 产物中同样输出"

**实测复核**（`tools/docclaim_check.py` 的 `scdbg-*` 断言）：

```
① 机制: `src/selfcrypt.c:101` 已有 `#ifdef PROT_SELFCRYPT_DEBUG`
        -> 未定义时 `SC_DBG(...)` 展开为 `((void)0)`（**完全编译掉**）
② 产物: build/demo.exe (327680 B) 与 build/demo_linux (108128 B)
        经二进制搜索 **均不含** `[SCDBG]` / `PRE-VP` / `CRC got` 任一字符串
=> **该技术债已清除**
```

**且已入库门禁（第 26 项「文档断言一致性」）** -> 若将来有人把它改回
"无条件输出"，**门禁立刻红**（不再依赖人工发现）。

> 下面保留原文的**泄漏内容分析** —— 它说明了**为什么要守护**这条断言。

```
[SCDBG] idx=N decrypt=1
[SCDBG]   rva=0x... len=... k=0x... crc=0x... dst=...
[SCDBG]   PRE-VP / VP-OK / XOR-OK / FLUSH-OK / RX-OK
[SCDBG]   CRC got=0x... want=0x...
```

泄漏内容：每个加密函数的 **RVA、长度、密钥流种子 `k`、明文 CRC 期望值、
解密后地址**。这等于给攻击者一个完整的"解密+校验 oracle"。

> `PROT_RELEASE_CONCEAL` 只遮蔽了 `prot_status` 错误码，**未覆盖 SCDBG**。

**这与本战略直接相关**：任何"消耗战"叙事的前提是攻击者需要付出成本；
而 SCDBG 把成本结构中的**最关键一环（定位与验证）免费送给攻击者**。
在关闭它之前，讨论杠杆比是没有意义的。

## 10. 诚实边界（本战略不主张什么）

对齐 `publish/06-诚实边界.md` 的既有纪律：

1. **不主张"不可破解"**——本战略的全部内容是成本博弈，不是绝对安全；
2. **不主张密钥轮换是万灵药**——§2 已证明它只覆盖数据面；
3. **不主张模块化一定更好**——§6 列出其组合脆弱性与维护负担；
4. **成本估算标注为估算**——现有数据支持"量级"，不支持"精确倍数"；
5. **不承诺防内核级攻击**——用户态边界不变（同上，边界 B5）。
