## 1. 已实测的可行性依据（计划的事实基础）

### 1.1 .NET 门 —— 实测通过 ✅

```
构建 protgate.dll（薄封装保护库）:
  ✓ DLL 112128 字节
  dumpbin /exports: prot_gate_check, prot_gate_init, prot_gate_version
  动态加载（模拟 P/Invoke 路径）: gate ver=1 check=0
```

**结论**：`.def` 文件导出 + 薄封装即可给出稳定 C ABI，托管侧 P/Invoke 可用。

### 1.2 GUI 双击授权 —— 障碍已定位 ✅

```
壳从 stdin 读序列号（app_main.c:709-711）:
    printf("请输入序列号:");
    fgets(mem.serial, sizeof(mem.serial), stdin);

实测: GUI 产物 + --license-file + 无 stdin -> rc=1, license: 0
```

**结论**：需要新增"无 stdin 的序列号来源"，是**受支持的扩展点**。

### 1.3 UWP —— 真实技术障碍 ⚠️

| 约束 | 影响 |
|------|------|
| `VirtualAlloc` RWX 受限 | **直接冲击 selfcrypt 解密期**（需可写+可执行页）|
| `ReadProcessMemory`/`OpenProcess` 受限 | antidebug/dbiguard 多项检测失效 |
| 全局 hook 受限 | indirect/反 hook 能力受限 |
| 文件系统沙箱 | vm.blob 装载路径受限 |

**结论**：**不是"工作量"问题，是沙箱模型与本项目技术前提冲突**。
诚实做法：出**评估文档**说明"哪些能、哪些不能"，不承诺完整支持。

### 1.4 内核驱动 —— 是新项目 ❌

| 障碍 | 说明 |
|------|------|
| 技术栈完全不同 | WDK/KMDF、无 CRT/stdout、独立构建链；**现有代码零复用** |
| **签名硬门槛** | 现代 Windows 需 EV 证书 + WHQL/attestation；否则无法加载（测试模式除外）|
| 能力边界 | 驱动能反 dump，但也被更底层（HyperVisor/Bootkit）绕过 |
| 与 B5 一致 | 现有文档已声明"深度对抗需驱动（未提供）" |

**结论**：**建议不做**。理由见 §4.3（含"若坚持要做"的最小方案）。

## 3. 阶段 1：GUI 双击运行授权

### 3.1 目标（可验收）

```
GUI 程序**双击运行**（无 stdin、无命令行参数）能完成授权判定。
```

### 3.2 设计：新增"序列号来源"抽象，而非改壳逻辑

**问题根源**：壳把"序列号来源"硬编码为 stdin。

**方案**：在业务层与壳之间加一个**可选的序列号提供者**，壳按优先级取用：

```c
/* prot_shell.h — 新增（可选实现，不实现则行为与现在完全一致） */
typedef enum prot_serial_source {
    PROT_SERIAL_FROM_STDIN  = 0,  /* 默认: 现有行为 */
    PROT_SERIAL_FROM_FILE   = 1,  /* 从授权文件读 */
    PROT_SERIAL_FROM_CALLBACK = 2, /* 业务层提供（GUI 弹对话框）*/
} prot_serial_source;

/* 业务层可实现此函数（弱符号/可选注册）:
 *   GUI 程序在此弹对话框收集序列号。
 *   壳在需要序列号时调用；返回 0 = 成功。
 *   未提供 -> 壳回退到 stdin（行为不变）。 */
typedef int (*prot_serial_provider_fn)(char* buf, size_t cap);
void prot_shell_set_serial_provider(prot_serial_provider_fn fn);
```

**为什么这样设计**：

| 好处 | 说明 |
|------|------|
| **向后兼容** | 不实现的工程行为**完全不变**（现有 14 项门禁不受影响）|
| 解耦 | 壳不知道 GUI/控制台/文件，只知道"要序列号" |
| 与既有设计一致 | 类似项目已有的 `set_watchdog_callback` 回调模式 |
| 不破坏"零改动"约定 | 壳只加一个可选钩子，不是分支复制 |

### 3.3 步骤

| 步 | 动作 | 验收 |
|----|------|------|
| 1.1 | `prot_shell.h` 加 provider 声明；`app_main.c` 加注册函数 + 序列号获取改为"优先 provider，回退 stdin" | C 构建通过 |
| 1.2 | `business_stub_gui.c` 实现 GUI 对话框收集序列号（`DialogBoxIndirectParam` 或自绘窗口）| 编译过 `/W4 /WX` |
| 1.3 | 实测：GUI 产物**双击等效**运行（无 stdin、无参）| `license: 1` |
| 1.4 | 实测：**不带 provider** 的构建行为不变 | 门禁 14/14 |
| 1.5 | 更新 `GUI_GUIDE.md` §3（限制 → 已解决）| 文档一致 |
| 1.6 | 提交 | 门禁 14/14 |

### 3.4 风险

| 风险 | 应对 |
|------|------|
| 改壳可能影响 .text 布局 | 门禁含 selfcrypt/页面检查；若异常则回滚 |

### 4.4 关于"是否纳入门禁"

**建议：单独脚本 + 可选门禁项**，理由：
- `dotnet` 不是本项目必需依赖（当前门禁仅需 MSVC + Python）
- 若强制纳入，会让**没有 .NET SDK 的环境无法跑门禁**（违反现有低依赖设计）
- 做法：`tools/build_dotnet_gate.ps1` 检测到 `dotnet` 才运行，否则 SKIP 并**明确打印 SKIP 原因**（不是静默跳过 —— P3 教训）

## 8. 阶段 6：内核驱动可行性评估（**建议不做**）

### 8.1 我的建议与理由

> **建议：不做内核驱动。** 这是**唯一我主动建议搁置**的一项。

| 理由 | 说明 |
|------|------|
| **不是扩展而是新项目** | WDK/KMDF 技术栈，现有代码**零复用**；相当于从零做一个新项目 |
| **签名硬门槛** | 现代 Windows 需 EV 证书（年费）+ WHQL/attestation；**无证书则产品无法部署** |
| **收益不确定** | 驱动能反 dump，但也被 HyperVisor/Bootkit 绕过；且**引入蓝屏风险**（用户态项目无此风险）|
| **与既有定位冲突** | 项目自我定位是"用户态保护框架"，B5 已公开声明边界。做驱动会改变定位 |
| **机会成本** | 同样的投入放在 .NET / 协议 / 在线授权上，收益明显更高 |

### 8.2 交付物（仍要产出，用于记录决策）

> **待创建**：`docs/KERNEL_DRIVER_ASSESSMENT.md`

内容：
- 技术障碍清单（WDK/签名/无 CRT/独立构建）
- 需要什么（EV 证书、KMDF 经验、测试签名环境）
- 驱动能做/不能做的诚实清单
- **结论：建议不做** + 若未来要做的**最小可行起点**（如仅做"反 dump"单一功能）

### 8.3 若你坚持要做（备选路径）

我会给出**最小方案**（而非完整实现）：
```
阶段 6'（仅在明确要求时执行）
  1. 环境确认: 是否有 WDK + 测试签名能力（没有则无法验证，属硬阻塞）
  2. 最小示例: 一个能做"拒绝 OpenProcess 到目标进程"的 KMDF 驱动
  3. 与现有项目的**接口**设计（用户态壳如何与驱动通信）
  4. 明确标注: 未签名 -> 仅测试模式可用
```

**但我不建议现在做** —— 理由如上表。
