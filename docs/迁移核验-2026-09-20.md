- 实测两种步长对比：

  | 步长 | P1 | P2 |

  | 20B（现行代码） | FAIL `fn 1 out of range` | FAIL `meta != mask` |

- 影响：`tools/release_check.ps1` 的 Check #10（protchain P1-P6）必然失败。
- 修法：`i * 20` → `i * 24`（两处）。
- 注：这与 `docs/DEFENSE_DEEPEN_PLAN.md` 记录的「整晚 TAMPERED 谜团」
  （20B→24B 步长错位）**同源** —— 当时修了 `integrity.c`，测试没跟上。

### 3.2 `prot_sdk/skeleton/strings.txt` 缺 3 项 —— SDK 接入阻断

## 4. 重要纠错：smoke 失败是核验环境造成的，**不是项目缺陷**

> 核验过程中曾误判为「`build.ps1` 的 `2>&1` + `ErrorActionPreference=Stop` 导致
> smoke 必然失败，改 `2>$null` 即可」。**该判断错误，在此更正并留档。**

- 改 `2>$null` **依然抛异常、exit 仍为 1**；完全去掉 `2>&1` 也仍是 exit 1。
- 真正根因：**PowerShell 管道给原生进程的 stdin 前置了 UTF-8 BOM（`EF BB BF`）**，
  而 demo 只剥 `\r\n`、不剥 BOM → 序列号变 23 字节 → 校验失败 exit 1：

  ```
  PS  管道: efbbbf 44454d4f...0d0a  -> exit 1
  cmd 管道:        44454d4f...0d0a  -> exit 0
  ```

- BOM 来源：**核验所用 harness 会话的 `chcp 65001`**（`Console.InputEncoding=utf-8`）。
- 决定性对照：

  | 环境 | Console In/Out | smoke |
  |------|----------------|-------|
  | harness 会话（chcp 65001） | utf-8 | **exit 1** |
  | 默认中文 Windows（chcp 936） | gb2312 | **exit 0** ✅ |

- **结论：`build.ps1` 在正常环境（含 CI/windows-latest）完全正常。**

修法候选实测（7 种，目标 exit=0）：

| 候选 | 结果 |
|------|------|
| 原始 `2>&1`（EAP=Stop） | ✗ 抛 `RemoteException` |
| 去掉 `2>&1` | ✗ exit 1 |
| `$OutputEncoding` 设为无 BOM | ✗ exit 1（非控制项） |
| `ProcessStartInfo` + `StandardInputEncoding` | ✗ 该属性在 .NET Framework 4.x 不存在 |
| `cmd /c` 管道 | ✓ exit 0 |
| `cmd /c` + stdin 文件重定向 | ✓ exit 0 |
| `Start-Process -RedirectStandardInput <file>` | ✓ exit 0 |
| `[Console]::InputEncoding = ASCII` | ✓ exit 0 |

> 附带确认：`build.ps1:378` 的 `2>&1` + `EAP=Stop` 确实会在 **stderr 非空时**
> 抛 `RemoteException` —— 这是真实脆弱点，但仅为表象，**不是 exit=1 的根因**。

## 5. 核验方法学的两条纠正

1. **`U+FFFD` 检测不足以判定双重编码**：双重编码产出合法字符（含 PUA），
   必须用「GBK↔UTF-8 往返」或 PUA 扫描。曾据此误判
   「`demo/main.c` 正常、仅 `app_main.c` 乱码」——实际两者均损坏（80 / 82 行）。
2. **`.obj` 残留不会弄脏 `release_check` Check #1**：`.obj` 已被 `.gitignore` 忽略，
   `git status --porcelain` 输出 0 行。曾据此误判「11/11 跑不出来」。

另核实：`tools/release_check.ps1` 实际含 **10 个 `Check`**（用 `^Check` 锚定会漏掉缩进的），
对外口径「11/11」的第 11 项来自 `codesign.pfx` 存在时签名块的 `pass++`。

### 6.4 ⚠️ 已评估并放弃的方案：整文件重建

**结论**：骨架一致性**不足以**作为语义等价证明。整文件重建风险收益比不划算，

## 8. 遗留项处理（提交 `dc4d15b`）

三项遗留经逐项核实：**1 项是真实缺陷、1 项是误判、1 项确认保留**。

### 8.1 ✅ `build.ps1` 冒烟自检 —— **真实缺陷，已修**

> ⚠️ 此处更正 §4 的结论。§4 认定「smoke 失败是核验环境造成的，非项目缺陷」——
> **该结论不完整**。BOM 只是成因之一，还存在第二个独立缺陷。

**实证**：在 **chcp 936 与 chcp 65001 两种环境**下裸跑 `build.ps1`
（不带 `-SkipSmoke`）**均失败**：

```
build: smoke try 1~3 launch failed: [SCDBG] idx=0 decrypt=1
build FAILED: smoke test (integrity/blob/license chain)
```

**两个独立成因**：

| # | 成因 | 说明 |
|---|------|------|
| a | `EAP=Stop` 下 stderr 重定向被包装成终止性异常 | `2>&1` **与** `2>$null` 均然 → 直接跳入 `catch`，`$LASTEXITCODE` 永不参与判定。`demo.exe` 恒向 stderr 输出 `[SCDBG]` 日志，故**必然触发** |
| b | PS 管道向原生 stdin 写 BOM | 序列号多 3 字节 → 校验失败 exit 1 |

**修法**：改用 `cmd /c`，以 stdin 文件重定向喂序列号、stdout 落文件、stderr 丢弃。
实测两种环境均 **PASS**（`build: smoke test PASS` / exit 0）。

> **为何长期未暴露**：所有自动门禁（`release_check.ps1`、`repro_check.ps1`、
> `ci.yml`）都带 `-SkipSmoke` —— 属「门禁绕过路径掩盖真实缺陷」。
> 现 `Release 构建` 项在门禁内已可裸跑通过。

**附带修复**：`build.ps1` 的 UTF-8 BOM 被编辑工具静默去除，已恢复
（PS 5.1 无 BOM 时按 GBK 解析，会破坏中文字符串，见提交 `72b75eb`）。

### 8.2 ❌ `app_main.c` 的 `#include "../prot_shell.h"` —— **误判，非缺陷**

§7 曾列为「潜在脆弱点」。**实测证伪**：用最小工程验证 include 解析路径，
结果解析到 `FROM_PROJ`（工程根的那份），而非父目录。

机制：MSVC 对 `"..."` 形式 include 的**回退搜索**会把每个 `/I` 目录与字面路径
拼接——`<proj>\gen` + `../prot_shell.h` 经路径规范化得 `<proj>\prot_shell.h`，
恰好命中工程根的头文件。移除 `/I gen` 才会失败（`C1083`）。

**结论**：这是依赖 `/I gen` 的隐式解析，虽不直观但**工作正常**，未做改动。

### 8.3 ⏸ 纯注释乱码 —— 确认保留

112 + 112 行，全部位于注释内（原判「1 处非注释」实为字符串字面量，见下），
不可逆，不影响编译与运行。**保留**，理由：

- 逐行重建已证伪（§6.4：骨架一致仍会改变语义）
- 改动面达 224 行、集中在两个最核心文件，风险显著高于收益
- 对产物零影响（已由全量回归与门禁验证）

### 8.4 ✅ 附带发现并修复：最后一处乱码字符串字面量

`prot_sdk/skeleton/app_main.c:740`：

```c
printf("鍚婇攢鍒楄〃鎹熷潖锛屽凡蹇界暐 (revoke.blob)\n");   /* 修复前 */
printf("吊销列表损坏，已忽略 (revoke.blob)\n");              /* 修复后 */
```

**此前漏检原因**：初版扫描的注释剥离用正则 `/\*.*?\*/`，无法正确处理
「字符串内出现 `/*`」等情形，导致该行被误判为注释。
改用**带字符串状态机的注释剥离器**后重新全库扫描，结果：
**62 个 `.c/.h` 文件中乱码字面量 = 0**。

> 教训：检测工具的准确性本身需要被验证。「已知的字符串字面量已修」
> 不等于「不存在其它字符串字面量」。
