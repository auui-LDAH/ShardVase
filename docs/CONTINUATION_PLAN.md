## 2. Q1 源码 mojibake —— 已探明的完整范围

### 2.1 判定算法（**确定性、已自校准**，Q1 的判据就是这个）

> ⚠️ **v1 算法（`gbk` 比例法）已被实测推翻** —— 它漏检 73% 的坏行。
> 下面先记 v1 原文（保留为"教训"），再给**现行权威算法 v5**。

**v1（❌ 已废弃，2026-10-01 实测推翻）**:
```python
CJK = r'[\u4e00-\u9fff]'
# 对一行 l：含 CJK 且 l.encode('gbk') 成功时
fx = l.encode('gbk').decode('utf-8', 'replace')
坏行  <=>  CJK数(fx) > 0  且  CJK数 / (CJK数 + '\ufffd'数) > 0.5
```
**v1 的致命缺陷（实测证据）**: 遇到 UDA/PUA 字（`U+E76C..U+E863`，CP936 有映射
而 Python `gbk` codec 无）时 `l.encode('gbk')` **抛 `UnicodeEncodeError`** ——
被 `except` 吞掉后**整行静默放过**。这不是理论风险: 权威表 23940 条双字节里
**81 条**落在这个区，且真实文件里确实出现（`app_main.c` 的 `\ue787` /
`demo/main.c` 的 `\ue046` 等）。

**v4（✅ 权威，Q1 用）—— 把行按 CP936 语义重建，再看还原文本**:
```python
# tools/mojibake.py（唯一权威实现，不得在其他脚本里重写判据）
txt = decode_cp936(line.encode('utf-8'))     # 精确复刻 .NET CP936 解码
坏行 <=> 最长连续 CJK 串(len) >= 2             # MIN_RUN = 2
```
`decode_cp936` 的关键语义（**这就是"吃标点/吃换行"的机制**）:
- ASCII 原样；`0x80` → `U+20AC`（欧元符，CP936 特有）
- 合法双字节 → 查 81 条 UDA 修正表，再回落 `gb18030`
- **非法双字节对 → 固定吞 2 字节并吐 `?`**（吞掉的可能是换行 → k 行合并）
- 尾部孤立字节 → 吞 1 字节吐 `?`

**v5（✅ 现行权威，Q2 补上）—— v4 + 单字符盲区兜底**:
```python
坏行 <=> run>=2  或  行内含 `_BLIND` 表里的"损坏像"字符
```
**v4 的盲区是结构性的，不是阈值问题**: 原文是 CJK 时其 UTF-8 占 **3 字节**，
CP936 每次只喂 2 字节 → 还原出的 CJK **必然成串**，故 `run>=2` 对"原文是 CJK"
完备。但原文若是**非 CJK 的 >127 字符**（如 `§` U+00A7，UTF-8 `C2 A7` 只 2 字节），
其错解**本身是 CJK**（`§` → U+6402），还原后 `run=0` → 被放过。实测全库
128 种非 CJK 字符里**恰好 16 种**如此 → **盲区有限可枚举**。

**`_BLIND` 表怎么来（不是人工拍脑袋）**: 判据 `freq_img == freq_cand and
freq_orig >= 5` —— 「像字符的**每一次**出现都落在硬验证候选行上」即
**从未观察到合法用法**（见到一次合法用法即拒绝）。16 对里只采纳 **3** 对
（见 `build/_q2_blind_table.txt`）。被拒的典型是 `实`→U+02B5（`实` 合法出现
**3856** 次）—— 它同时说明**纯编码规则无法区分**："正确中文 `写`"与"损坏的 `§`"
在字节层面完全同构（全库 71 条硬验证候选里 67 条其实是正确文本）。
⚠️ **诚实边界**: 这是一张**按本仓库语料校准的白名单**，可证伪、可重算，
但**换语料必须重算**；门禁每次运行都会重算频次并验证该表仍成立。

**v5 的量化**（v1/v2/v4 用同一独立标注集；v5 的增量由 Q2 实测给出）:

### 2.3 修复工艺: **求解而非人工判读**（v1 的"必须人工判读"已被推翻）

**v1 的判断**是「有损行必须人工判读（34 行）」。**实测推翻了它** ——
216 行里 **170 行字节已损**，逐条人工判读既不可靠也不可复现。实际采用的工艺是
**三源求解 + 硬验证**（`tools/fix_mojibake.py`）:

| 证据源 | 强度 | 说明 |
|--------|------|------|
| `CAND` | 最强 | 人工判读候选，**必须** `M.damage(候选) == 当前坏行` 才接受；不成立直接 `SystemExit` |
| `RESTORE` | 强 | 判据自行还原，`M.damage(还原文本) == 当前坏行` |
| `REF` | 强 | 行池里有**同一坏行**的干净原文（同文件历史修订 / mirror / 全工作区） |
| `SPLIT` | 强 | **k 行合并展开**（`MAXLEN = 6`）: 损坏吃掉了换行，原 k 行被挤成 1 行 |

**为什么必须支持 k 行合并**: 非法双字节对**固定吞 2 字节**，吞掉的若是换行
（`0A`），相邻两行就并成一行。实测最多 **4 行合并**，模式分布
`app_main.c {1:56, 2:13, 3:7, 4:1, 0:1}` / `demo/main.c {1:53, 2:15, 3:5, 4:1}`。
只试"行对"会剩 **15 行未决**（全部是 3 行合并）。
**写回必须倒序**（`sorted(items, key=lambda x: -x[0])`）—— k 行展开会改变后续行号。
写回前双断言: `ls[ln-1] == 当前坏行` 且 `M.is_bad(...)` 仍成立；BOM 按原样保留。

**人工判读只剩 1 条**: `prot_sdk/skeleton/app_main.c:496`
（`g_vmblob_path` 的注释）—— 行池里确实没有原文（四组合全试 0 命中，
`g_vmblob_path` / `尾部业务装载` / `函数级 blob` 在全部 `*.md` 中 grep 无匹配），
故走 `CAND` 路径硬验证写入。

**修复效果**: 6 文件坏行 **216 → 0**（复扫实测），全库白名单外坏行 **0**。

## 4. Q2 缺陷⑤复核（`usage` 显示字面宏名）—— ✅ **已定证并修复**

**结论: 缺陷⑤ 真实存在，且根因与本节 v1 的猜测不同。**

**v1 的错误判断（已推翻）**: 本节原写「当前状态：**未能复现**」，并推测 16 处
`usage` 用的 `APP_EXE_NAME_STR`「**已经过宏展开**」。**这是错的** —— 静态读代码
时看到 `PROT_APP_STR_` 就以为展开发生了，忽略了 C 标准对 `#` 的特别规定。

**真正的根因**: `#` 的**操作数不做宏展开**，故一级字符串化得到的是**参数符号本身**:
```c
#define PROT_APP_STR_(x) #x
#define APP_EXE_NAME_STR PROT_APP_STR_(APP_EXE_NAME)   /* ← 一级: 得到 "APP_EXE_NAME" */
```
修法 = 经典**两级间接**（`PROT_APP_STR(x)` 先展开参数，再交给 `#`）。

**定证证据链**（三条独立证据，非静态推断）:
1. `cl` 编译实测（`build/_q2_str.c` + `.bat`）: 一级恒为 `"S1X"`（参数名），
   二级在 `-D` 带引号/带空格两种情形下都正确展开（含 `"my app"`）。
2. `tools/skeleton_check.py --keep` 重建骨架 → 扫 `build/SkelCheck.exe`:
   8 条 usage 串全为 `usage: SkelCheck ...`；`literal macro name present? False`。
3. `.map` 里 `??_C@_0KD@…@usage?3?5APP_EXE_NAME?5…` → 字面量确实曾入二进制。
