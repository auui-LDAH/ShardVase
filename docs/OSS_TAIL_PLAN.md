### 阶段 C：许可证头（④）—— 合规 + 实测【计划已改进】

> **改进依据（2026-09-21 实测）**：原 C5 判据"产物字节一致"被质疑是否可达
> （此前为"描述符结构体"证明过它会改变产物）。本次先做判定实验，
> 结论是**对注释成立**，故判据保留，但补上了成立依据与更严的验证项。

#### C.0 先决判定：注释是否影响产物？（已实测）

最小实验：真实源文件 + SPDX 注释头，用项目同等参数编译链接
（`/O2 /W4 /std:c11 /utf-8 /GS- /Brepro` + `/OPT:REF /OPT:ICF /DEBUG:NONE`）：

| 指标 | 无注释 | 有注释头 | 差异 |
|------|--------|----------|------|
| 文件大小 | 140800 | 140800 | **0** |
| `.text` | 85456 | 85456 | **0** |
| `.rdata` | 43098 | 43098 | **0** |
| `.data` | 7136 | 7136 | **0** |
| **SHA-256** | `4c359eaa…` | `4c359eaa…` | **完全相同** ✓ |

**结论**：注释**逐字节零影响** —— 符合 C 标准翻译阶段 3（注释替换为空格）。
故 C5 判据"产物字节一致"**对本阶段成立**（与"加描述符结构体"不同，
后者必然改变 `.text`/`.rdata` —— 那次实测为 +1536 字节）。

#### C.1 勘查出的三个真实风险（已核实）

| # | 风险 | 实测情况 | 应对 |
|---|------|----------|------|
| **R1** | `src/crc32.c` 首行是 `#pragma code_seg(".protxec")` | 注释插在其前**不影响** pragma 位置，但需实测确认节名仍为 `.protxec` | C3 单独验证该文件**编译后的节名** |
| **R2** | Python 文件含 BOM / shebang / coding | **38 个 py 文件：1 含 BOM、27 含 shebang、32 含 coding** | 插入须跳过 shebang/coding；**写入时保留 BOM** |
| **R3** | `__LINE__`/`__FILE__`/`assert` 会因注释改变行号 | **全仓库命中 0** ✓ | 无需特殊处理（已核实） |

#### C.2 执行步骤（改进版）

| 步 | 动作 | 验证 |
|----|------|------|
| C1 | 记录基线：`demo.exe` **SHA-256**（不只字节数）+ 加密函数数 + 门禁 | 存档备比 |
| C2 | **先修工具**：`add_license_headers.py` 支持保留 BOM、跳过 shebang/coding、对含前置 `#pragma` 的文件插在其后 | 工具自测 + `--dry-run` |
| C3 | `--apply` 插入（预计 69 文件） | 报告实际改动数 |
| C4 | **单独验证 `src/crc32.c`**：编译后检查节名仍为 `.protxec` | 用 dumpbin 或 PE 解析 |
| C5 | 完整构建 `build.ps1` | DONE |
| C6 | **对比 C1 基线**：SHA-256 一致 + 加密函数数一致 | 逐字节 |
| C7 | 门禁 **14/14** | release_check |
| C8 | Python 文件语法自检（`py_compile` 全部） | 38 个文件 |
| C9 | 若 C6 出现差异 → `git checkout` 回滚并重新评估 | — |

#### C.3 与原计划的差异（改进了什么）

| 原计划 | 改进后 | 理由 |
|--------|--------|------|
| C1 只记"字节数" | 记 **SHA-256** | 字节数相同不等于内容相同（描述符实验已证明：大小可被节对齐吸收） |
| 无 C.0 判定 | **先做判定实验** | 避免"C5 判据本身不可达"的风险（该风险真实存在过） |
| C3 直接验证 crc32.c | **C2 先修工具**再插入 | 工具当前**不保留 BOM**（R2 实测），会破坏那 1 个带 BOM 的 py 文件 |
| 无 Python 语法自检 | 新增 **C8** | 插入位置错误会破坏 shebang/coding，需独立验证 |
| 未量化风险 | **R1/R2/R3 实测列表** | "必须实测确认"要具体到可执行的检查项 |

#### C.4 为什么这一阶段仍需单列

这是**本轮唯一"改源码文件"的操作**，而本项目对 `.text` 布局敏感
（**P2 教训**：`revoke` 因与 `main` 同页导致自永久排除）。

虽然 C.0 判定实验表明注释零影响，但：

- 那是在**最小程序**上验证的，真实项目有 15 个编译单元 + selfcrypt 加密段
- `.text` 布局变化会改变**加密段与 `main` 的页关系** → 可能触发页冲突跳过
- C5 的 SHA-256 对比是**最强的等价性证明**，成本却很低

> **判据之所以能这么严，是因为 C.0 已证明注释零影响。**
> 若 C0 判定为"有影响"，C6 就应改为行为等价（e2e+attacks 全绿）。
