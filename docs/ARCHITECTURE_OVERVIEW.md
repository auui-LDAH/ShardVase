## 1. 现状架构（三层 + 一道门）

```
┌─────────────────────────────────────────────────────────────────┐
│ 业务层（你的代码）                                                │
│   prot_business_main(ctx)   ← 唯一契约入口                        │
│   授权门通过后才被调用；ctx 只读（serial/machine_id/tier/expires） │
└───────────────────────────┬─────────────────────────────────────┘
                            │ ★ 唯一语义 choke point
┌───────────────────────────▼─────────────────────────────────────┐
│ 框架层（保护装配）                                                │
│   app_main.c（990 行）—— 编排、生命周期、策略执行                  │
│   indirect.c —— 函数级间接化（s_fn[] + s_perm 置换）              │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 模块层（13 个模块 × 12 字段契约）                                 │
│   检测类: antidebug dbiguard vmdetect                            │
│   校验类: license hostid revoke blob integrity                   │
│   隐藏类: selfcrypt strcrypt vm indirect syscall                 │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 原语层: crc32（不注册为模块，公共设施）                            │
└─────────────────────────────────────────────────────────────────┘
```

**构建期还有一条链**：`compositions/*.json` → `compose.py` → `prot_modconfig.h` + 源文件列表 → `selfcrypt_proto` / `hashpatch`（按**本次产物**生成掩码与 CRC）。

**关键设计事实（实测）**：

| 事实 | 数值 |
|------|------|
| 模块数 | 13 |
| 模块间显式依赖 | **4 / 13**（`antidebug→syscall`、`blob→license,vm`、`integrity→antidebug,selfcrypt`、`revoke→license`）|
| 宿主调用点 | **36 处，涉及 9 个模块** |
| `indirect` 槽位 | **4 个**（`s_fn[]` + `s_perm=[1,2,0,3]`，均 `const`）|

## 2. 「框架被替换」能到什么程度？—— 必须分两类看

这是你问题②的核心。**答案是"分两类，一类可以，一类不行"**，不能笼统说"强适应"。

### 2.1 ✅ 可替换（构建期契约明确）

| 可替换的东西 | 为什么可以 |
|--------------|-----------|
| **业务层** | 契约只有一个函数 `prot_business_main(ctx)` |
| **检测类模块** | 操作对象是"环境"（输入→报告），与产物无关 |
| **校验类模块** | 操作对象是"数据/签名"（输入→判定），与产物无关 |
| **授权链** | RSA 验签逻辑平台无关（已有 `license_auth_common.c` 跨平台基础）|
| **组合取舍** | 实测：4 档预设 + **任意自定义组合**均可构建运行 |

### 2.2 ❌ 不可替换（与产物强耦合）

| 不可替换的 | 原因 |
|-----------|------|
| **selfcrypt** | 必须按**本次产物的 `.text` 布局**生成掩码；换产物即失效 |
| **hashpatch / integrity** | CRC 按**本次产物**烧录；且与 selfcrypt 有页冲突约束 |
| **`indirect` 表** | `s_perm` 随构建 seed 变化（防跨构建复用 patch）|
| **宿主调用点** | 36 处硬引用（虽由 `#ifdef` 包裹，但仍是编译期绑定）|

### 2.3 结构性限制：框架的"替换单元"是**编译期 `#ifdef`**

实测：**13 模块 / 32 导出 / 平均 2.5；无 `register` 钩子**。

**含义**：加模块要改宿主源码（`app_main.c` + `business_stub.c` 各加 `#ifdef` 段），
**不能像 DLL 那样动态插拔**。

**这是当前的真实边界**：编译期可组合 ✅ / 运行期插件化 ⬜。

### 2.4 那么"完全替换框架"可行吗？

**不可行，且不应追求。** 理由：

> 框架的**价值**恰恰在于"与产物强耦合的那部分"（selfcrypt/hashpatch/页布局管理）。
> 把这些抽成可替换的，等于把保护强度交给第三方实现 —— 与"高防护"目标矛盾。

**正确的可替换边界**：
```
可替换: 业务层 + 检测类 + 校验类 + 授权链 + 组合取舍   （5 类）
不可替换: 自加密/完整性/间接化/宿主调用点              （4 类，且应有意固定）
```

## 3. 模块协议与接口（现行规定）

### 3.1 契约字段（12 个，来自 `modules.json`）

| 类别 | 字段 | 作用 |
|------|------|------|
| 身份 | `source` `header` `exports` | 源码/头/导出符号 |
| 能力 | `caps` `phases` | 能力位（detect/prevent/conceal/verify/respond）与生命周期阶段 |
| 依赖 | `deps` | **具名模块依赖**（4 个模块有）|
| **资源约束（P2）** | `page_align` `modifies_text` `verifies_text` `needs_writable_dir` | 防止组合踩 `.text` 布局雷 |
| **诚实边界（P4）** | `known_limits` | **13/13 全模块已声明**，共 32 条 |
| 证据 | `evidence` | drill 记录（覆盖率 13/13）|

### 3.2 接口形态（现行）

```c
/* 每个模块导出（以 antidebug 为例） */

uint32_t    prot_antidebug_detected(const prot_antidebug_report* r);
prot_status prot_antidebug_apply_policy(prot_policy p);   /* 可选 */
```

|------|------|

## 4. 【核心】暴露面控制 —— 如何避免被溯源与破解？

**这是你问题④，也是整个设计最关键的部分。**

### 4.1 方法论：**按"类型"而非"数量"管理威胁**

模块有 13 个，但**威胁面只有 6 类**。框架封装其中 4 类：

| # | 威胁面 | 框架如何封装 | 效果 |
|---|--------|-------------|------|
| **1** | 接口形态暴露（函数指针表）| **用编译期符号，不用函数指针** | 实测 `0/32` 可见 |
| **2** | 表结构暴露（`indirect` / 掩码 / CRC）| `s_perm` 随构建 seed 变化 + 掩码按产物生成 | 跨构建不可复用 |
| **3** | 命名/元数据暴露 | `#DEBUG:NONE`，无反射元数据 | 符号不进二进制 |
| **4** | 检测语义暴露（"在检测什么"）| 反调试 12 维**分散**在各处，不集中判定 | 无单点可读 |
| **5** | ⚠️ **授权逻辑本体** | **由 VM 执行**（`license_gate.vasm` 等）| **不可静态封装** |
| **6** | ⚠️ **业务逻辑本体** | 业务是你写的，框架管不了 | **不可静态封装** |

> **第 5、6 类是不可封装的** —— 它们就是"要被保护的东西"本身。
> 框架能做的是**提高理解成本**（VM + 自加密 + 随机化），不是"不暴露"。

### 4.2 六道防线（按"暴露 → 溯源 → 破解"的链条逐环阻断）

```
攻击者视角的链条:   找到入口 → 理解结构 → 定位关键 → 改写 → 复用
                      ↑          ↑          ↑        ↑       ↑
防线:               ①符号不落地 ②指针不集中 ③判定不单点 ④完整性 ⑤每构建变化
                                                             ⑥成本选择
```

| 防线 | 机制 | 实测依据 |
|------|------|----------|
| **① 符号不落地** | C 无元数据 + `/DEBUG:NONE` | **0/32** 模块函数名可见 |
| **② 指针不集中** | 入口经 `indirect`（`s_fn[]` + `s_perm` 置换）| 表内函数名 **0/8** 可见；`s_perm` 随 seed 变 |
| **③ 判定不单点** | 授权判定在 VM 内完成（`mem.result` 由 VM#4 逐位 AND）| 无单一 patch 点 |
| **④ 完整性覆盖** | 3 段 CRC（`.text`/`.rdata`/`.pdata`）+ watchdog 周期复查 | 改一处即被检测 |
| **⑤ 每构建变化** | 期望值随机化 + 引擎语义变异 + `s_perm` 变化 | 跨构建**不可批量 patch** |
| **⑥ 成本选择** | 攻击成本天级~周级 vs 防护成本一次性 | 见 `THREATMODEL.md` §3 矩阵 |

### 4.3 最关键的洞察：**"能被 patch" 不等于 "能被复用"**

实测的攻击成本矩阵（`THREATMODEL.md` §3）：

| 攻击者 | 成本 | 结果 |
|--------|------|------|
| 脚本级 | 中 | 被完整性杀掉 |
| 中级（IDA/DBI 全还原）| **天级** | **成功，但不通用** |
| 高级（通用还原器）| **周+** | 需按构建适配 |
| 泄漏型批量使用 | 即时 | **各构建指纹互异，不能批量 patch** |

> **这是本架构对"破解"的核心回答**：
> 不追求"不可还原"（用户态做不到），而是让**还原成果无法跨构建复用** ——
> 攻击者每遇到一个新版本都要重做。

### 4.4 ⚠️ 但必须指出：**协议化本身会削弱防线①②**

如果你引入"**统一的模块描述符 + 函数指针表 + 标准 ABI**"（§10 草案的原始设想），
会**重新引入**已被消除的暴露面：

| 引入的东西 | 后果 |
|-----------|------|
| 明文函数指针表 | 攻击者**读一张表 = 拿到全部模块入口**（抵消 `indirect`）|
| 模块名字符串 | 实测：使 **12/13 模块名可见**（暴露清单）|
| `known_limits` 文本 | 等于附赠"**哪里最弱**"的清单（12 条）|
| 统一 ABI | 一次理解 = 攻击**所有**部署 |

**这正是评审报告发现的"硬错误 2"**，也是平衡方案要解决的核心矛盾。

### 4.5 平衡方案：**把"协议"与"运行期发现"分离**

```
L-A 元数据层（开发/构建期）: 描述符 → **不进发布产物**
L-B 接口层（编译期）:        符号约定 → 零开销零暴露（实测 0/32）
L-C 运行期层（发布产物）:    入口走既有 indirect → 无明文指针表
```

**四项已决策**（`MODULE_PROTOCOL_DECISIONS.md`）：

| # | 决定 | 效果 |
|---|------|------|
| Q6 | **剥离描述符表**（开发构建保留）| 发布 0 暴露 |
| Q7 | **符号约定**（非函数指针表）| 实测暴露为 0 |
| Q8 | 要求 `known_limits`，**发布剥离文本** | 保 P4 又不泄露弱点 |
| Q9 | 新模块强制命名，**现有不改名** | 不破坏 ABI |

## 5. 【必须直说】完全开源与"藏内核"策略冲突

你的构想是"完全开源"，但仓库既有的 `docs/GITHUB_PLAN.md` 写着：

| 内容 | 公开? | 理由（原文）|
|------|-------|------------|
| 演示二进制 + 评估授权流程 | ✅ | "可下载、可自己破解试试——最强的说服力" |
| **保护内核源码（vm/selfcrypt/间接表等）** | ❌ | **"公开=直接武装破解者，且违反商业利益"** |
| prot_sdk 向导/骨架 | ⚠️ 部分 | 文档公开；骨架在"注册评估后获取"或订阅制内 |

并且该文档把"**无内核/工具代码混入**"列为发布前检查的**红线**。

### 5.1 这是真实的策略冲突，不是措辞问题

| 若**完全开源**（含 vm/selfcrypt/indirect）| 若**保留内核不开源** |
|---|---|
| ✅ 社区可审计、可贡献、更易建立信任 | ✅ 保留"理解成本"这一核心杠杆 |
| ❌ **"跨构建不可复用"的杠杆被削弱**： | ✅ 与既有红线一致 |
| 　攻击者能直接读 VM 指令语义、掩码生成算法 | ❌ 社区无法完整审计保护链 |
| 　"通用还原器"的研发成本大幅下降 | ❌ 与"完全开源"诉求冲突 |
| 　**每构建变化**仍在，但**理解成本**归零 | |

> **关键技术判断**：
> 防线 ⑤（每构建变化）**不依赖源码保密** —— 它靠随机化，公开源码也仍有效。
> 但防线 ④⑥ 中的"**理解成本**"**高度依赖源码不公开**。

### 5.2 三个可选立场（需你决策）

| 选项 | 做法 | 后果 |
|------|------|------|
| **S1 完全开源** | 全部公开（含 VM 引擎、selfcrypt、indirect）| 最大化透明与社区；**接受理解成本归零**，只剩"每构建变化"作为杠杆 |
| **S2 框架开源 + 内核闭源** | 开源框架/协议/工具/文档；`vm`/`selfcrypt`/`indirect` 以**二进制 + 接口**提供 | 与既有红线一致；社区可扩展模块，但核心保护不公开 |
| **S3 双轨** | 开源**限功能版**（如仅 `minimal` 组合的完整源码）+ 商业版含完整内核 | 兼顾；但维护两套（违反单一事实源）|

**我的倾向：S2**。理由：
1. 与仓库既有红线一致（不需要推翻已决策）
2. **协议与接口本就设计成"零暴露"** —— 开源它们**不削弱保护**（实测 0/32）
3. 真正的杠杆（VM 语义、掩码算法）保留，符合"成本非对称"战略
4. 社区仍能：加模块、审协议、用工具、读文档、跑测试

> 但 **S1 也并非不可行** —— 若你的目标是"以完全透明换取社区信任与采用"，
> 那是一个**有意识的战略取舍**（接受保护强度下降）。
> 这必须由你决定，我不能替你选。

## 6. 对"强适应性与功能"的最终评估

| 维度 | 评估 | 依据 |
|------|------|------|
| **组合适应性** | ✅ **强** | 4 档预设 + 任意自定义组合，实测均可构建运行 |
| **模块可替换** | 🟡 **分类别** | 检测/校验/业务可换；自加密/完整性/间接化**有意不可换** |
| **协议稳定性** | 🟡 **设计完成，未实施** | Q6-Q9 已决策；实施计划 6a-6g 待执行 |
| **跨平台** | ❌ **未做** | Linux 零适配；Android 仅"宿主编译通过"（无 NDK）|
| **运行期插件化** | ❌ **未实现** | 无 ABI，是编译期 `#ifdef` |
| **暴露面控制** | ✅ **强（实测）** | 符号 0/32、指针表 0/8、每构建变化 |
| **抗破解（成本）** | ✅ **中上** | 天级~周级；**跨构建不可复用**是核心杠杆 |

### 一句话

> **框架在"组合取舍"与"暴露面控制"上已经很强且可实证；
> 在"运行期插件化"与"跨平台"上是真空白；
> 而"完全开源"会削弱它的核心杠杆 —— 这是必须由你拍板的战略取舍。**
