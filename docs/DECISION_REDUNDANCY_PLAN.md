### 1.2 DRILL7 的**边界条件**（决定 R3.2 的范围）

```
原文 L93 : "函数头 patch 可被完整性检测捕获 | 本项目 demo 的 CRC 覆盖 .text
            —— **注意：本次 test_target 无完整性校验**，真实 demo 会有 watch"
原文 L100: 待做第 4 条 "与完整性校验对抗：patch 后需同时处理 CRC 重算
            （hashpatch 思路）"
```

=> **DRILL7 的"盾失效"是在无完整性校验的目标上取得的**。
**真实 demo 的 `.text` CRC 覆盖它** —— 所以真实攻击链是:
```
patch 判定函数头  ->  触发 .text CRC 失配  ->  必须**同时重算 CRC**
（hashpatch 思路；本仓库已有 `tools/hashpatch.py`，攻击者可复用同一知识）
```
**R3.2 必须针对这条完整链**，而非 DRILL7 的简化版。

```c
iat_snapshot_init();                       /* 启动时快照 */
...
for (i = 0; i < g_iat_snap_len; i++)
```

### 2.2 做什么

**实施结果（与设计的差异，逐条如实记录）**：

- **副本数量 3 个（r2/r3/r4）**，实现形态刻意互异以免被 `/OPT:ICF` 折叠：
  `r2` = 展开式顺序 OR；`r3` = 状态机但**逆序**遍历、状态编号不同；
  `r4` = 归约式 `(acc | (0u - acc)) >> 31`（无分支）。三个副本各绑一个**专属立即数**
  （`PROT_AD_R2_SALT 0x5A17C3E9u` / `R3 0x1B873593u` / `R4 0x9E3779B9u`）——
  **`PROT_BUILD_SALT` 是全局同值，做不到让副本互异**（`prot_noise.h:59`）。
- **聚合器** = `prot_antidebug_detected_multi`（`src/antidebug.c:686-705`），
  **非短路**逐入口位或：`hit |= f(rep);` 连续 4 次而非 `||` —— 短路会让后续副本永不执行，
  攻击者只需让先执行的那个返回 0 即跳过其余副本，冗余归零。
- **"不同位置"的实现方式与设计不同**：设计写"位置差异由构建期 seed 决定（复用 R3.1）"，
  实际**没有**让 `solve` 随机化副本布局 —— 三个副本是源文件里各自独立的函数，
  地址由链接器布局决定且被 `/OPT:ICF` 判定过（见下）。seed 随机化留作后续。
- **宿主调用点已全部切换**到 `prot_antidebug_detected_multi`，共 6 处：
  `src/antidebug.c:549`（`prot_antidebug_apply_policy` 内）/ `src/integrity.c:217`（A5 复查）/
  `demo/main.c` 3 处 / `prot_sdk/skeleton/app_main.c` 3 处 /
  `examples/tool_demo/main.c:261` / `prot_sdk/dotnet/Native/gate.c:64`。
- **守卫快照一并登记**：`src/integrity.c` 的 `g_guard_static[]` 由 2 条扩为 **6 条**
  （本体 + r2/r3/r4 + multi + `prot_integrity_check_self`）；
  `PROT_GUARD_N` 自动跟随，未改容量。

**验收 ①「单点 patch 不再足够」的机械判据（`tools/replica_check.py` 判据 4）**：
对 3 个副本各用 2 种手法打掉（`stub-ret0` = 换成 `return 0u`，与 DRILL7 的 `31 C0 C3` 同效；
`drop-key-bit` = 把某个关键位读取换成 `0u`，令该副本对该位失明），共 **6 组单点变异**，
全部编译后在同一输入域（12325 例，其中"检测到"的样本 12276 例）断言
**契约入口仍报"检测到"** ⇒ 实得 **入口漏报 = 0 / 6 组全通过**。
**对照（判据必须能失败）**：把 4 个入口 + 聚合器**全**换成 `return 0u` 后，
漏报 **12276** 例 ⇒ 该判据不是恒真。
**活体复核**（`tools/prot_dbg.py watch g_guard_hits --patch <符号>`，5 个符号逐个）：
patch 本体 / r2 / r3 / r4 / multi **任一**，`g_guard_hits` 均由 `0` 变为 `1`
⇒ 每个新副本**各自**被守卫快照守护，不是只有第一个候选被查。

**P1 机械判据（`tools/replica_check.py` 判据 1）**：借 `antidebug.h` 只依赖 `protdef.h`
这一点，把副本区独立切片编译成差分 harness，对 **12325 例**输入断言
4 个实现**逐位同输出**（`mismatch=0`）；并配**独立 oracle**（`any(7 个关键位) != 0`）
校验本体自身（`oracle_bad=0`）—— 纯差分对"全体一起错"是盲的。
另断言返回值域 `<= 1`（`range_bad=0`）与函数指针两两不同（`folded=0`，防 harness 自身被 ICF 折叠）。
**头文件漂移防护**：字段归属靠 `antidebug.h` 里关键位行的 `(咨询项)` 标注解析，
解析结果必须是 **7 关键 / 5 咨询**，否则报错（不静默接受漂移）。

**抗 `/OPT:ICF`（Release 的 `$linkHard` 含 `/OPT:ICF`，`build.ps1:526`）的机械判据**：
`build/demo.map` 里 5 个符号 VA **两两不同** ——
`prot_antidebug_detected 0x140005fe0` / `_r2 0x140006180` / `_r3 0x1400061c0` /
`_r4 0x140006290` / `_multi 0x1400060b0`。ICF 会把等价函数折叠成同一地址，
地址互异即证明折叠未发生。

**新增门禁项**：`tools/release_check.ps1` 第 **35** 项「判定多副本等价性 (replica_check)」，
项数 34/31 -> **35/32**（`tools/doccheck.py:149-155` 已同步）。
**必须先构建** `demo.exe`/`demo.map` 才有判据 2 与判据 4 的输入，故本项排在构建项之后。

**诚实边界**：
- **4 个副本全 patch 仍然能关闭判定**（判据 4 的全打掉对照正是这一点的实证）——
  冗余**提高成本**，不是不可破。
- 副本语义等价性由 `tools/replica_check.py` 守护，该判据覆盖**当前 12 个字段**
  （7 关键 + 5 咨询）；**未来新增字段不在覆盖内**（已写入 `modules.json` 的 `known_limits`）。
- §5 风险表预留的「只加函数**不重排**已有函数」已遵守：新代码全部追加在
  `src/antidebug.c` 文件尾，未移动任何既有函数。
- 「位置差异由构建期 seed 决定」**未实现**（见上），因此副本的地址分布目前是
  链接器布局的固定产物，不随 `--shuffle-seed` 变化。

**可选（成本中，先不做）**：`COST_ASYMMETRY §7` 的候选机制 3 ——
把判定聚合**下沉进 VM**（`// @vmcalc`）。**待 b/c 数据决定**。

## 9. ✅ R3.2-a 前置实证（2026-09-29）—— **判定点掩码区归属**

### 9.1 为什么先问这个

`src/integrity.c:433-436` 的 CRC 计算顺序：
```c
memset(mask, 0, len);
build_reloc_mask(base, mask, rva, len);        /* 重定位区清零 */
build_selfcrypt_mask(mask, rva, len);          /* **selfcrypt 区清零** */
crc = section_crc_masked(base, mask, rva, len);
```
=> **掩码区被清零** -> 改它**不影响 CRC** -> 完整性检测**抓不到**
（与 §38.4 记名的"静态 CRC 只承诺非掩码区"同源）。

### 9.2 实测结果（`build/r32a_verdict.json`）

| 判定点 | .text 偏移 | **在掩码区内？** | patch 是否被内存 CRC 抓到 |
|--------|-----------|----------------|------------------------|
| **`prot_integrity_check_self`** | +7488 | ✅ **在**（区 7488..8114）| ❌ **不被抓到** |
| **`prot_license_verify`** | +11776 | ✅ **在**（区 11776..11871）| ❌ **不被抓到** |
| `prot_antidebug_scan` | +22416 | ✅ 在 | ❌ 不被抓到 |
| `prot_antidebug_detected` | +22192 | ❌ 不在 | ✅ 会被抓到 |
| `prot_dbiguard_scan` | +8880 | ❌ 不在 | ✅ 会被抓到 |
| `prot_vmdetect_suspicious` | +624 | ❌ 不在 | ✅ 会被抓到 |

### 9.3 两个**高危缺口**（比原估计更严重）

```
① patch `prot_integrity_check_self` -> **完整性防护被静默关闭**
   根因: 校验器**自己**落在 selfcrypt 掩码区 ->
         **它不在自己 CRC 的覆盖范围内**（自我指涉缺口）
② patch `prot_license_verify` -> **授权恒通过且不被 CRC 抓到**
   （授权链的最关键判定，恰在掩码区内）
```
> **优先级据此排序**（R3.2-b 的落地顺序）:
> **④ license_verify** > **③ integrity_check_self** > ① antidebug > ② dbiguard > ⑤ vmdetect

### 9.4 ⚠️ 诚实边界（**必须标注，不得过度声称**）

```
"patch 能否**静默成功**"取决于**时序**，本步**未测**:
  · selfcrypt 对**解密后**的区域**有自己的 CRC 校验**（`CRC got/want`；
    构建立即输出 `prot_license_verify … crc=0x0b318d1e`）
  · D2b 是**调用级解密**（进入解密 / 离开重加密）
  => 若 patch 发生在**解密前** -> 解密产物错 -> selfcrypt 自身 CRC 可能抓到
     若 patch 在**解密后且离开前** -> 是否被察觉需实测
```
**=> 这**正是** DRILL9 要测的**：把"掩码区归属"（本步，静态分析）
与"运行时是否真能静默 patch"（DRILL9，动态实证）分开记录，
**不把静态推论当动态结论**。

### 9.5 本步结论

```
✅ R3.2 的**必要性被实测坐实**: 至少 2 个关键判定点**静态 CRC 覆盖不到**
✅ 给出**优先级**: license_verify > integrity_check_self > antidebug > dbiguard > vmdetect
✅ R3.2-b 的**快照校验是对的机制** —— 它**不依赖 CRC**，
   故"重算 CRC"与"落在掩码区"**两种规避都无效**
⏳ 待 DRILL9: 运行时能否真静默 patch（时序问题）
```

## 11. ✅ R3.2-b 第2组**修正结论**：守卫**确实有效**（2026-09-30）

> **本节推翻 §10 的否定结论。§10 的"守卫从未命中"本身是测量假象。**
> 这是本项目「测量 ≠ 缺陷」纪律的**第 6 / 7 次**实例 —— 且**由我在一小时内连犯三次**。

### 11.1 为什么前三次探查都没结论（**三次都是测量错误**）

| 次 | 错误 | 现象 | 差点得出的**错误结论** |
|---|------|------|----------------------|
| 1 | map 正则假设成 `0001:` + 8 位 RVA | 只解析出 **948** 个符号（实际 **2989**）→ 守卫符号"不在 map" | "符号被编译器优化掉了" |
| 2 | 用 map 的**偏好基址** `0x140000000` 去读 | 全部 `err=299`(ERROR_PARTIAL_COPY)、采样 0 轮 | "变量不存在" |
| 3 | 采样间隔 120ms，而**自增与 terminate 在同一 tick 内**（微秒级） | 最后一次采样永远是 0 | §10.1 的"守卫从未命中" |

**真实 map 行形态**（照抄，避免再次写错正则）：
```
 0004:00009e98   g_guard_hits   000000014003ce98  integrity.obj
```
正则：`^\s+([0-9a-fA-F]{4}):([0-9a-fA-F]{8})\s+(\S+)\s+([0-9a-fA-F]{16})`

**ASLR 实测生效**：模块运行时基址 = **`0x7FF6860A0000`**（每次运行可变），
**不是** `0x140000000`。`demo.exe` 大小 `0x4B000`，模块数 12。

> **对策（写进纪律）**：任何"读不到 / 恒为 0"的结论，**必须先用一个已知非零的靶子
> 证明读取链路是通的**（正向对照）。本次的对照 = `g_guard_dyn_n=3`（登记数，非零）
> —— 它一通，才说明"读到 0"是事实而非测量失败。

### 11.2 真正的根因：`continue` **整轮跳过**（一行代码）

`src/integrity.c:163-173`：
```c
if (prot_selfcrypt_enter(PROT_SELFCRYPT_GROUP_EXT) != PROT_OK) {
    /* 解密失败: 按 tamper 策略处理 */
    switch (g_wd_policy) {
        case PROT_POLICY_EXIT: prot_plat_terminate(PROT_EXIT_TAMPERED); break;
        default: (void)prot_plat_atomic_increment(&g_wd_tamper); break;
    }
    continue;                       /* <== **整轮跳过** */
}
```
看门狗一 tick 的顺序：
```
selfcrypt_enter(L163) -> check_self(L175, 段CRC) -> check_iat(L192)
   -> **check_guards(L211)** -> antidebug 周期复查(L227)
```
- **掩码区内**目标（`prot_license_verify` rva `0x3E80` ∈ `[0x3E80,0x3EDF)`；
  `prot_integrity_check_self` rva `0x2C50` ∈ `[0x2C50,0x2EC2)`）：
  被 patch 的是**密文** → **selfcrypt 自己的 per-region CRC 先失败**
  → `continue` → **守卫根本没跑** → `hits` 恒 0。
- **掩码区外**目标：段 CRC 失败 → 但 **CONTINUE 分支没有 `continue`** → 执行流继续
  → 到达 L211 → 守卫**可被观测**。

**⇒ §10 是"用错误的目标 + 读不到的时刻"得出的错误结论。**

### 11.3 决定性实验（`build/r32_decisive.json`）

**设计**：把运行期 `g_wd_policy` 置 `0`(`PROT_POLICY_CONTINUE`) ——
这是**观测手段，不是攻击**：它让"段 CRC 失败"只累加计数而不终止进程，
从而**恰好模拟"攻击者已中和段 CRC"**的场景（那正是守卫存在的意义）。
然后读 `g_guard_hits`。

**先写下可证伪的预测**（不许事后解释）：

| 用例 | `g_guard_hits` 预测 | `g_wd_tamper` 预测 |
|------|-------------------|------------------|
| 对照（只改策略、不打目标） | `= 0` | `= 0` |
| patch **掩码区外**目标 | `> 0` | 每 tick **+2**（段 CRC 一次 + 守卫一次）|
| patch **掩码区内**目标 | `= 0` | 每 tick **+1**（enter 失败即 continue）|

**实测（四项预测全部命中）**：

| 用例 | `g_guard_hits` 轨迹 | `g_wd_tamper` 轨迹 | 结果 |
|------|-------------------|------------------|------|
| 对照 | `0` | `0` | ✅ 无恒报 |
| ① `prot_antidebug_detected` | `0→1`(t=4.23s)`→2`(8.06)`→3`(11.28) | `0→2→4→6` | ✅ 预测命中 |
| ② `prot_dbiguard_suspicious` | `0→1`(3.02)`→2`(6.43)`→3`(12.69)`→4`(15.70) | `0→2→4→6→8` | ✅ 预测命中 |
| ⑤ `prot_vmdetect_suspicious` | `0→1`(3.23)`→2`(8.65)`→3`(13.07) | `0→2→4→6` | ✅ 预测命中 |
| ④ `prot_license_verify`（掩码区内）| **`0`** | `0→1`(5.22)`→2`(10.95)`→3`(14.75) | ✅ 预测命中 |

**⇒ 结论：判定点序言快照校验（守卫）机制正确且有效。**
`hits` 与 `tamper` 的比值（1:2 / 0:1）**定量吻合**三种 tick 路径，
说明模型完全正确、无残余未知。

### 12.5 位置抖动（2026-10-04 补做，关键设计③）

**问题（实测）**：`--shuffle-seed`（R3.1）只随机化**源文件/目标文件的链接顺序**；5 个符号
全在 `src/antidebug.c` 一个编译单元内，`cl /O2` 在该 TU 内的函数排布与函数间距**与链接
顺序无关**。三个 shuffle seed（`0x11111111` / `0x22222222` / `0x33333333`）下实测相对本体的
偏移**逐字节相同**：

| 符号 | seed1 / seed2 / seed3 偏移 |
|------|---------------------------|
| `prot_antidebug_detected` | `0` / `0` / `0` |
| `prot_antidebug_detected_multi` | `+208` / `+208` / `+208` |
| `prot_antidebug_detected_r2` | `+416` / `+416` / `+416` |
| `prot_antidebug_detected_r3` | `+480` / `+480` / `+480` |
| `prot_antidebug_detected_r4` | `+688` / `+688` / `+688` |

⇒ 攻击者只需定位**任意一个**副本，其余 4 个的地址即可用常量推算，无需符号表。R3.2-c 的
"多副本"在**同一次发布内**对定位成本的贡献接近于零。

**修法**：`include/protect/prot_noise.h` 新增 `PROT_PAD_STEP()`（语义恒等：局部 `volatile`
读-改-写，结果丢弃）与 `PROT_PAD_4/2/1()` 三个阶梯宏；`src/antidebug.c` 的 **5 个函数各取
一个互不重叠的 3 bit 位段**（本体 9..11 / r2 0..2 / r3 3..5 / r4 6..8 / 聚合器 12..14），
按位展开成 0..7 次 `PROT_PAD_STEP()` ⇒ 每个函数的**机器码长度**随 `PROT_BUILD_SALT` 独立变化。

- **为什么必须用 `#if` 阶梯**：`switch` 的**所有 case 体都会被编译出来**（长度恒定）；常量界
  循环是否展开由优化器决定（不可控）。只有**预处理期**条件编译才真正改变被编译的代码量。
- **为什么 5 个函数全填**：只填 3 个副本时，基线与聚合器未变，`delta(r2)` 仍含固定基线而恒定
  （首次实测即如此，`r2` 偏移纹丝不动）。本体自身也必须变，否则所有偏移仍含固定基线。
- **实测（4 个盐，各一次完整 Release 构建）**：

| 盐 | 偏移向量 `(本体, multi, r2, r3, r4)` |
|----|-------------------------------------|
| `0x12345678` | `(0, 304, 736, 800, 1232)` |
| `0xFF00FF00` | `(0, 432, 736, 800, 1008)` |
| `0x0F0F0F0F` | `(0, 432, 528, 800, 1040)` |
| `0xAAAAAAAA` | `(0, 368, 784, 912, 1280)` |

  4/4 有效构建得到 **4 个互不相同**的偏移向量；扫描两两间距的残余可预测性 = **无**
  （任意两符号的间距都随构建盐变化）。

**诚实边界**：判据 5 度量的是"间距**是否**随盐变化"，**不度量熵的大小** —— 若将来填充被削弱
到只剩 1 bit，本判据仍可能通过。每次构建的盐是随机 4 字节，发布构建的实际间距空间远大于
判据里用的 3 个盐。
