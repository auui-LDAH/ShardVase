## 1. 实测盘点（**计划的全部依据**）

### 1.1 要保护的**判定点**（可被 patch 成恒真/恒假者）

| # | 判定点 | 位置 | 被 patch 的后果 |
|---|--------|------|----------------|
| ① | **`prot_antidebug_detected`** | `src/antidebug.c:507` | **盾失效**（DRILL7 步骤 4 **实证**）|
| ② | `prot_dbiguard_scan` | `src/dbiguard.c:231` | 调试器守卫失效 |
| ③ | `prot_integrity_check_self` | `src/integrity.c:364` | 完整性自检恒 OK |
| ④ | `prot_license_verify` | `src/license.c:64` | 授权恒通过 |
| ⑤ | `prot_vmdetect_suspicious` | `src/vmdetect.c` | VM 探测失效 |
| ⑥ | `prot_antidebug_scan`（**setter**）| `src/antidebug.c:147/377` | **DRILL7 步骤 3 实证：patch 它盾仍有效**（它只是设置者）|

> **⑥ 是重要的对照**：DRILL7 步骤 3 与步骤 4 的差别证明
> **"patch 判定者"才对要害** —— 故 R3.2 应聚焦**判定者**（①③④⑤），
> 而不是设置者（⑥）。

### 1.2 DRILL7 的**边界条件**（决定 R3.2 的范围）

```
原文 L93 : "函数头 patch 可被完整性检测捕获 | 本项目 demo 的 CRC 覆盖 .text
            —— **注意：本次 test_target 无完整性校验**，真实 demo 会有 watch"
原文 L100: 待做第 4 条 "与完整性校验对抗：patch 后需同时处理 CRC 重算
            （hashpatch 思路）"
```

=> **DRILL7 的"盾失效"是在无完整性校验的目标上取得的**。
**真实 demo 的 `.text` CRC 覆盖它** —— 所以真实攻击链是:
```
patch 判定函数头  ->  触发 .text CRC 失配  ->  必须**同时重算 CRC**
（hashpatch 思路；本仓库已有 `tools/hashpatch.py`，攻击者可复用同一知识）
```
**R3.2 必须针对这条完整链**，而非 DRILL7 的简化版。

### 1.3 现成可复用的模式（**关键：不必从零设计**）

`src/integrity.c:517` 的 `prot_integrity_check_iat()`（G2 补洞）已经实现
**"启动快照 + 运行期逐字节比对"**:
```c
iat_snapshot_init();                       /* 启动时快照 */
...
for (i = 0; i < g_iat_snap_len; i++)
    if (((volatile uint8_t*)base)[iat.rva + i] != g_iat_snap[i])
        return PROT_ERR_INTEGRITY;         /* 运行期改写 -> 抓到 */
```
> **它防的正是"运行期写入"** —— 而 patch 判定函数头就是运行期写入。
> => **R3.2 的核心可以"复用该模式"扩展到判定函数头**，而不引入新解析。

### 1.4 已有的其它机制（避免重复建设）

| 机制 | 现状 |
|------|------|
| 看门狗 | **41 处**（`integrity.c` 7 处）—— 周期检查的载体已存在 |
| `rep` 变量传递 | **30 处**（`antidebug.h`/`main.c`/`gate.c`）|
| 控制流平坦化 | `prot_antidebug_detected` **已有**（S3 试点: switch-dispatch 状态机）|
| 抖动 | 4 处（`integrity.c`）|
| 布局随机化 | ✅ R3.1 实测 **95.2% 符号 RVA 变化** |

> ⚠️ **平坦化挡不住头 patch**：DRILL7 的 `31 C0 C3`（`xor eax,eax; ret`）
> 写在**函数序言**处 —— 控制流根本**不进入**状态机就返回了。
> => R3.2 的冗余必须是**结构性的**（多副本 + 运行时校验），
> 而非"把单个函数写得更绕"。

## 2. 目标与范围

### 2.1 目标

```
R3.2 使"patch 单个判定函数"**不再足够** ——
     攻击者须同时处理 ① 多处判定副本 ② 运行期函数头校验 ③ CRC 重算，
     即把 DRILL7 的"一次成功"变为**多点协同**。
```

### 2.2 做什么

| 方向 | 内容 |
|------|------|
| **判定函数头快照校验** | 复用 IAT 模式: 启动快照关键判定函数的**序言字节**，看门狗周期比对 |
| **判定多副本 + 交叉聚合** | 关键判定（先只做 `prot_antidebug_detected`）的**等价副本**，调用点聚合 |
| **DRILL9 端到端实证** | 完整攻击链（patch + CRC 重算 + 尝试绕过）-> 记录**真实成本** |

### 2.3 **明确不做**（防范围蔓延）

| 不做 | 理由 |
|------|------|
| 改动 `.text` **函数顺序** | **S1 已证的雷区**（`revoke` 同页自伤、`.text` CRC 原子性）—— R3.2 不碰布局 |
| 全量判定点一次做完 | 先只做 **① `prot_antidebug_detected`**（DRILL7 实证的要害），拿数据再扩 |
| 内核级防护 | 另一量级（`KERNEL_DRIVER_ASSESSMENT.md` 已评估）|
| 混淆强度提升（把函数写得更绕）| **挡不住头 patch**（§1.4），非本计划目标 |
| Android 侧 | `EXTENSION_PLAN.md` 独立线 |

## 3. 分步计划（**顺序 = 先证实 -> 再加固 -> 后扩展**）

### R3.2-a **前置实证**（**必做第一步，不直接改防护**）

> **纪律来源**：W1 教训（"部分成功 ≠ 可用"，§30）—— **先证实攻击链，再动手**。

| 项 | 内容 |
|----|------|
| 做什么 | 在**当前 demo**（有完整性校验）上复现 DRILL7 步骤 4: patch `prot_antidebug_detected` 头 |
| 判据 | ① **不重算 CRC** -> 是否被完整性抓到？② **重算 CRC**（用 `tools/hashpatch.py`）-> 是否盾失效？ |
| 交付 | `docs/ATTACK_DRILL9.md` 的"前置实证"节（含实测数据）|
| 决定点 | 若①已被抓 -> **R3.2 的价值集中在 ②**（patch+重算）这条链 |
| 工具 | ✅ **已查实**: `tools/attacker/winpe_sympatcher/winpe_sympatcher.exe`（已编译）|
| 命令（两步）| ① 定位: `winpe_sympatcher.exe --map <file.map> --sym prot_antidebug_detected`<br>② 写内存: `--pid <pid> --mod <exe> --pref 0x140000000 --addr 0x… --byte 31 --byte C0 --byte C3`（`31 C0 C3` = `xor eax,eax; ret`）|
| CRC 重算 | `tools/hashpatch.py <exe>`（本仓库既有；**攻击者可复用同一知识**）|

**验收**：明确回答"当前 demo 对 step-4 patch 的**真实**抵抗情况"，**不给推测**。

### R3.2-b **判定函数头快照校验**（**最小步，复用现成模式**）

| 项 | 内容 |
|----|------|
| 做什么 | 新增 `prot_integrity_check_prologues()`（命名待定）: 对**关键判定函数序言**做启动快照 + 周期比对；扩展现有看门狗循环 |
| 覆盖（首版）| `prot_antidebug_detected` · `prot_integrity_check_self` · `prot_license_verify` |
| **为什么复用 IAT 模式** | 同属"运行期写入检测"，模式已验证；**不引入新解析器**（降低风险）|
| 关键设计 | ① 快照时机 = **selfcrypt/完整性初始化之后**（避免把自身解密当篡改）② 失败动作**沿用现有策略**（`EXIT`/`FAKE`/`CONTINUE`）③ 快照容量不足时**明确失败**（**不静默截断** —— 与 §40 `_expires_safe` 同纪律）|
| 交付 | `src/integrity.c`（或新模块 + `modules.json` 登记）|
| 验收 | ① **patch 判定函数头 + 重算 CRC** -> **仍被检测**（这正是 R3.2-a 的②链）② 既有 28 项门禁全绿 ③ **3 连建稳定** ④ `repro_check` 仍绿 |

### R3.2-c **判定多副本 + 交叉聚合**

| 项 | 内容 |
|----|------|

| 关键设计 | ① 副本**语义必须逐位等价**（MODULE_GUIDE **P1**: 语义等价必须**可验证**）② 聚合做成"**多路 OR**"而非"取最后一个" ③ 副本的**位置差异**由构建期 seed 决定（复用 R3.1 体系）|
| 交付 | 副本实现 + 聚合函数（或 VM 内聚合，见"可选"）|
| 验收 | ① **单点 patch 不再足够**（patch 1 处 -> 仍检测到）② P1 语义等价有**可机械验证**的判据 ③ 门禁全绿 |

## 5. 风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| **新增代码改变 `.text` 布局** -> 踩 S1 雷区（`revoke` 同页 / CRC 原子性）| **高** | ① 每步**完整构建 + 3 连建** ② 只加函数、**不重排**已有函数 ③ 失败可按 commit 回滚 |
| 把**自身解密/初始化**误判为篡改（快照时机错）| **高** | 快照在 selfcrypt 初始化**之后**；先跑 `--selftest` + e2e 验证 |
| 多副本**语义不等价**（P1 违规）| 中 | ① 副本与原实现**逐位等价**（同一状态机）② 加**交叉断言**（同输入同输出）③ 门禁 `protchain P1/P2` 守护 |
| 误报导致**合法用户被杀**（`EXIT` 策略）| 中 | ① 首版**默认沿用现有策略**（不新增更激进的动作）② 边界写成 `known_limits` ③ 真机/多环境验证 |
| R3.2-a 无法复现 DRILL7（工具缺失）| 中 | 若内存 patch 工具不可用 -> **如实标注"未复现"**，并降级为"静态分析 + CRC 推理"（**不假装实证**）|
| Windows PowerShell 陷阱（本轮已多次踩）| 中 | 新脚本: **UTF-8 BOM** + **不用跨行 `-f`** + **反引号续行中间不放注释** + 改完**跑真实用例** |
