## 1. 一句话定位

**一个攻防双侧、可组合、以实证为准绳的开源反逆向框架。**

拆开说：

| 关键词 | 含义 | 现状 |
|--------|------|------|
| **攻防双侧** | 同一仓库里既有防御模块（`src/`），也有攻击工具与演练（`tools/attacker/`、`tests/attack_*.py`） | ✅ 已有，但未在同一抽象层 |
| **可组合** | 使用者按自己的威胁模型拼装，而非接受一个整体 | 🟡 刚起步（modules.json + compositions/） |
| **以实证为准绳** | 每项能力都有演练记录，每条边界都公开 | ✅ 最强项（7 轮演练 + 诚实边界） |
| **开源** | 机制公开，接受社区挑战 | 🟡 材料已备，尚未真正开源化组织 |

**这个组合本身就是差异化**：市面上的方案要么只卖防御（闭源壳），
要么只做工具集（无体系）。攻防同源 + 边界公开 + 可组合，三者兼具的项目极少。

## 2. 终态定义（v1.0 长什么样）

用**使用者视角**描述终态——不是功能清单，而是"一个人能做成什么"。

### 2.1 三种角色，三条路径

**角色 A：想保护自己软件的开发者**

```
1. 克隆仓库 → 运行向导 → 选择拼装图（standard）
2. 填写产品名/序列号模板
3. 把业务逻辑写成 prot_business_main(ctx)
4. 一条命令构建 → 得到受保护的 exe
5. 用 CLI 或 GUI 签发台签发授权
```
**目标：15 分钟内从零到受保护产物。**

**角色 B：想研究攻防的研究者**

```
1. 阅读 drills/ —— 每类攻击的完整记录（方法/结果/证据/缓解）
2. 运行 drills 复现脚本 —— 亲手验证每条记录
3. 提交新的攻击记录 → 触发防御模块改进
```
**目标：所有结论可复现，无"信仰型"声明。**

**角色 C：想贡献模块的开发者**

```
1. 阅读 MODULE_GUIDE（模块契约 + 检查清单）
2. 复制模板 → 实现 → 注册到 modules.json
3. 提交时必须附：单测 + 至少一条 drill 记录
4. modcheck 自动校验契约合规
```
**目标：新增模块有明确路径，且不破坏既有组合。**

### 2.2 终态的可验证标志

| # | 标志 | 为什么重要 |
|---|------|-----------|
| M1 | 任意参考拼装图可一键构建并通过自身测试 | 证明"可组合"不是口号 |
| M2 | 每条防御能力都能追溯到 drill 记录 | 证明"实证为准绳" |
| M3 | `modcheck` 能阻止破坏性组合 | 证明组合安全 |
| M4 | 新模块有模板 + 准入检查 | 证明可扩展 |
| M5 | 对外材料与内部能力无漂移 | 证明诚实 |

#### ⛔ 批3 判定：不做（附实测依据）

**问题**：`revoke` 无法从组合中排除，因为 `indirect_table.c` 硬引用
`prot_revoke_check`（该表由 `tools/indirect.py` 生成并写死 4 个函数）。

**先测量，再决定**（手工构造剔除 `indirect` 表引用的变体后对比）：

| 变体 | 产物 |
|------|------|
| 含 `revoke`（基线） | 228352 字节 |
| 排除 `revoke` | 227328 字节 |
| **收益** | **1024 字节（0.45%）** |

**代价**：`indirect.py` 需按组合过滤目标函数，且槽位置换与 `perm` 表长度
都会变化 —— 这直接触及 **P1/P2 风险区（布局敏感）**，需要重新验证
全部组合与 3 连建稳定性门槛。

**结论：收益 < 2KB，不值得。** 记为**已知边界**而非实现。

> 这是一次理性的工程取舍，不是遗漏。项目的既有纪律是"实测优先"——
> 测量结果表明这条路的性价比不成立。若将来 `revoke` 显著变大，可重估。

改用字母序源文件清单后，`full` 的加密函数由 **8 个降为 6 个**（`vm_var`

- 修复：`compose.py` 新增 `SOURCE_ORDER` 固化原顺序；并**去掉 `resolve()`

明确报告**（该组合本就不含完整性校验，没有 CRC 需要烧录）。属预期而非缺陷。

**为什么批2 比批1 难** —— 不是机械加 `#ifdef`，有三类真实语义问题：

#### 原定验收标准

1. `-Composition minimal` 能构建出更小的产物（缺模块不链接）
2. `-Composition standard` 产出与当前 demo 等价
3. 每个拼装图有独立测试脚本且全绿
4. `full` 组合构建时明确报出冲突处理方式

**风险**：布局敏感（`.text` CRC 原子性缺陷）——不同组合的 `.text` 布局不同，
**每个组合都必须重新生成 mask 与 CRC**。这是阶段 2 的技术核心难点。

**⚠️ 实测发现的额外难点（2026-09-20 核实）**：

阶段 2 的难度**不在构建参数，而在宿主**。实测 `demo/main.c`：

```
main.c 中直接调用模块函数 57 次
覆盖 antidebug / dbiguard / vmdetect / integrity / selfcrypt /
     vm_blob / license / vm_rekey / strcrypt 共 9 个模块
（hostid / revoke / license 另经 PROT_INDIRECT_CALL 间接表调用）
```

即 **`main.c` 是一个"全模块硬编码"宿主**。它无条件调用
`prot_antidebug_scan`、`prot_dbiguard_scan`、`prot_vmdetect_scan` 等。

**✅ 已用链接器取得权威证据（不是推测）**：

只编译授权链（7 个源文件）后，MSVC 报 **12 个无法解析的外部符号**，
全部来自被当作"可选"的 5 个模块：

| 缺失模块 | 未解析符号数 | 符号 |
|----------|-------------|------|
| `antidebug` | 4 | scan / detected / apply_policy / fake_active |
| `integrity` | 3 | check_self / start_watchdog / set_watchdog_callback |
| `dbiguard` | 2 | scan / suspicious |
| `vmdetect` | 2 | scan / suspicious |
| `indirect` | 1 | prot_indirect_resolve |

**结论**：宿主下限 = **11 个模块**（授权链 6 + 上述 5）。
在宿主改造前，任何组合都会被解析为这 11 个模块 —— 即
**组合机制已就绪，但组合的收益被宿主阻塞**。

实测对比（`tools/compose.py --list`）：

```
minimal   -> 11 模块 13 源文件   (仅省 2 个模块)
standard  -> 13 模块 15 源文件
```

**这意味着阶段 2 需要同时解决两层**：

| 层 | 问题 | 状态 |
|----|------|------|
| 构建层 | 按组合决定编译哪些 `src/*.c` | ✅ `tools/compose.py` 已就绪 |
| **宿主层** | `main.c` + `indirect_table.c` 硬引用未选模块 → **链接失败** | ⬜ 待改造 |

**两条可行路线**：

- **路线 A：宿主条件编译**（建议）—— `main.c` 用 `#ifdef PROT_MOD_<NAME>`
  包裹各模块调用段；`indirect.py` 按组合只登记已启用模块。
  产物不含未选模块代码，符合"可组合"本意；工作量集中在两个文件。
- **路线 B：模块桩** —— 未选模块提供空实现。构建层干净，但**不推荐**：
  桩会被链接进产物（与"更小产物"目标冲突），且桩本身是攻击面
  （可被 patch 成"永远无异常"）。

> **诚实的进度表述**：阶段 2 目前完成了**构建层**（组合解析 + 源文件清单 +
> 头文件生成），**宿主层未动**。在宿主改造前，"可组合"仍是声明而非事实。

**提取过程发现并修正的 4 个真问题**（若不修，矩阵会撒谎）：

1. **两类记录被混算** —— SDK 归档用 `PASS/CHECK` 是回归断言，不是攻击结论；
   混入会把"回归通过"算成"防御挡住攻击"
2. **捕获型条目被当结论** —— `*_out` 是执行输出快照，非结论
3. **模块推断拿不到线索** —— list 型记录只传 `result` 丢了 `detail` 中的
   `exit=2989 (integrity)` 等信号 → 113/122 误判；修正后降至 44
4. **过匹配比 unmapped 更糟** —— `V3_ledger_csv_injection` 命中 `forge`
   （"forged ledger rows" = 伪造台账行）与 `inject`（CSV **injection**，
   非代码注入）→ 误判 `license`。已加工具层优先判定

台账可改写 / CSV 注入 / 安装目录可写属**工具层与部署层**，
不被任何运行时防御模块覆盖 —— 这是框架的能力边界，如实记录而非强行归类。

## 8. 关键风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **宿主硬编码**（实测发现） | `main.c` 57 处直调 9 个模块；未选模块会导致链接失败 | 阶段 2 采用路线 A（宿主条件编译），见 §5 阶段 2 |
| **布局敏感**（`revoke` 同页、`.text` CRC 原子性） | 阶段 2 每个组合都要重算 mask/CRC，易出错 | 3 连建门槛 + 组合独立验证 |
| **组合爆炸** | 13 模块理论上 8192 种组合，无法全测 | 只验证**参考拼装图**，其余由 modcheck 静态校验 |
| **契约漂移** | modules.json 与代码不一致 | modcheck 接入门禁（已做） |
| **只防不攻的叙事** | 攻击侧工具若无演练更新会腐烂 | 阶段 3 的 drill 准入纪律 |
| **单人维护负担** | 文档与代码同步成本高 | 用工具强制（modcheck/drill 准入），而非靠记性 |
