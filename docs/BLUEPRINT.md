## 1. 一句话定位

**一个攻防双侧、可组合、以实证为准绳的开源反逆向框架。**

拆开说：

| 关键词 | 含义 | 现状（2026-09-21 实测） |
|--------|------|------|
| **攻防双侧** | 同一仓库里既有防御模块（`src/`），也有攻击工具与演练（`tools/attacker/`、`tests/attack_*.py`） | ✅ 有；**但未在同一抽象层**（攻击侧是脚本+手工编排，不与防御模块共用契约） |
| **可组合** | 使用者按自己的威胁模型拼装，而非接受一个整体 | ✅ **编译期可组合**（实测见 §3.4）<br>⬜ 运行期插件化（无 ABI） |
| **以实证为准绳** | 每项能力都有演练记录，每条边界都公开 | ✅ 最强项（9 轮演练 + 诚实边界 + 覆盖率 13/13） |
| **开源** | 机制公开，接受社区挑战 | 🟡 材料就绪（LICENSE/README/SECURITY/门禁），发布动作待做 |

**这个组合本身就是差异化**：市面上的方案要么只卖防御（闭源壳），
要么只做工具集（无体系）。攻防同源 + 边界公开 + 可组合，三者兼具的项目极少。

## 2. 终态定义（v1.0 长什么样）

用**使用者视角**描述终态——不是功能清单，而是"一个人能做成什么"。

### 2.1 三种角色，三条路径

**角色 A：想保护自己软件的开发者**

```
1. 克隆仓库 → 运行向导 → 选择拼装图（standard）
2. 填写产品名/序列号模板
3. 把业务逻辑写成 prot_business_main(ctx)
4. 一条命令构建 → 得到受保护的 exe
5. 用 CLI 或 GUI 签发台签发授权
```
**目标：15 分钟内从零到受保护产物。**

**角色 B：想研究攻防的研究者**

```
1. 阅读 drills/ —— 每类攻击的完整记录（方法/结果/证据/缓解）
2. 运行 drills 复现脚本 —— 亲手验证每条记录
3. 提交新的攻击记录 → 触发防御模块改进
```
**目标：所有结论可复现，无"信仰型"声明。**

**角色 C：想贡献模块的开发者**

```
1. 阅读 MODULE_GUIDE（模块契约 + 检查清单）
2. 复制模板 → 实现 → 注册到 modules.json
3. 提交时必须附：单测 + 至少一条 drill 记录
4. modcheck 自动校验契约合规
```
**目标：新增模块有明确路径，且不破坏既有组合。**

### 2.2 终态的可验证标志

| # | 标志 | 为什么重要 |
|---|------|-----------|
| M1 | 任意参考拼装图可一键构建并通过自身测试 | 证明"可组合"不是口号 |
| M2 | 每条防御能力都能追溯到 drill 记录 | 证明"实证为准绳" |
| M3 | `modcheck` 能阻止破坏性组合 | 证明组合安全 |
| M4 | 新模块有模板 + 准入检查 | 证明可扩展 |
| M5 | 对外材料与内部能力无漂移 | 证明诚实 |

四档预设可能只是硬编码分支。故实测一个**自定组合**

### 3.4.3 诚实的边界（尚未做到的）

| 边界 | 实测数据 | 含义 |
|------|----------|------|
| **单元是编译期 `#ifdef`，非运行期 ABI** | 13 模块 / 32 导出 / 平均 2.5；**无 `register` 钩子** | 加模块须改宿主源码（`demo/main.c` + `app_main.c` 各加 `#ifdef`），不能动态插拔 |
| **8 个模块不可排除** | 不可排除：`blob` `hostid` `indirect` `license` `revoke` `selfcrypt` `strcrypt` `vm`<br>可排除：`antidebug` `dbiguard` `integrity` `syscall` `vmdetect` | 宿主直接调用或间接表硬引用 |
| **攻防双侧不同层** | 攻击工具在 `tools/attacker/`、演练在 `tests/attack_*.py` | 是**数据层**对称（drills 记录），非**框架层**对称 |

### 3.4.4 结论

**编译期可组合：已实现且实测可验证。**
**运行期插件化：未实现**（无模块 ABI，宿主仍硬编码调用点）。

> 后续演进方向见 **§9 模块协议与接口规范（草案）** —— 目标是把
> "编译期可组合"推进到"**接口与协议不变的前提下，任意模块可替换/升级，
> 甚至全部替换仍能正常运行**"。

#### ⛔ 批3 判定：不做（附实测依据）

**问题**：`revoke` 无法从组合中排除，因为 `indirect_table.c` 硬引用
`prot_revoke_check`（该表由 `tools/indirect.py` 生成并写死 4 个函数）。

**先测量，再决定**（手工构造剔除 `indirect` 表引用的变体后对比）：

| 变体 | 产物 |
|------|------|
| 含 `revoke`（基线） | 228352 字节 |
| 排除 `revoke` | 227328 字节 |
| **收益** | **1024 字节（0.45%）** |

**代价**：`indirect.py` 需按组合过滤目标函数，且槽位置换与 `perm` 表长度
都会变化 —— 这直接触及 **P1/P2 风险区（布局敏感）**，需要重新验证
全部组合与 3 连建稳定性门槛。

**结论：收益 < 2KB，不值得。** 记为**已知边界**而非实现。

> 这是一次理性的工程取舍，不是遗漏。项目的既有纪律是"实测优先"——
> 测量结果表明这条路的性价比不成立。若将来 `revoke` 显著变大，可重估。

#### ✅ `build.ps1 -Composition` 已集成

```powershell
powershell -File build.ps1 -Config Release -Composition minimal
```

内部调 `compose.py` 生成 `prot_modconfig.h` + 源文件清单；未指定时默认 `full`
（等价于改造前行为）。`manifest.json` 新增 `composition` / `comp_modules`
字段，本次构建构成可追溯。

**集成时发现并修复一个真实回归（布局敏感）**：

改用字母序源文件清单后，`full` 的加密函数由 **8 个降为 6 个**（`vm_var`
被页冲突安全网跳过）。根因：**源文件链接顺序是语义相关的** —— 顺序变化
→ `.text` 布局变化 → 加密段与 `main` 的页关系变化。

- 修复：`compose.py` 新增 `SOURCE_ORDER` 固化原顺序；并**去掉 `resolve()`
  末尾的 `sorted()`**（那行会把顺序重新打乱，是"修复后仍不生效"的原因）
- 修复后 `full` 恢复 8 函数 / `hdr=196`，与改造前完全一致
- **新增模块须追加到 `SOURCE_ORDER` 末尾，不得重排**

**另一处真实耦合：`integrity` 与 `hashpatch`**。排除 `integrity` 后
`hashpatch` 报 `no .protcrc section found` —— 因为 `.protcrc` 段与三段 CRC
烧录表由 `src/integrity.c` 定义。处理：组合不含 `integrity` 时**跳过烧录并
明确报告**（该组合本就不含完整性校验，没有 CRC 需要烧录）。属预期而非缺陷。

#### ✅ 已解开：selfcrypt 与组合的耦合点

`tools/selfcrypt_proto.py` 原先**硬编码**加密目标且缺失即 `raise`，
导致组合排除 `integrity`/`antidebug` 时构建必然失败。现已改为：

## 10. 模块协议与接口规范（设计草案 · 待评审）

> **状态**：⬜ 设计阶段（未实施）。**动机**：完全开源面向社区后，需要一套
> 稳定的**模块协议与接口**，使各模块可**独立替换与升级** ——
> 极端目标是**全部模块都被替换后，系统仍能正常运行**（只要接口与协议不变）。
>
> **前置事实**（§3.4 实测）：当前是**编译期可组合**（`#ifdef` + 宿主硬编码
> 调用点），**没有**模块 ABI。本节的目的是把这条边界推进。
>
> ⚠️ **本草案已经评审，发现 2 处硬错误** —— 见
> [模块协议评审报告](REVIEW_MODULE_PROTOCOL.md)。实施前请先读该报告：
>
> · §10.9 的"产物字节不变"验收标准**不可达**（实测必然改变 .text/.rdata）
> · §10.3 的函数指针表与 `indirect` 的间接化目标**直接冲突**
>
> 下文为**原始草案**，保留以便对照评审意见；修正建议见评审报告 §5。
>
> 针对硬错误 2（函数指针 vs indirect 冲突），平衡方案见
> **[防护 vs 扩展性 — 平衡方案](PROTECTION_EXTENSIBILITY_BALANCE.md)**：
> 把协议与运行期发现分离 —— 接口用符号约定（零暴露）、
> 元数据只进开发构建、入口仍走 indirect。

### 10.1 目标定义（可验收）

| 级别 | 目标 | 验收方式 |
|------|------|----------|
| **L1 替换** | 用一个**第三方实现**替换某个现有模块（如 `antidebug`），其余不动 | 替换后构建 + 门禁全绿 + 该模块的 drill 记录仍适用 |
| **L2 升级** | 模块内部重写（改算法/加检测项），**调用方零改动** | 调用方源码 diff 为空 |
| **L3 全替换** | **所有**模块被替换为兼容实现，系统仍能运行 | 端到端跑通（授权 + 保护 + 门禁）|
| **L4 协议稳定** | 协议自身有版本与兼容规则，演进不破坏既有实现 | 版本协商测试 |

**核心约束**（来自项目既有教训，不可违背）：

> **协议只规定"接口与语义"，不规定"实现"。**
> 且必须承认：**P2（页粒度/布局）与 P1（语义等价可验证）是硬约束**，
> 任何协议都不能让模块绕过它们 —— 协议要做的是**让约束可被机器检查**，
> 而不是假装它们不存在。

### 10.2 分层：协议不管什么、管什么

```
┌─────────────────────────────────────────────────────────┐
│ L3 组合层   拼装图 + 校验器      ← 协议的一部分（依赖/冲突声明）│
├─────────────────────────────────────────────────────────┤
│ L2 模块契约 模块描述符 + 生命周期 ← **本协议的主体**          │
├─────────────────────────────────────────────────────────┤
│ L1 原语     crc32 / vm_rekey     ← 不注册为模块（公共设施）  │
└─────────────────────────────────────────────────────────┘
```

**协议明确不管**（留待实现自由）：

- 模块内部算法、数据结构、线程模型
- 模块是否用 C / 内联汇编 / 其它
- 模块的检测项数量与命名（只要求"结果可被聚合"）
- 模块的加密方式（但**必须声明** `touches_text`）

### 10.3 模块描述符（草案，基于 MODULAR_ARCH §3.1 扩充）

`docs/MODULAR_ARCH.md` §3.1 已给出 `prot_module_desc` 草图。本节在其上
补齐**协议所需的增量字段**（标注 ★ 为新增）：

```c
/* include/protect/module.h — 框架核心（草案） */
#define PROT_MODULE_ABI_VERSION  1u   /* ★ 协议版本: 接口变更时 +1 */

typedef struct prot_module_desc {
    /* --- 身份 --- */
    const char* name;              /* 唯一标识, 如 "antidebug" */
    uint32_t    abi_version;       /* ★ 本模块编译时遵循的协议版本 */
    const char* impl_version;      /* ★ 实现版本 (如 "1.2.0"), 供诊断 */

    /* --- 能力与阶段 (MODULAR_ARCH 已有) --- */
    uint32_t    caps;              /* prot_capability 位掩码 */
    uint32_t    phases;            /* 参与的 prot_phase 位掩码 */
    uint32_t    requires_caps;     /* 需要哪些能力先就绪 */

    /* --- 资源声明 (P2 硬约束, 机器可查) --- */
    uint32_t    wants_page_align;
    uint32_t    touches_text;
    uint32_t    needs_writable_dir;

    /* --- 依赖 (★ 从 caps 升级为具名模块依赖) --- */
    const char* const* requires_modules;  /* ★ NULL 结尾; 替代隐式依赖 */
    const char* const* provides;          /* ★ 本模块对外提供的符号前缀 */

    /* --- 诚实边界 (P4, 强制) --- */
    const char* const* known_limits;      /* NULL 结尾; 不得为空 */

    /* --- 生命周期钩子 (MODULAR_ARCH 已有, 本节补齐语义) --- */
    prot_status (*init)  (void);
    prot_status (*scan)  (void* report_out);
    uint32_t    (*decide)(const void* report);
    prot_status (*enforce)(prot_policy pol);
    prot_status (*fini)  (void);

    /* --- 报告自描述 (★ 新增, 解决"聚合器不认识第三方 report") --- */
    uint32_t    (*report_size)(void);     /* ★ 报告结构字节数 */
    uint32_t    (*report_flags)(const void* r); /* ★ 关键项位掩码 (见 10.5) */
} prot_module_desc;

/* 注册表: 链接期由各模块自行登记 (替代宿主硬编码调用点) */
extern const prot_module_desc* const g_prot_modules[];
extern const uint32_t                g_prot_module_count;
```

### 10.4 生命周期与调用约定

| 钩子 | 何时调用 | 契约（不可违背） |
|------|----------|------------------|
| `init` | 启动早期，按依赖拓扑序 | 不得失败退出；失败返回错误码由框架决定策略 |
| `scan` | 采集期 | **永不失败**（§3.4 既有约定）；结果写入 `report_out` |
| `decide` | 判定期 | 纯函数（无副作用）；返回 0 = 不可疑 |
| `enforce` | 执行期 | 按 `prot_policy` 执行；不得假设自己能终止进程 |
| `fini` | 退出前 | 允许为空（NULL） |

**关键约定（这三条是协议的核心价值）**：

1. **`scan` 永不失败** —— 单项检测失败 ≠ 检测到问题 ≠ 模块失败。
   环境不允许某项检测时，该项记 0 并继续。（既有三个检测器都遵守）
2. **`decide` 只聚合"关键项"** —— 咨询项不计入判定（误报成本高）。
   通过 `report_flags` 的位掩码表达，而非让聚合器解析结构体。
3. **`enforce` 不假设自己能终止** —— 终止是宿主/框架的责任
   （因为 `TerminateProcess` 不冲刷 stdout，本项目踩过这个坑）。

### 10.5 报告聚合协议（★ 本草案的关键增量）

**问题**：若第三方模块提供自己的 `report` 结构体，框架的聚合器如何理解它？

**方案**：模块通过 `report_flags()` 把报告"投影"为**协议定义的位掩码**：

```c
/* 协议定义的语义位 (与具体检测项解耦) */
typedef enum prot_finding {
    PROT_FIND_DEBUG_ENV     = 1u << 0,  /* 调试/分析环境 */
    PROT_FIND_INSTRUMENT    = 1u << 1,  /* 动态插桩/hook */
    PROT_FIND_VIRTUALIZED   = 1u << 2,  /* 虚拟化/沙箱 */
    PROT_FIND_TAMPERED      = 1u << 3,  /* 代码/数据被改 */
    PROT_FIND_LICENSE_BAD   = 1u << 4,  /* 授权无效 */
    PROT_FIND_ATTEST_FAIL   = 1u << 5,  /* 证明/签名失败 */
    PROT_FIND_CLOCK_ANOMALY = 1u << 6,  /* 时钟异常 */
    PROT_FIND_OTHER         = 1u << 7,  /* 其它（须在 known_limits 说明）*/
} prot_finding;
```

模块的 `report_flags()` 返回**关键项**命中的位掩码；框架据此聚合，
**完全不需要知道模块的内部结构**。这是"全替换仍能运行"的技术基础。

> **权衡（诚实说明）**：位掩码必然**有损** —— 它无法表达任意新颖的检测项。
> 故协议要求：使用 `PROT_FIND_OTHER` 的模块**必须在 `known_limits` 说明
> 其语义**，否则 `modcheck` 报错。宁可显式承认"协议表达不了"，也不要
> 让聚合器去猜。

### 10.6 可机器检查的规则（协议不靠自觉）

协议若不能自动校验，就是文档而已。故**每条规则都须有检查器**：

| # | 规则 | 检查方式 | 现状 |
|---|------|----------|------|
| R1 | 每个注册模块必须提供全部必需钩子 | `modcheck` 静态扫描 | ⬜ 待做 |
| R2 | `known_limits` 不得为空 | `modcheck`（已有同类规则） | 🟡 部分 |
| R3 | `requires_modules` 必须成闭包（无悬空依赖） | `modcheck`（**已实现**） | ✅ |
| R4 | `touches_text` 与 `verifies_text` 不得共存于同一组合 | `modcheck`（**已实现**） | ✅ |
| R5 | `wants_page_align` 模块不得与宿主同页 | 构建期检查（**已实现**） | ✅ |
| R6 | `abi_version` 必须等于框架的 `PROT_MODULE_ABI_VERSION` | `modcheck` | ⬜ 待做 |
| R7 | 每个模块至少 1 条 drill 记录 | `modcheck`（**已实现**） | ✅ |
| R8 | 使用 `PROT_FIND_OTHER` 必须在 `known_limits` 说明 | `modcheck` | ⬜ 待做 |
| R9 | 模块名 / 符号前缀不得冲突 | `modcheck` | ⬜ 待做 |

**已有 5/9**，说明这套规则是**渐进式**的，不需要推倒重来。

### 10.7 替换性测试（L1–L3 的验收方法）

**这是本节最重要的部分** —— 协议是否有效，只能靠"真的换掉"来证明。

```
T-L1 单模块替换: 用 src/_template.c 派生一个 antidebug 的替代实现
                  （接口相同、算法不同）-> 替换后构建 + 门禁全绿
T-L2 零改动升级: 修改模块内部（如把 7 个关键项换成 9 个）
                  -> 断言调用方源码 diff 为空
T-L3 全替换:     所有模块用"桩实现"（返回固定结果, 不改 .text）
                  -> 端到端跑通（这条会暴露 P2 相关假设是否被硬编码）
```

> **T-L3 的预期结论（诚实预判）**：`selfcrypt`/`integrity` 这类与
> `.text` 布局强耦合的模块，其"桩替换"**很可能失败** —— 因为
> selfcrypt 的 mask 与 hashpatch 的 CRC 是按**具体产物**生成的。
> 若失败，这就是协议的**真实边界**，应如实记录而非掩盖。

### 10.8 兼容性与版本策略

| 变更类型 | 版本动作 | 兼容性 |
|----------|----------|--------|
| 新增可选字段（放结构体末尾） | ABI 不变 | 旧模块仍可用 |
| 新增必需钩子 | ABI +1 | 旧模块须更新 |
| 改变钩子语义 | ABI +1 | **不兼容**，须迁移指南 |
| 调整位掩码含义 | ABI +1 | 同上 |

**规则**：`abi_version` 不匹配时**构建期报错**（不是运行期静默降级）——
与本项目 P3 教训一致：**可绕过的检查会掩盖缺陷**。

| 阶段 | 内容 | 验证 |

### 10.10 待评审的决策点

| # | 问题 | 选项 |
