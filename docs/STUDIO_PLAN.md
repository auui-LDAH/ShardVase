## 0. 先把目标函数说清楚

「做成 vscode 那样」有两种读法，成本差一个量级，**必须让用户选定**：

| 读法 | 含义 | 关键交付 |
|------|------|----------|
| **A. 体验像 VSCode**（推荐默认） | 我们要的是**断点 / 单步 / 变量窗 / 调用栈 / 输出面板**这一整套调试体验，外壳自己写 | 自研 Studio 外壳（本地浏览器 UI） |
| **B. 就是 VSCode** | 把编辑器交给 VSCode，我们只提供协议后端（DAP / LSP） | `shardvase` VSCode 扩展 + 调试适配器 |

本文档按 **A 为主线**、**B 为可选分支**编排（理由见 §4-D6）。两者共用 §2 的后端契约。

**「就像调试 java 一样」的准确落点**：Java 的体验建立在三件事上 ——
① 源码 ↔ 字节码的行号表（LineNumberTable）② 可暂停/单步的虚拟机 ③ 变量与调用栈视图。
本项目**已经有 ② 的雏形**（见 §1.4），**缺的是 ①**，③ 要新建。**这就是本规划的技术核心。**

## 1. 现状盘点（实测，2026-10-09）

### 1.1 生成侧 —— 成熟，缺统一出口

| 已有 | 说明 |
|------|------|
| `tools/solve_profile.py` | 威胁 → 能力 → 模块集 → **结构化构建计划**（含每模块「为何被选/被排除」） |
| `tools/compose.py --profile` | 拼装图 → `demo/gen/prot_modconfig.h` + 源文件清单 + 定义列表 |
| `build.ps1 -Composition` | 4 档拼装图（minimal/standard/hardened/full）+ Release/Debug 配置 |
| `tools/identity.py` | 每用户唯一（主密钥 → HKDF 派生，实测跨用户差异 93.04%） |
| `compositions/` `profiles/` `modules.json` | 组合、策略库、13 个模块的机器可读契约 |

**缺口**：这些能力是**多个 CLI**，各自参数风格不同，没有一个**统一的 JSON 出口**给面板消费。
`modules.json` 是唯一成熟的机器可读契约；profiles 求解结果目前是**文本清单 + 一个 JSON 旁路**。

### 1.2 测试侧 —— 覆盖面广，但**结果不可机读**

| 已有 | 说明 |
|------|------|
| `tools/release_check.ps1` | **41 项**门禁（默认跑 38 项，3 项由 `-With*` 开关控制） |
| `tests/e2e.py` | T1-T30；`tests/attacks.py` A1-A12；`tools/vmc.py` M2/M3；E1-E7；P1-P6 |
| `tools/gate_log.ps1` | 门禁落 **PowerShell transcript** 日志（`build/logs/release_check_<ts>.log`） |
| `tools/mutate_check.py` / `tools/selftest_audit.py` | 检查器自身的变异测试（判据必须自证能抓错） |

**缺口（本轮最大的可用性瓶颈）**：门禁输出是**文本行** `[ok]/[X]/[skip]` +
一份 PowerShell 转录。没有 `{name, status, seconds, detail}` 这样的结构，
所以「测试面板」「失败重跑」「历史趋势」**今天都做不了**。

### 1.3 主机级调试 —— CLI 已可用，能力窄

`tools/prot_dbg.py`（82158 B）现有子命令：`doctor` / `sym` / `mask` / `exit` /
`patch` / `read` / `watch`，并支持 `--json` 结构化证据落盘。

**没有**：内存断点、单步、反汇编视图、任何图形界面。
`docs/DEBUG_CONSOLE_PLAN.md` §4 逐字记着「**GUI 界面** | CLI 足够；且非交互环境可脚本化
（门禁要能用）」—— 本轮要**推翻这条决策**，但必须**保留它的理由**（见 §4-D8）。

### 1.4 VM 侧 —— **已经有一个调试器后端，只是没人把它当调试器用**

- `tools/vmenc.py`：**47 条指令**的 `INSTRUCTIONS` 表（`halt` 0x00 … `storr32` 0x2E）；
  `.vasm` 汇编器；构建期 opcode 置换 + 槽位置换（由 `key[1]` 派生）。
- ⭐ `tools/vm_reduce.py`：对运行期镜像做 **解密 → 用 key1 逆置换还原 canonical opcode
  → 栈式模拟执行 → 打印语义轨迹**（`trace.append(line + '  <-- HALT')`，`max_steps=2000`）。
  ⇒ **「像调试 Java 一样调试 VM 字节码」的后端逻辑已经存在**，
  缺的是**行号表、断点、暂停/继续、以及变量/内存视图**。
- ⚠ **缺口（唯一的新增基础设施）**：`vmenc.py` 只在**报错时**打印 `.vasm` 行号
  （`raise VasmError('line %d: ...')`），**不产出源码行号 ↔ 字节码偏移的映射**。
  没有它，断点只能打在**字节码偏移**上，做不到「在 `license_verify.vasm:34` 打断点」。

### 1.5 宿主/二进制侧

- `build/demo.map` + `tools/mapfile.py`（符号 → VA/RVA/.text 偏移）；
  `build/selfcrypt_mask.txt`（掩码区）；`tools/hashpatch.py`（CRC 目标表）。
- ⚠ **Release 链接参数含 `/DEBUG:NONE`** ⇒ **产物无 PDB** ⇒ 源码级原生调试**今天不可用**，
  需要另起一个带 `/Zi` 的构建配置（且**不得污染发布产物**）。
- ⚠ **selfcrypt 密文窗口**：保护函数只在 `enter/leave` 窗口内是明文，其余时间是密文
  （门禁第 39 项就是这个不变量的守护者）⇒ **原生单步走进密文区会失败**。
  这是「VM 级优先于主机级」的**硬技术理由**（见 §4-D3）。

### 1.6 UI 侧 —— 零起点

全库 **没有任何前端痕迹**：`.vscode` / `package.json` / `tsconfig.json` / `web` / `gui` /
`studio` / `electron` **全部不存在**。本机实测可用底座：

|------|------|
| Python 3.13.13 + **tkinter 8.6** | ✅ 可用（既有 `prot_sdk/wizard/prot_wizard.py`、`sdk_service/issue_console.py` 用的就是它） |

## 2. 架构：三条边界（先定边界，再排阶段）

```
        ┌──────────────── Studio 外壳（ST5，可选可换）────────────────┐
        │  生成面板 │ 测试面板 │ 调试面板 │ 输出/控制台 │ 模块视图     │
        └───────────────────────────┬─────────────────────────────────┘
                                    │  NDJSON over stdio / localhost
        ┌───────────────────────────▼─────────────────────────────────┐
        │  studio_core（ST0，纯逻辑，零 UI、零副作用、可无头调用）      │
        └───┬───────────────┬───────────────┬───────────────┬─────────┘
            │               │               │               │
      solve_profile    门禁/用例         prot_dbg        vm_reduce
      compose/build    release_check     sym/mask/      解密+逆置换+
      identity         gate_log          read/patch     栈式模拟
                                                         ▲
                                              ST4 新增：行号表 + 断点 + 单步
```

**边界 1（后端先行）**：任何能力必须先能**无头调用**并产出**机器可读**结果，UI 只是消费者。
**边界 2（契约统一）**：后端对外只有一套契约 —— **每行一个 JSON 对象的事件流**（NDJSON）。
选 NDJSON 而不是「一个 JSON 文件」：调试天生是**流式**的（断点命中、单步、日志、退出）。
**边界 3（UI 不入 CI）**：UI 在无显示环境的 CI 上不可跑，故**只有 core 进 CI 与门禁**。
这不是妥协，而是沿用 `DEBUG_CONSOLE_PLAN` §4 已记名的既有理由。

**风险**：中 —— W3.4 的「计划」是**文本清单 + JSON 旁路**，要确认旁路是否完整（缺字段则补）。
**成本**：S-M。**实际**：旁路**不完整**（缺 11 字段，ST1.3 的缺口比预期大），其余按计划。

**实施发现（2026-10-10，两条都是"看文档会写错"的）**：

1. **`deps` 与 `ordering` 是两种不同的关系，不可混画。**
   `tools/compose.py:topo_order` 的注释早已写明（2026-09-23）：`deps` = 运行时
   **能力**依赖，`ordering` = **链接顺序**；混成一张图会产生**假环**。
   原设计里 `plan.graph` 只回一套 `edges` + `topo`，面板按 topo 排列、按 edges
   画箭头 ⇒ 画出**自相矛盾的图**（实测每个组合两处相反）。已改为分两套边
   （`edges` / `order_edges`）+ `relations.why_not_mixed` + `topo_dep_violations`。
   ⇒ **这条是 ST1.4 的真实技术内容，不是包装**：原以为"复用 modcheck 即可"，
   实际要做的是**把两种关系分开陈述**。
2. **`modules.list` 的旁路缺 11 个字段**（含验收点名的 `known_limits`）。
   缺它会让 UI 把每个模块都渲染成「无已知局限」—— 那是**静默的谎**，
   比不显示更坏（项目 P4 诚实边界纪律）。

**实施偏离**：ST1.2 原写「core 暴露 `build(plan, config)`」，实施时 core **不接收
`plan` 对象**、只接收构建参数（`build_argv`）—— 因为「计划」与「构建命令行」之间
没有可靠的映射：`plan` 的产物是模块集合，而 `build.ps1` 吃的是 `-Composition` 名
或源码列表，两者的转换属 `compose.py` 的职责，塞进 core 会造出第二份口径。

而该函数的语义（**只取 scriptblock 最后一个值**）是 2026-09-23 一次事故后定下的。

1. 门禁自己新增 `-Only <正则>` 参数（子集运行），结果照常落 NDJSON；
2. core 新增 `test.gate.results`，**读** `build/logs/*.ndjson` 做历史查询。

等于把「什么算通过」这件事写两遍 —— 而两套口径中漂移的那一套
会安静地给出另一组数字。故此步的验收从「子集可跑」改为
**「子集可跑（门禁侧）+ 历史可查（core 侧）+ 两个出口逐项一致（verify）」**。
**成本**：M。

**实施发现（2026-10-10，两条都是「按计划做会得到错结果」的）**：

1. ⭐ **隔离改造必须查「工具自己的默认值」，不能只看命令行里写了什么路径。**
   `tools/selfcrypt_proto.py` 的 `--mask-out` 有硬编码默认 `build/selfcrypt_mask.txt`；
   第一次改造时 `build.ps1` 只改了**传给它的参数**，结果调试构建把这个**共享**文件
   悄悄覆盖了，而本变体目录下的掩码根本不存在 ⇒ Hashpatch 少带掩码，
   且发布侧掩码被污染。修法是 `build.ps1` **显式传** `--mask-out`。
   ⇒ 一般化：**「路径隔离」要覆盖「默认值」这一层**，否则最危险的那种失败
   （共享状态被悄悄改写）正好落在命令行看不见的地方。
2. ⭐ **`/OPT:NOREF /OPT:NOICF` 与运行期完整性校验不兼容。** 初版给 `Debug` 加了
   这两个开关（想着「调试版不该被优化掉代码」），结果 `demo.exe` 一律报
   「完整性校验失败」（rc `2989` / `0xBAD`）。根因是 `src/integrity.c` 的段 CRC
   缓冲是**栈上的 `uint8_t mask[0x40000]`**（256 KB），而它把
   **「缓冲区装不下」与「被篡改」报成同一个错误**：
   `if (len > sizeof(mask)) return PROT_ERR_INTEGRITY;`。
   实测 `/Od` 无优化代码体积约为 `/O2` 的 **3.3 倍**（`.text` 458688 B > 262144 B）
   ⇒ 必然触发。该上限历史上已被撞到过一次（`docs/BLOB_SIGN_PLAN.md` 记
   128 KB→256 KB 扩容）。**故 `Debug` 与 `Release` 用同一套优化开关**，
   只加调试信息 ⇒ 调试版与发布版**同尺寸**、行为逐字一致。
   ⇒ 一般化：**「调试构建」不等于「关掉优化」**；当一个项目有「体积上限」
   这类隐含约束时，关优化会把它变成一个**看起来像防御报警**的构建错误。

**实施偏离（2026-10-10）**：

1. **ST3.2 的隔离不是新写一套输出变量，而是给 `tools/genpaths.py` 加「构建变体」。**
   原计划只说「不同输出目录」。实施时选择了让**已有的路径单一来源**承担它
   （`--variant debug` / 环境变量 `PROT_BUILD_VARIANT`，`build_dir` 及其派生
   `b()` / `out_rel()` 自动带变体段），而不是在 `build.ps1` 里散落新变量 ——
   散落会让「产物在哪」出现第二个真值源。`variant` 为空时所有路径与改造前
   **逐字符相同**，这是「发布字节不变」得以成立的前提。
2. **ST3.3 的 `read` / `patch` 没有做成流式。** 它们是**一问一答**，
   硬做成事件流只会增加状态而无信息；只有 `watch` 天然是事件流。
   协议因此只把 `debug.watch` 放进 `STREAM_COMMANDS`。

修法（`tools/studio_server.py:_check_wiring()`，作为 `_check_real_ui()` 的第三条判据）：
① `app.js` 里每一处 `$('字面量')` 都必须在 `index.html` 里存在；
② **动态族逐个成员核对** —— `['gen','test',...].forEach((v) => $('view-' + v))`
的数组要展开；只判「前缀下至少有一个 id」**不够**：单独改掉 `view-vm` 时同族
其它成员还在，前缀检查照旧通过；③ 每个 `addEventListener` 的具名处理器必须在
`app.js` 里已定义；④ `index.html` 的 id 不得重复，且扫描面为空即失败（失锚）。

**刻意只做正向对账**。反向「每个 id 都必须被 `$()` 引用」会误报 9 处：
`adwarn`/`vmhint` 是纯提示元素，`pane-main` 与六个 `view-*` 由动态前缀取。

**诚实边界**：这条判据是**静态文本**层面的（问"名字对不对得上"），**不验证**
`addEventListener` 挂的事件类型是否正确、也不验证处理器行为 —— 那需要真浏览器。
`tools/studio_server.py --selftest` 里另有 6 条造坏输入的**负向**用例守着
`_check_wiring()` 自己（否则它被改成 `return True` 时，真实资产那条照旧绿）。

**实施补记（2026-10-11 同日晚）：接线判据的诚实边界**已由**真浏览器**判据兑现 ——
并且它落地后立刻抓到了一个静态判据**看不见**的真缺陷。

`tools/studio_ui_check.py`（门禁第 **45** 项 `Studio 真浏览器 (studio_ui)`）：起一个真的
headless Edge（CDP，零依赖纯 node 内置 `http` + 全局 `WebSocket`），把六个活动栏按钮
**逐个点一遍**，断言 ① 外壳启动（`#app` 不再是 `hidden`）② 每个按钮点得中
③ 点完**恰好只有它**可见 ④ 每个视图渲染出的叶子文本元素数不低于下限
⑤ `#gate-list`/`#vmimg` 点完必须真的被填上 ⑥ `window.__err` 必须为空。

**它抓到的第一件事**：`studio/static/app.js` 的 `loadCaps()` 原先写
`d.items.forEach(...)`，而后端 `capabilities` 发的是 **`capabilities{}`（以能力名为键的
对象）**，没有 `items` —— 于是「关于」页**从 ST5 起一直是空的**。三条既有判据全都
看不见：静态接线判据只问 id、needle 只问"提到没提到命令"、服务端 e2e 只验"资产被正确
读出且命令全通"。唯一的表现是一个 **unhandled rejection**。

**根因还牵出一行错的文档**：`docs/STUDIO_PROTOCOL.md` 当时写的是 `items[]` ——
**前端照着文档写，文档错了**（后端自检的 10+ 处都按 dict 用）。已一并改为
`capabilities{}`。教训：协议文档与实现不一致时，**不能默认"实现错了"**。

**三态**：找不到 Edge ⇒ `rc=2`（SKIP）。CI runner 上没有 Edge ⇒ 这一项在 CI 上恒为
SKIP。**SKIP 不是通过**（`PASS: N 项` 只数 `[ok]`）。因此本项的价值在**本机**：
它把"前端没在真实浏览器里跑过"这条诚实边界，换成了"本机每轮都跑"。

**判别力**（`build/_ui_neg2.py`，真实资产注入 + `finally` 逐字节还原）：真·原缺陷形态
（`d.items.forEach`，抛异常）⇒ rc=1 报 **3** 条（含 JS 错误）；静默为空形态
（`d.items || {}`，不抛）⇒ rc=1 报 1 条（靠渲染计数）；修复后基线 rc=0。
**两种形态都被抓到** —— 只锚定"有没有 JS 错误"会漏掉第二种。

**诚实边界**：① 只点六个活动栏与两个按钮，不覆盖表单交互与流式输出；
② 「渲染元素数下限」是启发式（实测 gen 14 / test 10 / vm 23 / host 6 / mods 159 /
about 30，下限设在远低于它的位置），它防的是"整块空掉"，不是"内容对不对"；
③ 依赖本机 Edge 与 node，**不在 CI 上生效**。

**面板与 CLI 的关系（D8 的兑现）**：面板调用的每一条命令都有**等价的 CLI 入口**
（`tools/studio_cli.py --cmd`），门禁第 42/43 项跑的是**无头自检**，UI **不入 CI**。
⇒ 「推翻『GUI 界面：CLI 足够』」推翻的是**结论**，不是**理由**。

**实施补记（2026-10-11 再晚）：契约本身从来没有被对账过**。§2.68 修了
`capabilities{}` **那一条**，接着的问题是「这一类还有没有别的地方对不上」。
准确的问题不是"有没有第二处"，而是：**「文档说了什么」与「代码实现了什么」
今天有没有任何一处判据在交叉验证？**

`build/_proto_gap.py` 的实测答：**没有**。把 `plan.list` 从
`docs/STUDIO_PROTOCOL.md` §5 表格里**整行删掉** ⇒ `tools/doccheck.py` /
`tools/studio_core.py --selftest` / `tools/studio_server.py --selftest` /
`tools/docclaim_check.py` **四个判据全是 rc=0**。反过来改名代码里的注册行，
只有 `studio_core` 自检变红 —— 而那一条**读的是代码自己**。

修法 = `tools/studio_proto_check.py`（门禁第 **46** 项 `Studio 协议 (studio_proto)`）：
① 命令集合双向一致（代码 25 + 流式 2 = 27，与 §5 表格相等）
② 文档声明的 `x[]`/`x{}` 键必须真的存在于 `dispatch()` 的载荷
③ 失锚必须失败。实测 10 条声明键命令**今天全部命中**（缺失键 = 0）
⇒ 这条判据当下的价值是**回归守卫**，不是刚抓到一个 bug。

**诚实边界**：只覆盖带 `[]`/`{}` 的声明键（另有 11 条命令只写自然语言，
**不被判**）；只保证名字两侧都有，不保证参数名与返回结构的正确性。

## 4. 关键设计决策（含理由与替代方案）

| # | 决策 | 理由 | 被否决的替代 |
|---|------|------|--------------|
| **D1** | **后端先行，UI 最后** | 沿用既有纪律（`prot_wizard.py`：核心与 GUI 解耦、可无头调用）；UI 不入 CI，逻辑必须可回归 | 直接写 UI 再补逻辑（无法门禁、无法自检） |
| **D2** | **NDJSON 事件流**作唯一契约 | 调试是流式的（断点/单步/日志）；一文件一 JSON 无法表达「暂停中」 | 一次性 JSON 输出；自造二进制协议 |
| **D3** | **VM 级优先于主机级** | 镜像可离线解密（免受密文窗口影响）、不 attach（不触发反调试）、不需 PDB、不碰 `src/` | 先做原生断点（撞 selfcrypt 密文窗口与反调试，且 Release 无 PDB） |
| **D4** | **行号表用 sidecar** | 不破可复现性、不撞 CRC/meta 四方一致判据、发布产物不携带 | 写进镜像头（会改产物字节、撞既有判据与 CI 逐字节比对） |
| **D5** | **断点先解释器、后真机** | 解释器断点零产物改动、零风险；真机断点须**只对副本**操作并给出哈希不变的证据 | 一上来改产物下 `brk`（动了 `build/` 原产物） |
| **D6** | **UI 默认走「本地浏览器 + 零依赖」；VSCode 扩展为可选分支** | 本机 **npm 不可用**；零依赖方案可离线、可离线单机、可被门禁覆盖（后端部分）；VSCode 扩展是最真但也是**最重的前置依赖** | tkinter（同形态先例多，但可停靠面板/多编辑区成本高）；Electron（必须 npm） |
| **D7** | **门禁结果是文本 + NDJSON 双出口，且必须同轮对照** | `PASS: N 项` 这句话被 `docclaim` T7 拿去与 `[ok]` 行数对账 ⇒ 改坏即门禁自伤 | 直接重写输出为 JSON（会破 T7 契约） |
| **D8** | **GUI 不入 CI，但「GUI 的理由」要留住** | 推翻 `DEBUG_CONSOLE_PLAN` §4 的「GUI 界面：CLI 足够」，但**保留它的理由**（非交互环境可脚本化）⇒ 所有能力仍有纯 CLI/无头入口 | 把能力只做在 UI 里（门禁就再也跑不了） |

## 5. 起步顺序与最小可用切分

用户原话「生成与测试工具 + 调试器和面板」可切成三块，**每块都能独立交付**：

| 交付块 | 阶段 | 用户拿到什么 |
|--------|------|--------------|
| **① 生成与测试工具** | ST0 + ST1 + ST2 | 选策略 → 看计划（含为何）→ 构建 → 跑测试 → **看结构化结果与历史** |
| **② 调试器** | ST3 + ST4 | 主机侧只读/读写面板 + **VM 字节码级断点、单步、栈/寄存器/内存视图** |
| **③ 面板外壳** | ST5 | VSCode 式分栏界面，把 ①② 装进去 |

**建议顺序：ST0 → ST4 → ST2 → ST1 → ST3 → ST5 →（ST6）**，而不是编号顺序。理由：
1. **ST4（VM 级调试器）是本规划唯一的技术新高地**，也是用户最想要的那一半；
   它**不依赖任何 UI**，却决定了整个 Studio 是否配得上「调试器」这个词。
2. ST4 的后端（`vm_reduce.py`）已存在，**先做它能把风险最高的部分提前暴露**。
3. ST2（测试机读化）要动 `release_check.ps1` 的 `Check`，是**第二个高风险点**，紧随其后。
4. ST1/ST3 是**包装既有能力**，风险低，可以晚做且不容易返工。
5. ST5 外壳最后做，因为它**消费**前面所有阶段的输出；提前做会不断返工。

**最小可用（MVP）** = ST0.1-0.2 + ST4.1-4.4 + ST2.1-2.2 + ST5.1-5.3
⇒ 「能对 `.vasm` 下断点、单步、看栈，并在一个面板里看到门禁结果」。

## 6. 风险与诚实边界（先记下来）

| # | 风险 / 边界 | 说明 |
|---|-------------|------|
| R1 | **解释器与虚拟机可能语义漂移** | ST4 的 Python 解释器是对 `src/vm.c` 的**再实现** ⇒ 两者可能分叉。缓解：以 `tests/unit_vm.vasm`、`vmc_tests.py`、`vm_unit` 为对照锚；**漂移即视为缺陷**，如实记录 |
| R2 | **调试器会被被测对象当成攻击** | `OpenProcess`/`ReadProcessMemory` 就是调试行为 ⇒ 目标可能以 `219` 退出。**这不是防御失效**（`DEBUG_CONSOLE_PLAN` 第 4 步已记名），协议里必须机读标注 |
| R3 | **Release 无 PDB** | 原生源码级调试需要新构建配置；**发布产物必须逐字节不变**（可复现性优先） |
| R4 | **selfcrypt 密文窗口** | 宿主级单步走进密文区间会失败 —— 这正是 ST4 优先的技术理由，不是可以绕过的细节 |
| R5 | **UI 无法进 CI** | 只测 core；UI 的回归靠**手动验收清单**（须写进文档，不能靠记忆） |
| R6 | **npm 不可用** | VSCode 扩展路线（D6-B）**前置未满足**；如需该路线，须先解决工具链 |
| R7 | **范围膨胀** | 「VSCode 那样」若被读成**编辑器**，成本是另一个量级 ⇒ §0 的 A/B 读法**必须先定** |
| R8 | **本规划未实施** | 本文档是规划；**未经实测的步骤一律标注为未验证**，不得在别处被当作已完成引用 |
